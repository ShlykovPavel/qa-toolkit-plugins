# Паспорт трекера: шаблон и опрос

**Что это.** Единственный файл специфики, на который опирается скилл `tracker-filing`. В
скилле — процедура «как заводить», в паспорте — «куда именно и через что». Понадобилось
зашить в скилл имя проекта в трекере, путь к токену или конкретную команду CLI — это
поле паспорта, а не строка скилла.

Если в проекте уже есть `project-passport.md` для `task-recheck` или `site-notes.md` для
`ui-bug-sweep` — не дублируй то, что там уже есть (адрес стенда, роли, доступы). Этот
паспорт — только про сам трекер и про синхронизацию находок с источником.

---

## Как заполнять

1. **Сначала дешёвая проба** — не спрашивай то, что проверяется одной командой (таблица
   ниже).
2. **Потом опрос** — только решения, которые проб не заменяют.
3. **Незаполненный пункт — это «не делать»**, а не «по умолчанию можно». Пока в паспорте
   нет ответа про апрув — считай, что апрув нужен на всё, включая чтение.
4. **Заполнил — покажи целиком человеку**, получи подтверждение прежде чем заводить первую
   карточку.

### Определяешь сам, до вопросов

| Что | Как |
|---|---|
| Есть ли готовый плагин/скилл/CLI для этого трекера в окружении | список установленных плагинов/скиллов, `<tool> --version` |
| Отвечает ли API трекера | один `GET` на список проектов или на текущего пользователя |
| Где лежит токен/конфиг, если инструмент документирует это сам | референс/README инструмента |
| Поддерживает ли инструмент вложения | ищешь в его референсе слово «attachment»/«вложение»; не нашёл — не значит «нет», значит «неизвестно», см. шаг 4 скилла |

### Спрашиваешь — только решения и границы

Какой конкретно трекер и инстанс (если их несколько). Нужен ли апрув на обращение к
трекеру, и на что именно — на чтение тоже, или только на создание. Куда заводить по
умолчанию (проект/доска), и есть ли предпочтение по спринту/итерации. Какой шаблон тела
карточки использовать, если не общий. Где источник находок (если он есть) и в каком
формате туда класть обратную ссылку. Кто решает приоритет — предлагаешь ты, утверждает
человек, или у него есть готовая шкала соответствий.

## Шаблон

Скопируй в `tracker-passport.md` в корне проекта (там же, где обычно лежит
`project-passport.md`) и заполни. Поля со `?` считаются незаполненными и блокируют работу
по соответствующему пункту.

```markdown
# Паспорт трекера

Проект: **?**. Обновлено: ГГГГ-ММ-ДД.

## 1. Трекер и доступ
| Что | Значение |
|---|---|
| Трекер | ? YouTrack / Jira / Linear / GitHub Issues / другое |
| Инстанс/URL | ? если self-hosted или нестандартный домен |
| Способ доступа | ? плагин/скилл (имя), CLI, прямой API |
| Где токен/конфиг | ? путь, не значение |
| Апрув на обращение | ? нужен всегда / только на запись / не нужен |

## 2. Проект в трекере
| Что | Значение |
|---|---|
| Ключ/имя проекта по умолчанию | ? |
| Внутренний id, если отличается от ключа | ? или «узнавать каждый раз запросом» |
| Доска по умолчанию | ? |
| Правило выбора спринта/итерации | ? спрашивать всегда / дефолт — текущий |

## 3. Шаблон карточки
| Что | Значение |
|---|---|
| Использовать общий `ticket-body-template.md` | ? да / нет |
| Свой шаблон | ? путь, если нет — общий |
| Кто решает приоритет | ? предлагает агент / есть готовая шкала соответствий — привести её |
| Язык текста карточки | ? |

## 4. Вложения
| Что | Значение |
|---|---|
| Документированы в используемом инструменте | ? да / нет / неизвестно |
| Если нет — пробовали эндпоинт вручную, сработало? | ? |

## 5. Источник находок (если есть)
| Что | Значение |
|---|---|
| Где живёт (вики/файл/страница) | ? путь |
| Формат обратной ссылки | ? как выглядит строка с номером карточки |
| Что обновлять вместе с бэклинком | ? реестр, счётчики, список «без задачи» |
| Репозиторий источника, если это файлы | ? путь; коммитить отдельно от чего? |

## 6. Границы
| Что | Значение |
|---|---|
| Что нельзя трогать в трекере | ? существующие карточки, чужие проекты |
| Что необратимо | ? закрытие, удаление, смена ответственного |
```

## Опрос: шесть вопросов

1. **Трекер и доступ.** Какой трекер и инстанс? Чем к нему обращаться — готовый
   плагин/скилл, CLI, прямой API? Где токен? Нужен ли апрув, и на что именно?
2. **Проект по умолчанию.** Какой ключ проекта/доски заводить по умолчанию, если не
   сказано иное? Есть ли правило выбора спринта или спрашивать каждый раз?
3. **Шаблон.** Подходит общий шаблон тела карточки, или в проекте свой формат?
4. **Приоритет.** Кто решает — агент предлагает, человек утверждает, или есть готовая
   шкала соответствий (например, «блокирует юзера → Major»)?
5. **Источник находок.** Есть ли документ/вики, откуда взяты находки? Нужно ли туда
   добавлять обратную ссылку на карточку, и в каком формате?
6. **Границы.** Что в трекере трогать нельзя категорически — даже если по ходу работы
   покажется, что «а вот эту старую карточку стоило бы поправить»?

## Чего в паспорте быть не должно

- **Текущие значения `Type`/`Priority`/`State`.** Они узнаются живьём каждый раз (шаг 2
  скилла) — в паспорте фиксируется только *как* их узнавать, если это нетривиально.
  Хардкод в паспорте — то же самое устаревание, от которого спасает динамическая проверка.
- **Содержание конкретных находок.** Паспорт — про механику трекера, а не про то, что
  сейчас заводится.
- **Секретов.** Токены — по путям, не значениями.
