# Каналы к фронту: чем и когда

## Решение

**База прогона — debug Chrome и скрипты.** Площадь обходит `${PLUGIN_ROOT}/bin/probe.mjs`, сценарий проходит
`${PLUGIN_ROOT}/bin/drive.mjs`, кадры и дампы кладёт на диск `${PLUGIN_ROOT}/bin/shot.mjs`. Один порт, одна среда, работает и в
CLI, и в Desktop, и по расписанию, и это единственная база, где есть сессия человека и файлы,
которые потом можно предъявить.

**Встроенный браузер — не база, а добор в двух местах, где он объективно сильнее:**

1. **Незнакомый экран.** `read_page` отдаёт элементы с `ref` — тыкаешь, не угадывая
   селекторы. У `${PLUGIN_ROOT}/bin/drive.mjs` этого нет, ему надо назвать текст или CSS.
2. **Сеть.** Он читает запросы, статусы и тела ответов. У `${PLUGIN_ROOT}/bin/drive.mjs` журнала сети нет
   вообще, а именно на сверке витрины с API находятся самые весомые баги и решается, чей
   дефект — фронта или бэка.

Плюс третье, бытовое: нет поднятого debug Chrome и человека рядом, чтобы залогиниться, —
работай встроенным, не жди.

**Чего не делать:** обходить площадь встроенным браузером (впятеро дороже и без находок) и
пытаться пройти сценарий из нескольких шагов `${PLUGIN_ROOT}/bin/probe.mjs` (каждый его запуск — новая вкладка,
второй шаг придёт на чистую страницу).

Остальное в этом файле — обоснование и детали.

---

К одной странице ведут четыре канала. Выбор между ними — не про экономию, а про то, что
канал физически может: у каждого есть класс задач, где остальные либо врут, либо не работают.

## Разделительная черта — состояние между шагами

Это главное, и это не про цену.

**Пошаговые каналы** держат живую страницу между твоими действиями. Заполнил поле одним
шагом — нажал кнопку другим — посмотрел результат третьим. Так проверяются сценарии.

**Одноразовые каналы** на каждый запуск открывают страницу заново. Сценарий из трёх
действий в них надо уложить в один вызов, иначе второй шаг придёт на чистую страницу.

| Канал | Состояние | Где доступен |
|---|---|---|
| Встроенный браузер агента | **держит** (одна живая вкладка) | Desktop / веб-клиент |
| `${PLUGIN_ROOT}/bin/drive.mjs` → debug Chrome | **держит** (подключается к открытой вкладке) | везде, где есть Bash + Chrome |
| `${PLUGIN_ROOT}/bin/probe.mjs`, `${PLUGIN_ROOT}/bin/shot.mjs` | не держат (новая вкладка на каждый запуск) | везде |
| Личный Chrome человека (расширение) | держит | где подключено расширение |

`${PLUGIN_ROOT}/bin/probe.mjs` не «хуже» — он про другое: обойти площадь и напечатать выводы. Пытаться пройти
им сценарий бессмысленно, как и обходить сорок страниц пошаговым каналом.

## Пять ситуаций

### 1. Обойти площадь, понять где смотреть — `${PLUGIN_ROOT}/bin/probe.mjs`, всегда

Любая среда, любой режим. Одна страница ≈ 700 символов, пятнадцать — 5.6 КБ. Дальше
точечно разбираются другие каналы, но начинается прогон отсюда.

```bash
${PLUGIN_ROOT}/bin/probe.mjs <url> --crawl 15                 # карта раздела
${PLUGIN_ROOT}/bin/probe.mjs <url> --viewport mobile          # то же на телефоне
${PLUGIN_ROOT}/bin/probe.mjs <url> --repeat 5                 # плавает или стабильно
${PLUGIN_ROOT}/bin/probe.mjs <url> --crawl 5 --dump raw/      # + сырьё файлами
```

### 2. Пройти сценарий там, где есть встроенный браузер — им

Клики, формы, живая сеть и консоль, а главное — **незнакомый интерфейс**: `read_page`
отдаёт дерево элементов с готовыми `ref`, по которым сразу можно кликать, не выдумывая
селекторов. Это его сильная сторона: смотришь — решаешь — нажимаешь, и так по кругу.

Помни про его особенности: собственный профиль (логины Chrome человека тут не действуют),
скриншот вдвое уменьшен, файл на диск не кладётся, а родная ширина панели может оказаться
уже мобильного перелома — **ширину задавай числами**, не пресетом.

### 3. Пройти сценарий там, где встроенного браузера нет — `${PLUGIN_ROOT}/bin/drive.mjs`

CLI, cron, любая среда с одним Bash. Человек поднимает Chrome с CDP-портом, дальше
**один вызов = один шаг**, состояние живёт между вызовами (проверено: скролл, введённые
значения и маршрут SPA сохраняются).

```bash
${PLUGIN_ROOT}/bin/chrome-debug.sh <url> --size 1440x1000   # один раз: окно нужного размера
${PLUGIN_ROOT}/bin/drive.mjs open <url>                  # перейти
${PLUGIN_ROOT}/bin/drive.mjs read                        # что на странице: заголовки, элементы
${PLUGIN_ROOT}/bin/drive.mjs click --text "Фильтры"      # клик по тексту
${PLUGIN_ROOT}/bin/drive.mjs type --sel 'input[type=search]' 'запрос'
${PLUGIN_ROOT}/bin/drive.mjs key Enter
${PLUGIN_ROOT}/bin/drive.mjs state                       # где я и что сломалось
${PLUGIN_ROOT}/bin/drive.mjs shot кадр.png               # снимок текущего состояния
```

**`click --text` берёт первый элемент с таким текстом, а не «активный».** Открыта модалка, а в
таблице под ней есть кнопка с тем же словом — клик уйдёт в таблицу, и увидишь ты это шагом
позже, по неожиданному диалогу. Замерено дважды, второй раз — на кнопке «Отклонить», которая
была и в строке таблицы, и в модалке подтверждения. Надёжный приём — пометить нужный узел
уникальным атрибутом и кликать по нему, а не подбирать более точную строку:

```bash
${PLUGIN_ROOT}/bin/drive.mjs eval "[...document.querySelectorAll('button')].find(b => \
  b.textContent.includes('Отклонить') && b.closest('[role=dialog]'))?.setAttribute('data-t','1')"
${PLUGIN_ROOT}/bin/drive.mjs click --sel '[data-t="1"]'
```

**Рабочий размер задаётся при запуске окна, а не подгоняется потом.** Вьюпорт выйдет на
~90 px ниже окна — интерфейс браузера.

Ширина по ходу — тремя разными способами, и путать их дорого:

| Что надо | Чем | Оговорка |
|---|---|---|
| Рабочая ширина на весь прогон | `${PLUGIN_ROOT}/bin/chrome-debug.sh --size 1440x1000` | правильный способ по умолчанию |
| Сменить ширину живого окна | `${PLUGIN_ROOT}/bin/drive.mjs resize 1024 900` | **уже 500 px окно не делается** — предел Chrome |
| Мобильные 390 px, в том числе под сессией | `${PLUGIN_ROOT}/bin/probe.mjs --viewport mobile --port 9222`, `${PLUGIN_ROOT}/bin/shot.mjs --viewport mobile --port 9222` | своя одноразовая вкладка **того же** Chrome: те же куки и тот же вход, окно человека не тронуто |
| Мобильный **пошаговый** сценарий | встроенный браузер (`resize_window width:390`) | он умеет 390 px и держит состояние |

**Эмулировать вьюпорт на живой вкладке нельзя** — это необратимо, см. ловушки. Мобильную
ширину в чужом Chrome берут только одноразовые скрипты, у которых своя вкладка.

Клики и ввод идут через `Input.*` — тем же путём, что настоящие мышь и клавиатура. Это
важно: `el.click()` и синтетические `Event` часть обработчиков игнорирует, и «кнопка не
работает» оказывается артефактом автоматизации. Проверено: `key Enter` доходит до формы
поиска и меняет URL, как у человека.

Чего у него нет по сравнению со встроенным браузером: дерева элементов с `ref` — нажимать
надо по тексту или селектору, то есть по незнакомому интерфейсу он ведёт хуже; журнала
сети; консоли за то время, пока он не подключён (сборщик ошибок ставится при `open` и
живёт в странице до полной перезагрузки, но всё, что случилось раньше, потеряно — для
консоли и сети есть `${PLUGIN_ROOT}/bin/probe.mjs` и встроенный браузер).

### 4. Авторизованные экраны — тот канал, в котором залогинился человек

Пароли агент не вводит (если паспорт проекта, раздел 7, не разрешает вход в окне браузера). Значит
логин делает человек — **внутри конкретного браузера**, и
дальше работать надо именно в нём. Профили не общие: вход в debug Chrome не даёт сессии
встроенному браузеру и наоборот.

```bash
${PLUGIN_ROOT}/bin/chrome-debug.sh https://стенд/ --size 1440x1000    # поднять окно
# → дальше человек логинится в нём руками
```

Скрипт берёт отдельный профиль (`~/.chrome-debug-profile`), а не личный: прогоны не трогают
личные вкладки, пароли и историю. Занятый порт он не молчит, а показывает, **чей** там Chrome
и какие вкладки открыты — потому что анонимный headless и залогиненное окно внешне
неразличимы. Побочная выгода живого окна: браузер уже поднят, и прогон вдвое быстрее
(5.8 с против 10.3 с на своём headless).

Дальше **каждый раз** проверяй, жива ли сессия: профиль тот же, а сессия истекает. Проверяется
она **только рендером защищённой страницы** — `document.cookie` и `localStorage` для этого не
годятся: сессионная кука обычно `HttpOnly` и из JS невидима, а пустой ответ канала и неумение
канала вернуть непустое выглядят одинаково. Замерено: на пустых `document.cookie` и
`localStorage` заход едва не записал «сессии нет» под живой сессией человека. Команда и признак
анонима — ниже, «Четыре проверки, без которых выводу верить нельзя», пункт 2.

### 5. Кадр как доказательство — `${PLUGIN_ROOT}/bin/shot.mjs`, для состояния — `${PLUGIN_ROOT}/bin/drive.mjs shot`

`${PLUGIN_ROOT}/bin/shot.mjs` берёт страницу с нуля целиком в полном разрешении и кладёт файлом. Если кадр
нужен **после действий** (открытая модалка, применённый фильтр, залогиненный экран) — снимает
`${PLUGIN_ROOT}/bin/drive.mjs shot`, потому что он видит текущее состояние вкладки.

## Встроенный браузер против debug Chrome: чем отличаются

Обе колонки — пошаговые каналы, и выбор между ними частый.

| | Встроенный браузер | `${PLUGIN_ROOT}/bin/drive.mjs` → debug Chrome |
|---|---|---|
| Незнакомый интерфейс | **дерево с `ref`, можно тыкать не думая** | по тексту или селектору — надо знать, куда |
| Цена шага | 1.5–2 КБ на чтение страницы | 100–600 симв. на шаг |
| Настоящие мышь и клавиатура | да | да (`Input.*`) |
| Сеть и консоль | **да, читаются целиком** | только собранные с момента `open` |
| Сессия человека | своя, логин внутри панели | **его, логин в окне Chrome** |
| Файл на диск | нет | **да** |
| Скриншот | вьюпорт, вдвое уменьшен | **страница целиком, полное разрешение** |
| Где работает | Desktop / веб | **везде, где Bash + Chrome** |

Коротко: **незнакомое разбираешь встроенным, известный сценарий гоняешь `${PLUGIN_ROOT}/bin/drive.mjs`.**
Нужны логины человека, файлы или CLI — `${PLUGIN_ROOT}/bin/drive.mjs` без вариантов.

## Что сколько стоит

Замер на живой странице (текста ~1.8 тыс. символов, ширина 1440). Цифры — порядок величины;
считай их отношениями, не константами.

| Канал | В контекст | Время |
|---|---|---|
| `${PLUGIN_ROOT}/bin/probe.mjs <url>` | **666 симв.** | 6–10 с |
| `${PLUGIN_ROOT}/bin/probe.mjs --crawl 5` | 2320 симв. (464/стр.) | 26 с |
| `${PLUGIN_ROOT}/bin/probe.mjs --crawl 15` | 5572 симв. (371/стр.) | 78 с |
| `${PLUGIN_ROOT}/bin/probe.mjs --dump <кат>` | +~100 симв. на стр. | +1 с |
| `${PLUGIN_ROOT}/bin/drive.mjs` один шаг | 150–600 симв. | 2–5 с |
| `${PLUGIN_ROOT}/bin/drive.mjs read` | ~800–1200 симв. | ~2 с |
| `${PLUGIN_ROOT}/bin/shot.mjs` → файл | **41 симв.** | 10–12 с |
| Браузер: `get_page_text` | ~1900 симв. | ~2 с |
| Браузер: `read_page interactive` | ~1500 симв. | ~2 с |
| Браузер: `screenshot` | ~375 токенов | ~2 с |

Отношение, ради которого всё это: **обход 15 страниц скриптом — 5.6 КБ контекста, тот же
обход чтением DOM — около 28 КБ.** Впятеро, и это без навигаций.

### Скриншот: цена растёт не с высотой страницы, а с площадью после сжатия

Картинка в контексте сжимается до 1568 по длинной стороне. Отсюда неочевидное:

| Кадр | В контексте | Токены | Читаемость |
|---|---|---|---|
| PNG 1440×1797 (страница целиком) | 1256×1568, масштаб 0.87 | ~2600 | текст читается |
| PNG 1440×4137 (длинная страница) | 546×1568, масштаб 0.38 | ~1100 | **мелкий текст не читается** |
| Вырезка 1320×380 из того же PNG | без сжатия | ~670 | полное разрешение |
| Скриншот встроенного браузера | 671×419 | ~375 | половина разрешения вьюпорта |

Длинная страница целиком выходит **дешевле** короткой и при этом бесполезна для глаз.
Полностраничный PNG — человеку и в отчёт, своим глазам — **вырезка**.

## Четыре проверки, без которых выводу верить нельзя

Каналы молчат о собственном состоянии, а вывод при этом получается уверенный и неверный.

**1. К какому Chrome ты подключён.** Скрипты занимают свободный порт своим headless, а
занятый — чужим браузером. `${PLUGIN_ROOT}/bin/probe.mjs` печатает это в поле `browser`, `${PLUGIN_ROOT}/bin/shot.mjs` и
`${PLUGIN_ROOT}/bin/drive.mjs` — в строке вывода; читай их. Нужен изолированный анонимный прогон — **задавай
свободный порт явно** (`--port 9333`).

```bash
curl -s http://127.0.0.1:9222/json/version   # кто держит порт
curl -s http://127.0.0.1:9222/json/list      # какие вкладки открыты
```

**2. Залогинен ли ты.** Только рендером защищённой страницы: `localStorage` может быть
полон, а сессионная кука — `HttpOnly` и из JS невидима. Открой страницу, требующую входа, и
посмотри `h1`: пришла форма входа — ты аноним. Поднятый под профилем человека порт **не
означает, что человек в нём залогинен**.

```bash
${PLUGIN_ROOT}/bin/probe.mjs <url защищённой страницы> --port 9222   # h1: "ВХОД" → аноним
```

**3. Какая ширина.** У каналов вьюпорты разные, пресеты врут («desktop» может означать
«вернуть родной размер панели»), а родная ширина бывает уже мобильного перелома. Правильный
порядок — **задать размер при запуске окна и не подгонять потом**, а ширину наблюдения
называть рядом с находкой. `${PLUGIN_ROOT}/bin/drive.mjs` печатает вьюпорт в каждом ответе, `${PLUGIN_ROOT}/bin/probe.mjs` и
`${PLUGIN_ROOT}/bin/drive.mjs resize` печатают `WARNING`, если запрошенная ширина не совпала с фактической.

**4. Разрешение кадра.** Половинный скриншот и сжатый до 0.38 полностраничный PNG не
годятся как доказательство мелкого дефекта — только вырезка.

## Ловушки, подтверждённые прогоном

- **Порт занят — прогон уехал в чужой браузер.** Анонимный headless и залогиненная сессия
  внешне неразличимы, и «поля нет» означает «я не залогинен».
- **Профиль человека ≠ залогинен.** Порт поднят, профиль правильный, вкладка со стендом
  открыта — а защищённая страница отдаёт форму входа.
- **Пресет вьюпорта соврал.** Вернул родной размер панели, уже мобильного перелома.
  Переданные вместе с пресетом `width`/`height` при этом игнорируются **молча**: пресет
  означает «сбросить эмуляцию к родному размеру», а не «получить заданные пиксели».
- **Эмуляция вьюпорта на чужой вкладке необратима.** Проверено на живом Chrome: снятое
  переопределение не возвращают ни `clearDeviceMetricsOverride`, ни
  `setDeviceMetricsOverride(0,0)`, ни то же плюс навигация. Пересчёт от границ окна даёт
  правильную ширину лишь **до первого перехода**, после которого эмулированная возвращается —
  то есть «починка» выглядит успешной и разваливается позже. Чистый вьюпорт даёт только
  **новая вкладка**. Практический вывод: на вкладке человека эмуляции не место; ширина
  задаётся при запуске окна, мобильная — одноразовым скриптом в его собственной вкладке.
- **Окно Chrome не бывает уже 500 px** (проверено на macOS: 390 и 480 дают 500). Мобильную
  вёрстку размером окна не проверить вообще — только эмуляцией.
- **Синтетические события не доходят.** `dispatchEvent`, «нажатый» через JS Enter — часть
  обработчиков их игнорирует, и получается ложная находка «кнопка не работает». Нажимай
  через `Input.*` (`${PLUGIN_ROOT}/bin/drive.mjs click/key`) или средствами браузера, не через `el.click()`.
  То же и с вводом: программная запись в `value` (native setter) **не доказывает**
  утверждение «поле принимает ввод длиной N» — его доказывают только реальные
  keydown-события. Нативный сеттер законен для других целей: быстро выставить стартовое
  состояние перед сценарием или намеренно подсунуть значение вне `maxlength`, чтобы
  проверить валидацию на невозможном для пользователя вводе. Использовал в одном прогоне
  оба способа — различай их в тексте кейса, а не молчи, каким из двух получено число.
- **Полностраничный PNG нечитаем в контексте** — чем длиннее страница, тем сильнее сжатие.
- **Только `--dump` и `${PLUGIN_ROOT}/bin/drive.mjs dump` сохраняют текст страницы файлом.** Вывод `${PLUGIN_ROOT}/bin/probe.mjs`
  — производные числа, `${PLUGIN_ROOT}/bin/shot.mjs` — пиксели. Нужен текст, который потом цитировать в
  отчёте, — это дамп.

## Встроенная панель браузера: что ломается молча

Панель — не тот же браузер, что под скриптами, и ломается она по-своему. Всё ниже подтверждено
прогоном. Общая цена одинакова: расхождение канала выглядит как дефект продукта и уезжает в
отчёт готовой ложной находкой.

**Размер вьюпорта и клики связаны — и это неочевидно.** Чтобы задать конкретный размер, вызывай
изменение вьюпорта **без** пресета, только числами, и сверяй результат по вьюпорту, который
печатает чтение страницы, а не по тому, что передал в вызов. **Но после вызова с явными числами
клики в этой панели попадают не туда: координата масштабируется дважды.** Признак — клик по
геометрически правильной точке не даёт эффекта, хотя элемент найден и не перекрыт. Порядок
проверки, прежде чем писать «кнопка не реагирует»: сбросить эмуляцию пресетом и повторить тот же
клик на естественном размере панели. Сработало — вывод про продукт снимается, и дальше
**интерактивные** проверки прогона идут без эмуляции вовсе. Для read-only наблюдений эмуляция
остаётся законной.

**Сетевой журнал панели накопительный.** Отсутствие новой записи доказывает «запрос не ушёл»
только тогда, когда список снят **явным вызовом непосредственно перед** действием и **явным
вызовом сразу после**, оба рядом по времени и оба сохранены файлом. Сравнение с журналом,
снятым в другой момент разговора, не годится. Приписывая пачку записей конкретному действию,
проверяй их позицию **относительно записи о самом действии** в дословном выводе инструмента — у
записи навигации свой узнаваемый формат идентификатора, — а не по соседству номеров и не по
тому, как хорошо это ложится в ожидаемый нарратив «сделал → увидел эффект».

**Общий селектор по роли берёт первый подходящий узел в DOM, не обязательно открытый.** Когда на
странице может существовать больше одного экземпляра одинакового по роли компонента (диалог,
поповер, выпадающий список), ищи его через идентификатор, совпадающий с `aria-controls` /
`aria-owns` **того триггера, который был нажат**. Общий `[role=…]` годится, только когда таких
элементов на странице заведомо не больше одного одновременно, и это проверяется счётом
(`querySelectorAll(…).length`), а не предполагается.

**Состояние контролируемого компонента, прочитанное сразу после события, ещё старое.** После
клика по компоненту с внутренним состоянием (чекбокс, селект, поповер библиотеки компонентов,
любой контролируемый компонент) состояние читается **отдельным вызовом через паузу**, а не в той
же функции, что событие. Признак — значение атрибута не изменилось, хотя событие точно
доставлено. Ложное «не сработало» здесь дороже задержки: следующий клик приводит компонент в
обратное нужному состояние, и форма отправляется не в том виде, в каком её описывает кейс.

**Центр `getBoundingClientRect()` инлайнового элемента может лежать вне элемента.** У ссылки или
подписи, чей текст перенесён на две строки, геометрический центр общего прямоугольника попадает
в межстрочный зазор. Перед кликом по инлайновому элементу, который может переноситься (короткие
ссылки в узких колонках, длинные подписи), проверяй `getClientRects().length` — больше одного,
кликай в центр **одного конкретного** прямоугольника.

**Заголовок виджета не доказывает его состояние.** Текст подписи и реальная внутренняя раскладка
— два разных источника, и они расходятся. Утверждение «открыт X» в виджете с собственной сеткой
(календарь, пагинация, карусель) проверяется арифметикой самой раскладки, а не чтением
`textContent` подписи. Расхождение подписи с раскладкой — сигнал остановиться и искать более
узкое наблюдение, которое от спора о состоянии виджета не зависит вовсе.

## Личный браузер человека

Расширение к его настоящему Chrome даёт готовые логины без возни, но ходит под его учёткой
во все открытые сервисы. Это **не дефолт**: включай, только когда задача требует именно
этих сессий, и скажи человеку, что работаешь в его браузере.
