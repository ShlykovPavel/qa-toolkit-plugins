# Генерация API-тестов (api-tests)

Вход — ресурс (тег спеки, пути, тикет или текстовое описание). Выход — рабочий
слой тестов: API-клиент, фикстуры домена, regression + smoke тесты, зелёная
верификация. Семантику API скилл берёт из среза OpenAPI-спеки и паспорта
проекта — не из догадок.

## Шаг 0 — Pre-flight (первым действием, до любой другой работы)

Прочитай `docs/project-profile.md` и выбери режим строго по таблице:

| Ситуация | Действие |
|---|---|
| Паспорта `docs/project-profile.md` нет | Одной фразой: «форк не настроен, запусти /setup-fork» — и СТОП. Файлы не трогать, интервью не начинать. |
| Запрос про фронтенд (Selenium/админка) или мобилку (Appium/Flutter) | Одной фразой скажи, что этот скилл покрывает только API-слой, и верни управление. |
| Запрос про починку/рефакторинг СУЩЕСТВУЮЩИХ тестов | Одной фразой скажи, что скилл генерирует новое покрытие, а починка — вне его скоупа; верни управление. |
| Запрос — только срез спеки, без тестов | Сделай срез `${PLUGIN_ROOT}/bin/openapi_slice.py` и покажи результат; пайплайн тестов не запускай. |
| Запрос — сквозной сценарий/флоу из нескольких эндпоинтов с состоянием между шагами (register→код из БД→login) | ОСТАЁШЬСЯ здесь (это один слой, один сценарий, а не «много доменов» → test-flow не нужен). Клиенты задействованных ресурсов уже есть → не разворачивай полную CRUD-матрицу на каждый: матрицу Шага 2 строй по ШАГАМ флоу и их негативным веткам. Проговори этот выбор пользователю до кода. |
| Иначе | Прочитай паспорт целиком: роли и ключи access_folder, конвенции кодов/конвертов, доступные таблицы БД, base URL, где спека. Работай дальше. |

**Оснащение машины — прогоном, а не памятью.** В этом же шаге:

```bash
preflight.py --use-marker
```

Молчит, пока на машине ничего не менялось (маркер `.preflight-ok` привязан к
хосту, не к клону — репозиторий ездит между машинами). Красное **не чинишь и
ничего не ставишь**: называешь пользователю, какой класс работы закрыт (колонка
«без неё» в выводе прогона), и продолжаешь в оставшемся
объёме — недостача идёт в отчёт. Для этого скилла критичны: `.venv` с pytest (иначе не собрать и не прогнать тесты), файл спеки из паспорта (иначе нет среза), `.env` (иначе прогон по живому стенду и сверка в БД закрыты — код пишется, зелёным его объявлять нельзя).
Заполнен ли `.env` — тоже из вывода прогона (строки с колонкой «Переменные»
называют пустые переменные по имени): сам `.env` и `.env.example` не читай —
доступ к ним обычно закрыт, попытки уходят в отказы.

**Автономный режим** (упоминается в шагах ниже) = пользователь недоступен для
ответов или явно попросил сделать всё без вопросов. В нём вместо любого
«спроси» — зафиксируй ДОПУЩЕНИЕ и продолжай; все допущения попадут в отчёт.

## Шаг 1 — Вход и срез спеки

1. Извлеки из запроса ресурс: тег спеки, пути или описание. Вводные из
   запроса (коды, поля, роли) фиксируй — не переспрашивай их.
2. Спека указана в паспорте → сделай срез (полную спеку в контекст НЕ читай):

```bash
python3 ${PLUGIN_ROOT}/bin/openapi_slice.py --spec <файл|URL из паспорта> --list-tags
python3 ${PLUGIN_ROOT}/bin/openapi_slice.py --spec <файл|URL> --tag <Тег> --out /tmp/slice.json
python3 ${PLUGIN_ROOT}/bin/openapi_slice.py --spec <файл|URL> --path /api/tasks --out /tmp/slice.json  # если во вводных пути, а не тег
```

   Тег не назван и не очевиден из запроса — покажи `--list-tags` и спроси
   (в автономном режиме — выбери тег по совпадению с именем ресурса и
   зафиксируй это как допущение).
3. Спеки нет → собери контракт вопросами по чеклисту «Шаг 0» из
   `docs/api-layer.md` (путь, тело, коды, конверт списка, роль). Ответ
   «не знаю» — нормальный: пункт станет допущением в матрице (Шаг 2).
4. **База знаний** — что вики проекта знает о ресурсе сверх сваггера.
   Дали поведенческую тест-спеку домена (тебя позвал оркестратор) — её
   секция 7 «Из базы знаний» уже это сделала, срез не повторяй. Иначе:

   ```bash
   qa-kb-slice --spec-slice <файл среза> --out <файл среза без .json>_kb.json
   qa-kb-slice --endpoint "POST /api/tasks" --out /tmp/slice_kb.json   # среза спеки нет
   ```

   Код 2 «база знаний не найдена» — вики нет, дальше как раньше. Есть —
   прочитай срез вики: куски `rules`, `bugs`, `caveats`, названия `cases`;
   из `related` (флоу и домен пишут правила словами, а путь не называют
   или сокращают) прочитай целиком страницы типов `flow`, `domain`, `api`,
   первые по порядку среза, — до трёх; шаги кейса — только его раздел `### TC-NN`. `history`
   (отчёты, заметки) и `raw/` вики не читай — это история и сырьё.

## Шаг 2 — Тестовая матрица ДО кода

Построй матрицу по `references/test-matrix.md` (прочитай его) и ПОКАЖИ
пользователю таблицей до написания кода. У каждой строки — источник:
`спека` / `паспорт` / `запрос` / `вики` / `ДОПУЩЕНИЕ`. Коды ответов и конверты бери
ТОЛЬКО из среза, паспорта или запроса; чего там нет — помечай ДОПУЩЕНИЕМ,
не выдумывай «типовое». Дождись подтверждения; в автономном режиме —
зафиксируй допущения (они пойдут в отчёт Шага 7) и продолжай.

**Строки из вики** (Шаг 1, п. 4) — только то, чего нет в срезе: правило,
лимит, переход, код ошибки, кейс `TC-NN`; источник — `вики` со страницей,
разделом или номером кейса и датой страницы. Открытый баг по эндпоинту —
строка «ожидаемо падает — BUG-N (задача)»: `xfail` со ссылкой ставится,
только если человек подтвердил ЭТУ строку; нового баг-репорта не
заводить; в автономном режиме тест не пишется, строка — в отчёт. Закрытый
баг — строка-регресс. `TO-BE` и оговорки стенда («только в БД»,
«необратимо») — строки без теста с причиной. Вики расходится со срезом —
не выбирай: вопрос человеку с обеими позициями (в автономном режиме — по
срезу, расхождение — допущением).

Для запроса-СЦЕНАРИЯ (флоу из нескольких эндпоинтов) матрица — это ШАГИ
флоу и их негативные ветки (например: регистрация ok / дубль email;
токен не появился в БД в срок; логин по неверному коду), а НЕ полный CRUD
каждого задействованного ресурса. Гейт «покажи матрицу до кода» и
финальная зелёная верификация (Шаг 6) действуют и здесь — не пропускай их.

## Шаг 3 — API-клиент

**Сначала проверь, есть ли уже клиент и модели ресурса в `src/`** (частый
случай — их мог сгенерировать `/api-clients` или прошлый прогон). Не гни
скилл под наличие/отсутствие кода — иди по развилке:

- **Клиента НЕТ** → пиши новый (дефолтный путь, см. ниже).
- **Клиент ЕСТЬ** → НЕ дублируй. Сверь его со срезом МЕХАНИЧЕСКИ, не на глаз:

  ```bash
  python3 ${PLUGIN_ROOT}/bin/api_client_check.py --spec <файл|URL из паспорта> --package src/<пакет ресурса>
  ```

  Скрипт сверяет пути/методы/коды, query, тела и поля моделей.
  - **Подходит** (покрывает нужные операции, коды и поля из среза, и в
    методах есть параметр `access` — см. ниже) → пиши тесты НА ЕГО ОСНОВЕ,
    клиент НЕ трогай.
  - **Частично** (нет нужного метода/поля, разошлись коды, нет `access`) →
    ДОпиши недостающее в существующий файл, дубль не создавай; повтори сверку
    до зелёной.

Дефолтный путь (нового клиента) строго по `docs/api-layer.md` (Шаг 2): копия
`src/example_resource/`, один класс на ресурс, `@staticmethod`, `status_code=`
с дефолтом из спеки, `deep_merge` для тела, докстринги на русском.

Два ОБЯЗАТЕЛЬНЫХ отличия от эталона (в example_resource этого нет) —
и в новом клиенте пиши их, и в существующем проверяй их наличие:

1. **Параметр роли**: в каждый метод добавь `access: str = "<основная роль
   из паспорта>"` и пробрасывай его в вызов HttpClient — иначе тесты
   401/403 написать невозможно. Для теста 401 тест передаёт `access=None`
   (HttpClient не добавит заголовок Authorization); для 403 — имя чужой
   роли. НЕ передавай access через `**kwargs` — так он утечёт в тело запроса.
2. **Строгие коды**: убери толерантный хак эталона
   (`expected = (200, 201) if ...`) — ассерть ровно тот код, что в спеке.

## Шаг 4 — conftest домена

По `docs/api-layer.md` Шаг 3: `create_<ресурс>` (yield id + терпимый
teardown) и `<ресурс>_cleaner`. Сверься с чеклистом файлов из Шага 1
api-layer.md — все 5 файлов, включая `__init__.py` и СОСЕДНИЙ conftest
(самая частая ошибка — тесты без conftest падают на коллекции).

Опирайся только на операции, существующие в срезе: если у ресурса НЕТ
delete — не выдумывай метод; фикстуру создания делай без удаления и
явно отметь в отчёте риск накопления тестовых данных. Смягчение — уникальные
имена и ассерты списка по принадлежности созданного, а не по количеству.

**Create без id в ответе** (204 без тела, id узнаётся только из списка) —
уборку регистрируй ДО мутации: сохрани признак, по которому сущность потом
найдётся (уникальное сгенерированное имя), и доищи её в teardown. Иначе в
красном прогоне, где список сущность как раз не отдал, уборки нет ровно там,
ради чего написан тест. Поиск и сверку держи разными шагами: поиск может не
покрывать все части отображаемого значения, и запрос «полным значением»
вернёт пусто.

**Предусловие со `pytest.skip`** (долгоживущий ресурс окружения) не
объявляй параметром фабрики, которой оно нужно лишь в части ветвей: skip
потянется на все тесты фабрики и молча обнулит суиту. Запрашивай его лениво
(`request.getfixturevalue("...")`) внутри нужной ветки, а «сколько тестов
скипнется без него» проверяй прогоном без ресурса, а не докстрингом.

## Шаг 5 — Тесты

По `docs/tests.md`: regression-классы `Test<Ресурс>Create/Read/Update/Delete`
в одном файле домена (классы — только для операций, существующих в срезе)
+ один smoke happy-path — по образцу `Tests/Smoke_tests/ExampleFeature/`:
своя директория, свой conftest и `__init__.py`. Обязательно: модульный
`pytestmark`, allure-разметка, уникальные данные из `src/data_generators.py`,
негативы через `status_code=` (результат — None, НЕ разыменовывать),
inline-созданное — в cleaner. Каждая строка матрицы Шага 2 → тест
(или явная пометка в отчёте, почему не написан).

Ссылка-обоснование в докстринге («см. баг-репорт …», «как в тесте …»)
ставится только после чтения цели: там должна быть именно эта операция, а
прецедент в коде — делать то же, а не противоположное. Нового расхождения в
старом документе нет — это новая запись в паспорт или новый файл, а не
ссылка на старый.

## Шаг 6 — Верификация

1. `make verify` — до зелёного (в среде без `.venv` эквивалент:
   `python3 -m compileall -q src Tests && python3 -m pytest --collect-only -q`).
   Лимит 5 попыток починки; упёрся — честный отчёт о том, что не
   собирается и почему, а не бесконечный цикл.
   Перед словом «зелёные» сверь `pytest --collect-only -q -m <маркер> <dir>`
   с тем же без `-m`: CI гоняет по маркеру, и домен без модульного
   `pytestmark` локально зелёный, а в CI не исполняется вовсе.
2. Живой прогон (`pytest -x -q Tests/Regression_tests/<домен>/`) — ТОЛЬКО
   если пользователь явно попросил гонять И `.env` заполнен (по прогону `preflight.py`). Падения
   классифицируй по `docs/tests.md` («Команды прогонов и логи»): баг теста —
   чини; расхождение со спекой — по п. 3; баг стенда — **вызови скилл
   `/bug-report`**: он отсеет баг теста, согласует короткое описание с
   пользователем и оформит репорт, а `xfail` ставится со ссылкой на этот
   репорт (его Шаг 5). Строки в отчёте и `xfail` без репорта мало. Лимит 10
   итераций.
   Данные на живом стенде создаются только через отслеживаемые фикстуры и
   cleaner'ы — id сохраняется в момент создания; сохранить его негде —
   диагностику вне тестов на стенде не делай. **Перебирать или угадывать id
   для DELETE/PUT запрещено без исключений**, даже ради «только своего»
   ресурса: потерял id — остановись, оставь ресурс и напиши человеку.
   Однажды такой перебор безвозвратно удалил чужой реальный ресурс.
3. **Расхождение спеки и стенда — ДЕФЕКТ, а не «особенность стенда, под
   которую подстраиваются».** Спека — документация API: разошёлся код
   ответа или форма тела — правят спеку или код на бэкенде, а не память
   тестировщика. Поэтому обязательны ОБА действия:
   - в клиент — ФАКТИЧЕСКОЕ значение (иначе тесты красные) плюс рядом
     комментарий «подстроено под стенд, спека расходится»;
   - в отчёт (Шаг 7) — ОТДЕЛЬНОЙ находкой, не сноской: что говорит спека,
     что отдал стенд, на каком запросе.

   Молча выставить дефолт по факту и промолчать запрещено — следующий агент
   решит, что так и задумано, и расхождение осядет в коде навсегда.

   Расхождение надо передать бэкенд-команде → `/bug-report` (он сам отсеет
   баг теста и согласует описание с тестировщиком до оформления).
4. **Допроси УСПЕШНЫЕ ответы, а не только падения** — зелёный тест ≠
   корректное API. По логу свежего прогона (`logs/log_*.log`) или
   контрольным `get` после `create` проверь:
   - поля, которые тест НЕ передавал: non-nullable тип без `required` в
     спеке молча получает default (`DateTime` → `0001-01-01`, int → `0`,
     bool → `false`) и сохраняется с кодом 200 — мусор в БД без ошибки;
     это баг API, а не теста, и он опаснее 500, потому что не виден;
   - коды успеха мутирующих операций (PUT/DELETE/PATCH): 200 по спеке
     против 204 по факту — типовое расхождение, дальше по п. 3.
5. **Ревью своего дифа — обязательно, до отчёта.** Зелёные verify и прогон
   доказывают, что тест РАБОТАЕТ, но не что он СООТВЕТСТВУЕТ конвенциям
   (утечка данных при падении до `yield`, проверяемый вызов в conftest,
   коды из шаблона вместо среза проходят зелёными). Свой код сам не
   ревьюй — автор не видит своих нарушений. Спавни агента `qa-auto:test-reviewer` со скоупом = список
   файлов, созданных и изменённых в этом прогоне, плюс путь к срезу спеки
   (пункт 8 чеклиста). Это шаг процедуры: отдельного разрешения
   пользователя он не требует.
   - **high и med** — чинишь в этом же прогоне; med не чинится только с
     причиной, записанной в отчёт. **low** — в отчёт.
   - После правок — `make verify`; был живой прогон — точечный перезапуск.
   - Были high → ОДИН повторный `test-reviewer` по тем же файлам. Больше
     кругов не заводи: остаток — в отчёт.
   - Находки по чужим файлам — «вне скоупа» в отчёт, не править.
   - **Под оркестратором** (тебя запустили сабагентом `/api-suite` или
     `/test-flow`, либо ты `test-fixer`) шаг пропусти: ревью у оркестратора
     отдельной фазой. В отчёте — строка «ревью — за оркестратором».

## Шаг 7 — Отчёт

Покажи: созданные/изменённые файлы; покрытие матрицы (написано / xfail /
требует человека); из вики — строк матрицы, `xfail` по багам с «да»,
строк без теста, расхождения вики со срезом (вики нет — «база знаний:
нет»); допущения, ждущие подтверждения; итог ревью Шага 6.5
(high/med/low до и после правок, число кругов, незакрытые находки с
причиной); напоминание — живой прогон возможен только в форке с
заполненным `.env`.

Найденная в работе ловушка ПРОЕКТА (особенность стенда, флаки, расхождение
доки/спеки с фактом) → допиши её коротко («сигнатура → как избегать») в
секцию «Копилка ловушек проекта» в `docs/api-layer.md` или в паспорт
проекта И упомяни это в отчёте.

**Для вики.** Что работа выяснила о продукте — правило, которого в вики
нет, расхождение стенда с вики (не только вики со срезом), баг стенда,
вопрос продукту — выведи в отчёте блоком «Для вики»: находка → эндпоинт с
методом → где она записана в автотестах. Блок — не вопрос: дальше сразу
раскладка по страницам вики пользователю (куда что ложится — справочник
«находка стенда» скилла `qa:kb-ingest`). Вопрос один, на раскладке. После
«да» первым действием **вызови скилл `qa:kb-ingest`** с находками и
пометкой «раскладка показана, „да“ получено» — вики пишет он; сам по
справочнику вики не правь. Запись в паспорт или `docs/api-layer.md` остаётся — вики она
не заменяет. Автономный режим или «нет» — блок остаётся в отчёте с пометкой
«не занесено». Находок нет — строка «для вики: нет». Вики у проекта нет
(срез Шага 1 ответил кодом 2) — блока нет.

## Границы и безопасность

- Не изменяй `example_*` файлы и `docs/*.md` — они эталоны (единственное
  исключение — секция «Копилка ловушек проекта», Шаг 7).
- Не трогай чужие домены в `src/` и `Tests/` — только свой ресурс.
- Никаких значений секретов и хардкода URL — только `config.py`/`.env`
  (имена переменных — из колонки «Переменные» `docs/toolchain.md`).
- Не коммить без явной просьбы.
- Данные между тестами не передавать; scope='session' для тестовых данных
  запрещён (см. CLAUDE.md).
