# Генерация API-клиентов (api-clients)

Вход — OpenAPI-спека (файл/URL из паспорта или из запроса) и, опционально,
список тегов. Выход — клиентский слой: на каждый домен `__init__.py` +
`<домен>.py` + `models.py`, ничего в `Tests/`. Семантику API скилл берёт из
среза спеки и паспорта — не из догадок и не из соседнего домена.

Клиенты этого слоя потом используют тестовые скиллы (`api-tests`,
`api-suite`) — поэтому цена ошибки здесь умножается на все будущие тесты.

## Шаг 0 — Pre-flight (первым действием, до любой другой работы)

Прочитай `docs/project-profile.md` и выбери режим строго по таблице:

| Ситуация | Действие |
|---|---|
| Паспорта `docs/project-profile.md` нет | Одной фразой: «форк не настроен, запусти /setup-fork» — и СТОП. |
| Просят вместе с клиентами написать тесты/фикстуры/conftest | Одной фразой: тесты — это `api-tests` (ресурс) или `api-suite` (вся спека); верни управление. Сам тесты НЕ пиши. |
| Запрос про фронтенд или мобилку | Скажи, что скилл покрывает только API-слой, и верни управление. |
| Клиент домена уже существует | Расширяй существующий файл, дубль не создавай. |
| Иначе | Прочитай паспорт целиком: сервисы и их пакеты в `src/`, роли и ключи `access_folder`, конвенции кодов и конвертов, где спеки. Работай дальше. |

Прочитай `docs/api-layer.md`.

**Оснащение машины — прогоном, а не памятью.** В этом же шаге:

```bash
preflight.py --use-marker
```

Молчит, пока на машине ничего не менялось (маркер `.preflight-ok` привязан к
хосту, не к клону — репозиторий ездит между машинами). Красное **не чинишь и
ничего не ставишь**: называешь пользователю, какой класс работы закрыт (колонка
«без неё» в выводе прогона), и продолжаешь в оставшемся
объёме — недостача идёт в отчёт. Для этого скилла критичны: `.venv` с pytest (сверка `${PLUGIN_ROOT}/bin/api_client_check.py` импортирует модули клиентов), файл спеки из паспорта.

**Автономный режим** = пользователь недоступен или явно попросил без
вопросов. В нём вместо «спроси» — фиксируй ДОПУЩЕНИЕ и продолжай.

## Шаг 1 — Спека, сервис, раскладка

1. Определи по паспорту, к какому сервису относится спека и какой у него
   пакет: `src/<сервис>/<домен>/`. Спек в паспорте больше одной → плоский
   `src/<домен>/` запрещён (коллизия имён тегов между сервисами).
2. Полную спеку в контекст НЕ читай, работай срезами:

```bash
.venv/bin/python ${PLUGIN_ROOT}/bin/openapi_slice.py --spec <файл|URL> --list-tags
.venv/bin/python ${PLUGIN_ROOT}/bin/openapi_slice.py --spec <файл|URL> --tag <Тег> --out _specs/<тег>.json
```

   Спека может быть и JSON, и YAML — скрипты читают оба формата, но YAML
   требует PyYAML из `requirements.txt`, поэтому зови интерпретатор
   проекта (`.venv/bin/python`), а не системный `python3`.
   `_specs/` — директория срезов в корне репо, она в .gitignore.
3. Теги в запросе не названы → покрываем все теги спеки.

## Шаг 2 — Масштаб: сам или fan-out

- **До 3 тегов** — пиши сам, домен за доменом.
- **Больше 3** — fan-out сабагентами, волнами не больше 3 одновременно;
  один агент = один домен (домены не пересекаются по файлам). Перед
  запуском покажи план таблицей: домен → число операций → путь к срезу.

В промпт каждому агенту обязательно: путь к файлу-срезу, целевая
директория, «прочитай `docs/api-layer.md` и `src/http_methods.py` до написания
кода», ВСЕ правила Шага 3 этого файла,
«сабагентов не запускай, работай сам», «тесты не пиши».

## Шаг 3 — Клиент домена

Эталон — `src/example_resource/example_resource.py` и, если в форке уже
есть написанные домены, соседний принятый домен. Базовые правила — в
`docs/api-layer.md` (Шаг 2); ниже — то, на чём ломаются генерации:

1. **Сигнатуры HttpClient читай в `src/http_methods.py`, а не по памяти.**
   У `post/put/patch` тело — обязательный позиционный аргумент: вызов
   `HttpClient.patch(url, access="user")` падает с TypeError. Нет тела —
   передавай `None` явно.
2. **Каждый тип в аннотации должен быть определён или импортирован в этом
   же модуле.** Python вычисляет аннотации в момент `def`, поэтому ссылка
   на ненаписанную модель роняет импорт всего домена — и `compileall`
   этого НЕ видит.
3. **Модель ответа берётся по `$ref` конкретной операции**, а не по
   похожести имени: pydantic молча игнорирует лишние поля, поэтому не та
   модель не падает, а тихо теряет данные.
4. **Имя метода — от смысла эндпоинта** (`get_page`, `get_attachments`,
   `mark_all_read`, `get_details`). Машинные суффиксы `get_list_2`,
   `get_list_3` запрещены: с ними невозможно читать тесты.
5. **Все query-параметры операции** пробрасываются в `query_params={...}`
   (фильтры, поиск, сортировки — не только limit/offset). Query-строку
   руками f-строкой не собирать.
6. **Тело запроса — только поля из `requestBody` операции.** Нет
   requestBody — нет тела и нет придуманного аргумента под него.
7. `status_code=` в каждом методе с дефолтом из спеки; при `>= 400` —
   ранний `return None` ДО парсинга.
8. Роль — `access="<роль из паспорта>"`; сервис без авторизации (гостевой
   API) — вызов без `access` вовсе. Имена ролей не выдумывать.
9. Ни одного метода-заглушки: если операция возвращает объект или массив,
   клиент обязан его разобрать и вернуть, а не `return None`.
10. Докстринги на русском; BASE_URL только из `config.py`.

## Шаг 4 — Модели ответов

По `docs/api-layer.md` («Модели ответов»): `models.py` рядом с клиентом,
имена полей КАК В СПЕКЕ (camelCase, 1-в-1), `nullable`/необязательное →
`Optional[...] = None`, enum-поля спеки типизируются как `str` (отдельных
Python-Enum не заводить — их отсутствие как раз и роняет импорт, см. Шаг 3.2).

Схема, повторяющаяся в нескольких доменах (общий конверт, общая карточка),
переезжает в `src/common_models.py` и импортируется оттуда — копий в
каждом домене быть не должно.

## Шаг 5 — Верификация (без стенда, обязательна)

```bash
.venv/bin/python -m compileall -q src/<сервис>
.venv/bin/python ${PLUGIN_ROOT}/bin/coverage_check.py --spec <спека> --package src/<сервис>
.venv/bin/python ${PLUGIN_ROOT}/bin/api_client_check.py --spec <спека> --package src/<сервис>
```

`${PLUGIN_ROOT}/bin/api_client_check.py` — главный гейт: сверяет пути, методы, коды, query,
тела, модели и поля со спекой, импортирует каждый модуль и проверяет
аннотации. **Слово «готово» допустимо только при нулевом числе ОШИБОК**
(предупреждения — разбери каждое и либо почини, либо объясни в отчёте).
Лимит 5 итераций починки; упёрся — честный отчёт, а не бесконечный цикл.

Окружение не собрано (нет `.venv`) → `--skip-import`, и это ограничение
явной строкой в отчёт: статические проверки пройдены, импорт не проверен.

## Шаг 6 — Отчёт

Покажи: созданные файлы по доменам; вывод всех трёх команд верификации;
ДОПУЩЕНИЯ и ОТКРЫТЫЕ ВОПРОСЫ явными строками («допущений нет» — тоже
явной строкой); что осталось непокрытым и почему.

Коды ответов, взятые из спеки, но не проверенные на живом стенде, —
всегда допущение: спека часто объявляет только 200 там, где API отдаёт
204. Так и пиши.

Найденная ловушка ПРОЕКТА → короткой строкой в «Копилку ловушек проекта»
в `docs/api-layer.md` или в паспорт, и упомяни в отчёте.

## Границы и безопасность

- Тесты, фикстуры, conftest — НЕ пишутся этим скиллом ни при каких
  условиях (это `api-tests` / `api-suite`).
- Не изменяй `example_*` файлы и `docs/*.md` (исключение — «Копилка
  ловушек проекта»).
- Не трогай домены и сервисы вне запрошенного скоупа.
- Хардкод URL и секретов запрещён — только `config.py` / `.env`.
- Не коммить без явной просьбы.
