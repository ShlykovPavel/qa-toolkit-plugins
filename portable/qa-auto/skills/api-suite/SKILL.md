# Полное покрытие API (api-suite)

Вход — OpenAPI-спека проекта (путь/URL из паспорта или из запроса). Выход —
тестовый слой по ВСЕМ ресурсам спеки: клиенты, фикстуры, regression + smoke
на каждый домен, зелёная верификация, сводный отчёт. Оркестрация ролей:
writer'ы пишут параллельно, fixer верифицирует последовательно, reviewer'ы
адверсарно ревьюят; роли — агенты плагина `qa-auto:test-writer`,
`qa-auto:test-fixer`, `qa-auto:test-reviewer` (роли исполняют скилл api-tests, не
дублируют его).

**Механика делегирования:** каждую роль запускай агентом её типа
(read the corresponding role SKILL.md and pass its procedure to spawn_agent), промпт: «Рабочая директория: <корень
проекта>. Вход: ...». Оркестратор читает только финальный ОТЧЁТ агента, не транскрипт.
**Fallback (обязателен):** если Agent tool недоступен — выполни роли САМ,
последовательно, по процедурам ролей из `${PLUGIN_ROOT}/agents/<роль>.md` и с теми же входами.

## Шаг 0 — Pre-flight (первым действием)

| Ситуация | Действие |
|---|---|
| Паспорта `docs/project-profile.md` нет | Одной фразой: «форк не настроен, запусти /setup-fork» — и СТОП. Файлы не трогать. |
| Запрос про ОДИН ресурс/эндпоинт | Одной фразой: «это задача /api-tests» — и выйти. |
| Запрос про фронтенд (Selenium) или мобилку (Appium/Flutter) | Одной фразой отослать к соответствующему слою, выйти. |
| Запрос про починку/рефакторинг существующих тестов | Одной фразой: вне скоупа — и выйти. |
| Иначе | Прочитай паспорт целиком (роли, конвенции, где спека) и работай дальше. |

**Оснащение машины — прогоном, а не памятью.** В этом же шаге:

```bash
preflight.py --use-marker
```

Молчит, пока на машине ничего не менялось (маркер `.preflight-ok` привязан к
хосту, не к клону — репозиторий ездит между машинами). Красное **не чинишь и
ничего не ставишь**: называешь пользователю, какой класс работы закрыт (колонка
«без неё» в выводе прогона), и продолжаешь в оставшемся
объёме — недостача идёт в отчёт. Для этого скилла критичны: `.venv` с pytest, файл спеки из паспорта, `.env` — оркестратор раздаёт работу writer-агентам, и недостача, найденная после fan-out, стоит всех порций сразу.

**Автономный режим** = пользователь недоступен или попросил без вопросов:
вместо любого «спроси/дождись» — фиксируй ДОПУЩЕНИЕ, все допущения — в
сводный отчёт Шага 6.

## Шаг 1 — Analyze: инвентаризация спеки и план fan-out

1. `python3 ${PLUGIN_ROOT}/bin/openapi_slice.py --spec <спека> --list-tags` — таблица
   ресурсов с числом операций (полную спеку в контекст НЕ читать).
2. Срез КАЖДОГО тега сохрани В ФАЙЛ: `python3 ${PLUGIN_ROOT}/bin/openapi_slice.py
   --spec <спека> --tag <Тег> --out _specs/<тег>.json`
   (директория срезов — `_specs/` в КОРНЕ рабочего репо, она в .gitignore;
   по умолчанию скрипт пишет в stdout, а контракт writer'а — именно ПУТЬ
   к файлу-срезу).
2а. **Срез базы знаний** на каждый тег — что вики проекта знает об этих
   эндпоинтах сверх сваггера (правила, кейсы, баги, оговорки стенда):
   `qa-kb-slice --spec-slice _specs/<тег>.json --out _specs/<тег>_kb.json`.
   В выводе — итоги и `empty` (эндпоинты, которых в вики нет). Код 2 «база
   знаний не найдена» — вики у проекта нет: срезов вики нет, дальше всё как
   раньше, в сводный отчёт одной строкой.
3. Составь JSON-план fan-out: по каждому ресурсу — имя, число операций,
   какие CRUD-операции есть/отсутствуют, порядок запуска.
4. Спец-случаи — реши прямо в плане:
   - **Auth-подобные теги** (login/refresh/token): сверь с паспортом и
     наличием `src/auth.py`. Если логин-клиент уже существует — CRUD-домен
     НЕ городить: либо «не покрывать» с причиной в плане, либо только
     негативы login/refresh (401) — выбор зафиксируй в плане.
   - **Ресурсы из 1 операции** — один тестовый класс, не четыре.

## Шаг 1.5 — Spec-writers: поведенческие тест-спеки доменов (до плана)

После срезов, ДО показа плана — на каждый ресурс запусти агента
`qa-auto:test-spec-writer`,
параллельно волнами не больше 3, как writers. Вход агенту: имя ресурса,
путь к файлу-среза, путь для файла спеки, путь к паспорту и — если есть —
путь к срезу базы знаний `_specs/<тег>_kb.json` (секция 7 спеки «Из базы
знаний»).

**Контракт путей:** срезы (Шаг 1) И спеки живут в `_specs/` в КОРНЕ
рабочего репо; имя спеки — `_specs/<ресурс>_spec.md`. Путь к спеке ты
обязан передать writer'у этого ресурса в Шаге 3 — без него writer спеку
не найдёт. Отчёт агента начинается со `СПЕКА НЕ ЗАПИСАНА: <путь>` — запиши
текст спеки из отчёта по этому пути сам, без правок (субагенту Claude Code не
даёт создать `.md` с «отчётным» началом имени — Report…, Summary… и т.п.).

Выход шага: спеки всех доменов + собранная тобой СВОДНАЯ таблица
открытых вопросов всех доменов (из отчётов спека-агентов) — она уходит
в Шаг 2. Из секций 7 спек выпиши строки `ожидаемо падает` (открытые баги
из вики) — они тоже уходят в Шаг 2. Риски из отчётов спека-агентов (например teardown при
отсутствии delete) — в реестр допущений для сводного отчёта Шага 6.

## Шаг 2 — Подтверждение плана + вопросы пачкой

Покажи план fan-out пользователю таблицей ВМЕСТЕ с единым списком
открытых вопросов всех доменов и дождись ответов и подтверждения ДО
написания кода. Формат списка:

- один нумерованный список по ВСЕМ доменам сразу (не по разу на домен);
- дубликаты схлопнуты: один вопрос «DELETE несуществующего: 404 или
  204?» на весь API с перечислением затронутых доменов;
- у КАЖДОГО вопроса — рекомендуемый дефолт и влияние
  («меняет N тестов домена X») — бери их из таблиц спек.

Единый список — обязательный артефакт стадии плана, НЕ только реплика
для показа: составь его и выведи ВМЕСТЕ с планом fan-out в ОБОИХ
режимах, ДО запуска writer'ов. В автономном режиме показывать некому,
но список всё равно фиксируется ЯВНО одним блоком в твоём выводе —
СНАЧАЛА список, ПОТОМ принятие дефолтов; вписывать дефолты по спекам
врозь, не собрав единый список, — нарушение процедуры.

**Открытые баги из вики** (строки `ожидаемо падает` секций 7) — отдельным
блоком после вопросов: по каждому баг, задача трекера, дата страницы и
выбор «тест с `xfail` и ссылкой на баг» / «тест не пишем». Нового
баг-репорта на них не заводят. `xfail` ставится только после «да»
человека: баг мог починиться, а вики — отстать.

Ответы пользователя ВПИШИ в спеки соответствующих доменов (секция
«Открытые вопросы»: ответ + пометка «отвечено пользователем»; по багам —
в статус строки секции 7: «ожидаемо падает — `xfail`, да человека» или
«ожидаемо падает — тест не пишем») до запуска writer'ов. В автономном
режиме баги — «тест не пишем», в реестр допущений. В автономном режиме — каждый дефолт становится допущением
ДОСЛОВНО: «принят дефолт X, проверить на живом стенде» — и в спеку
домена, и в твой реестр допущений для Шага 6.

## Шаг 3 — Writers (параллельно, не больше 3 одновременно)

Каждому writer'у — свой ресурс + ПУТЬ к файлу-среза + ПУТЬ к спеке домена
(`_specs/<ресурс>_spec.md` из Шага 1.5). Спека — источник правды ПОВЕРХ
среза: writer не гадает, а читает её; конфликт спеки со срезом — в отчёт
writer'а, не разрешать гаданием. В промпт каждого writer'а включи явную
строку: «сабагентов НЕ запускай, работай сам». Домены не пересекаются
по файлам, конфликтов нет. Больше 3 ресурсов — запускай волнами по 3,
следующая волна после отчётов предыдущей. Отчёты writer'ов (файлы, матрица,
допущения) собирай — они пойдут в сводный отчёт.

## Шаг 4 — Fixer (последовательно, один на весь проект)

После ВСЕХ writer'ов — один test-fixer на весь проект: `make verify` до
зелёного (лимит попыток — в файле роли).

**Маршрутизация по отчёту фиксера** (секция классификации
`тест | тип | действие`; правила — `docs/tests.md`, «Маршрутизация по
классификации»):

- «баг теста» — уже починен фиксером, действий не требует;
- «расхождение со спекой» — СПЕКА-ПЕТЛЯ: test-spec-writer домена
  обновляет спеку (вход: старая спека + отчёт фиксера), затем writer
  домена правит тесты по обновлённой спеке, затем точечный verify.
  Лимит — **2 возврата на домен**; счётчик возвратов по каждому домену
  веди и включи в сводный отчёт Шага 6 (0 — тоже значение); упёрся в
  лимит — стоп по домену, honest report, решает человек. В шаблоне без
  живого стенда петле не от чего сработать — счётчик 0 это норма;
- «баг стенда» — СТОП по домену: домен — отдельной секцией в сводный
  отчёт, дальше решает человек. Репорт — **вызови скилл `/bug-report`**
  сам, из основной сессии (сабагенту гейт с человеком не пройти), тест
  остаётся `xfail` со ссылкой на этот репорт (как в `docs/tests.md`).

**Правило конкуренции за стенд:** живые прогоны в форке — только
ПОСЛЕДОВАТЕЛЬНО (`pytest -x -q` по доменам по очереди, флаг
`LIVE_STAND=available` в промпте fixer'а — только если стенд реально
доступен и пользователь просил гонять); писать код можно параллельно,
уникальные генераторы данных обязательны — параллельные прогоны и
ночные запуски не должны конфликтовать по данным.

## Шаг 5 — Reviewers (параллельно по доменам)

На каждый домен — test-reviewer (вход: директории домена + путь к срезу).
Это РЕВЬЮ-ПЕТЛЯ того же маршрутизатора: тип находки «нарушение
конвенций» severity **high** → возврат к writer'у того же домена (или
правит сам оркестратор), затем повторный `make verify`. Лимит —
**1 круг доработки на домен**; счётчик кругов по каждому домену — в
сводный отчёт Шага 6 (0 — тоже значение). Что осталось после круга —
в сводный отчёт, не чинить бесконечно.

## Шаг 6 — Финал

1. Финальный `make verify` — зелёный.
2. Сводный отчёт — по ОБЯЗАТЕЛЬНОМУ скелету; отчёт без любой из секций
   невалиден, даже если секция пуста (пустоту фиксируй явной строкой,
   например «допущений нет»):
   - таблица домены × (созданные файлы, покрытие матрицы, находки ревью
     и их статус после доработки);
   - секция «Допущения и открытые вопросы»: сюда ПЕРЕНОСЯТСЯ (копией,
     не пересказом по памяти) допущения и риски из отчётов ВСЕХ агентов
     (spec-writers, writers, fixer, reviewers) плюс реестр Шага 2
     (принятые дефолты); каждый пункт — с доменом-источником;
   - строка «счётчики петель по доменам»: спека-возвраты и ревью-круги
     по каждому домену (0 — допустимое значение, тоже пишется);
   - строка «база знаний»: по доменам — проверок из вики в тестах,
     `xfail` по багам с «да» человека, строк без тестов (TO-BE, не
     автоматизируем, баг без «да»), расхождения вики со сваггером; вики
     нет — «база знаний: нет»;
   - что требует человека: неподтверждённые допущения, отложенные
     находки, непокрытые ресурсы с причинами;
   - напоминание — живой прогон возможен только в форке с заполненным
     `.env`.
4. Найденная в работе ловушка ПРОЕКТА (особенность стенда, флаки,
   расхождение доки/спеки с фактом) → допиши её коротко («сигнатура →
   как избегать») в секцию «Копилка ловушек проекта» в `docs/api-layer.md`
   или в паспорт проекта И упомяни это в отчёте.

## Границы и безопасность

- Не изменяй `example_*` файлы и `docs/*.md` (включая паспорт) — эталоны
  (исключения Шага 6: «Копилка ловушек проекта», уроки стенда в паспорт).
- Никаких значений секретов и хардкода URL — только `config.py`/`.env`.
- Не коммить без явной просьбы.
- Агентам передавай только пути и имена ресурсов — не пересказывай им
  конвенции своими словами (они читают доки сами).
