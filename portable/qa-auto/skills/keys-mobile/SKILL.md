# Локаторы в репозитории мобильного приложения (keys-mobile)


## Короткий порядок: то, что реально решает исход порции

Полная процедура — ниже, шагами. Но если читаешь только один блок, читай этот:
девять пунктов, каждый из которых на живых прогонах отделял «порция принята с
первого раза» от «ревьюер нашёл дефект вместо тебя».

2. **Область считается от реестра ключей, а не от имени параметра**, и греп
   идёт по `packages/` тоже. Плюс: однотипный метод рядом — не один метод,
   семейство ищется по шаблону имени.
3. **Форма правки измеряется ДО правки, виджет-тестом, таблицей по формам** —
   видимые узлы, `hasAction(...)` на самом идентифицированном узле, число
   узлов против контроля без идентификатора (Шаг 10.1). Замер
   опроверг два вывода «по типу виджета» и третий — «над кнопкой нужен
   merge». Предиктор: у виджета **своя граница семантики** (Material-кнопки,
   `IconButton`, FAB) → идентификатор **внутрь**, на содержимое слота
   `child`/`icon`; плоско снаружи — пустой узел, `MergeSemantics` снаружи —
   трёхслойный обход, сливающий всё поддерево. Своей границы нет (`InkWell`,
   `GestureDetector`, `ListTile`, голый `Checkbox`) → плоская обёртка
   снаружи; но в `AppBar.title` (держатель без `container`) такой элемент
   сливается с шапкой → `container: true` над ним, а не перенос глубже.
   Шаг 3, Случай D и «Корневой узел обёртки».
4. **Примитив — отдельная первая порция**, и сразу правильной формы:
   `semanticId` nullable, флаг `merge` (запасной, не форма по умолчанию),
   собственного `key` НЕ заводит, `label` НЕ передаётся, лежит в самом нижнем
   пакете (проверить направление зависимости в корневом `pubspec.yaml`).
5. **Гейт таблицы Шага 6.** На этом проекте тестировщик содержание правки в
   чужом репозитории не ревьюит и передаёт решение агенту — поэтому гейт
   работает как «назови, где расходишься с ревьюером и чем закроешь», а не как
   «согласуй список элементов».
6. **Гейты сразу после правки, до проверок и дампов:**
   ```bash
   git diff -w origin/<база> | grep '^+' | grep -cE "final root = |\? root\b|== null \? (root|child)\b"   # 0
   git status --short | grep -vE '\.dart$'                                     # пусто
   ```
   Первый ловит переиндентацию (её было ~60% дифа), второй — чужие файлы,
   которые дописывает их же тулинг (`ios/Podfile.lock` после сборки,
   `.gitignore`, `pubspec.yaml`). Полный набор перед показом — Шаг 11:
   стилевые запреты **по сырому** дифу, идентификатор мимо примитива, тест
   реестра ключей, фолбэк в идентификаторе, наши обозначения в дифе И в
   сообщениях коммитов.
7. **Дамп: навигацию ведёт человек, дамп снимает агент.** Не открылся маршрут
   с первой попытки — отдать навигацию тестировщику, а не перебирать тапы.
   Когда экран довёл человек, снимать `adb shell uiautomator dump` (без
   Appium: сессия с `appPackage` перезапустит приложение и сбьёт экран).
   Перед любым выводом «локаторов нет» — сверить, что в фокусе наше
   приложение: `adb shell dumpsys window | grep mCurrentFocus`.
8. **В отчёте по каждому месту различать «подтверждено дампом» и «вывод по
   форме».** Одинаковая форма с подтверждённым местом — это вывод, а не факт.
9. **Ревью MR — продолжение прогона.** Правки по замечаниям проходят те же
   гейты, раунд заканчивается отчётом Шага 11, вопрос
   ревьюеру — грепом по HEAD своей ветки до отправки, ответ публикуется один
   раз, описание MR переписывается под исход раунда (Шаг 11.1). Раунд,
   отработанный мимо скилла, не проходит ни гейтов, ни отчёта.

Три ловушки окружения, каждая уже съедала прогон: длинные команды в фон
**без пайпа** (пайп прячет падение и обрезает лог), обход чужого кода под
локальную сборку проверяется **скриншотом** до пересборки, и рецепты из
`docs/apps-repos.md` — тоже гипотезы: один из них был неверен и стоил
пересборки впустую.

Вход — экран приложения, элементы которого недоступны нативному Appium.
Выход — diff в чужом репозитории, где нужным виджетам добавлен
`Semantics(identifier:)`, прогнанный их тестами и проверенный дампом

видят**. Приложение может быть полностью «покрыто ключами» и при этом
непригодно для Appium.

Затем — состояние клона, **до любой правки**:

```bash
git -C <путь> fetch && git -C <путь> status --short --branch
```

| Состояние клона | Действие |
|---|---|
| Базовая ветка, чисто | Норма, работай дальше |
| **Наша** ветка из прошлой порции, а в diff только идентификаторы | Это продолжение миграции: скажи тестировщику и иди дальше от Шага 1, ветку заново не создавай (Шаг 7 пропускается) |
| Чужие незакоммиченные правки, или ветка не наша и не базовая | Покажи тестировщику и СТОП |

Миграция идёт порциями (Шаг 2), поэтому «не базовая ветка» — это НОРМАЛЬНОЕ
состояние между порциями, а не повод останавливаться.

Проверь отставание клона:
`git -C <путь> rev-list --count <базовая ветка>..origin/<базовая ветка>`.

**Оснащение машины — прогоном, а не памятью.** В этом же шаге:

```bash
preflight.py --use-marker
```

Молчит, пока на машине ничего не менялось (маркер `.preflight-ok` привязан к
хосту, не к клону — репозиторий ездит между машинами). Красное **не чинишь и
ничего не ставишь**: называешь пользователю, какой класс работы закрыт (колонка
«без неё» в выводе прогона), и продолжаешь в оставшемся
объёме — недостача идёт в отчёт. Для этого скилла критичны: клон приложения на месте (без него скилл невозможен — это стоп) и `fvm` для их проверок: без него `fvm flutter analyze` не запустить, и diff нельзя выдавать за готовый к MR.

**Автономный режим** = тестировщик недоступен или явно попросил без вопросов:
вместо «спроси» — ДОПУЩЕНИЕ в отчёт. **Исключение — гейт таблицы (Шаг 6): он
автономным режимом НЕ снимается.** Правка чужого репозитория без

## Шаг 1 — Свежий аудит

Не доверяй цифрам из документа — сними заново, репозиторий живой:

```bash
python3 ${PLUGIN_ROOT}/bin/mobile_keys_audit.py --repo <путь к приложению>
```

Скрипт отвечает на три вопроса: какие ключи объявлены и **не применены**
(локатора в приложении нет), в какой форме применены остальные
(`ValueKey` = невидим, `Semantics(identifier:)` = виден), какие ключи из их
документа для автотестов не имеют соответствия в реестре.

Расхождение с карточкой `.qa/keys-mobile/docs/card.md` → обнови карточку, это её смысл.

Скрипт по умолчанию возвращает 0: ненулевой код бывает только с `--strict`.
Классификация формы применения — эвристика по окну строк, скрипт сам печатает,
сколько вердиктов получено не с самой строки. Числа реестра и списка мёртвых
ключей — точные.

**Три системных завышения счётчика, которые он не видит:**

1. Обёртка объявляет параметр ключа и **не использует его в `build`** —
   ключ числится применённым, а в дерево не попадает никогда. Проверяется
   грепом: упоминания параметра только в конструкторе и в поле.
2. Ключ навешен формой, невидимой платформе (`ValueKey`) — это и есть
   предмет миграции.
3. **После миграции счётчик не растёт**: `identifier` оказывается в обёртке,
   а `<Реестр>.X` остаётся в месте вызова, и классификация по окну строк этого
   не связывает. **Метрика прогресса — число мигрированных узлов,
   подтверждённых дампом, а не вывод скрипта.** Не отчитывайся его цифрами.

## Шаг 2 — Режим работы

| Что просят | Режим |
|---|---|
| «Appium не видит элементы», «перевести ключи на семантику» | **Миграция**: ключ уже есть, добавляем `identifier` рядом с существующим `ValueKey` |
| «нет ключа на элементе X», новый экран | **Добавление**: новый ключ в реестр + применение через примитив |
| «ключ есть в документе, но не работает» | Сначала аудит Шага 1 покажет, что именно: мёртвый ключ, невидимая форма или ключа нет вовсе. Режим — по результату |

**Миграция идёт порциями по экранам или по виджетам-обёрткам, а не всем
репозиторием за раз.** Диф на сотню файлов их команда не примет, и откатывать
его нечем.

## Шаг 3 — Форма правки

Нужная форма — `Semantics(identifier: <String>)` на узле виджета.
`identifier` требует именно `String`, а ключ прокидывается в виджеты как
`Key?`, `ValueKey<String>` или `ValueKey<String>?` — строкой не является
почти нигде, сама строка живёт в месте вызова.

**Правка АДДИТИВНА.** Обёртка получает новый `final String? semanticId`
РЯДОМ со старым параметром, а не вместо него. Менять тип старого параметра на
`String` нельзя: общие обёртки вызываются из сотен мест, смена типа ломает
компиляцию всех разом — порции по экранам становятся невозможны, получается
один diff на весь репозиторий.

Следствие: **`ValueKey` не снимается** — он остаётся на своём виджете, и их
`find.byKey` продолжает его находить, поэтому ассерты их виджет-тестов правки
не требуют. Условие: примитив не дублирует этот ключ на себе (см. ниже).

### Случай A — примитив (всегда первая порция)

```dart
class SemanticId extends StatelessWidget {
  const SemanticId({
    required this.child,
    this.semanticId,          // nullable — см. ниже, это НЕ мелочь
    this.merge = false,       // см. Случай D
    super.key,
  });

  final String? semanticId;
  final bool merge;
  final Widget child;

  @override
  Widget build(BuildContext context) {
    final id = semanticId;
    if (id == null) return child;
    final node = Semantics(identifier: id, child: child);
    return merge ? MergeSemantics(child: node) : node;
  }
}
```

**`semanticId` обязан быть nullable, и это решение об объёме дифа, а не о
стиле.** С `required` каждое место вызова вынуждено само разбираться с null
и писать `final id = …` + тернарник + вынос `final root = …` — а вынос root
переиндентирует всё поддерево виджета. На реальном прогоне это дало
+3131/−2049 там, где содержательных правок было +1295/−213: **~60% дифа —
переиндентация**, и в ней потерялся функциональный дефект (Случай D).
Nullable переносит проверку внутрь примитива, место вызова становится одной
безусловной обёрткой, поддерево не сдвигается.

**Флаг `merge` закладывается сразу, но это запасной вариант, а не форма по
умолчанию.** Он нужен в редком случае «у виджета своя граница семантики и нет
слота для идентификатора» (Случай D): без флага вызывающая сторона вынуждена
дублировать `MergeSemantics(Semantics(...))` инлайном — получится копипаста
примитива в N файлах. Где слот есть, идентификатор ставится внутрь, и merge не
нужен: `MergeSemantics` поверх кнопки ревьюер продукта назвал кривым, и замер
показал почему.

**Про `label`: параметра в примитиве НЕ заводить.** Прежняя редакция говорила
«держим, но не передаём» — на ревью это вскрылось как мёртвый код: 0 из 102
мест вызова его передавали, а doc-комментарий сам себе противоречил («задавай
вместе с merge» / «задашь — будет задвоение»). Параметр заводится вместе с
первым местом применения, а не на будущее. Почему передавать его нельзя — ниже,
и это остаётся в силе. Проверено
дампом до/после на одной сборке: `merge` сам берёт метку из слитого
поддерева, и она корректна (`label="I don't have a middle name"`), а явный
`label` конкатенируется с ней — узел отдаёт `«Sign in\nSign in»`, VoiceOver
произносит текст дважды. Для Appium это неважно (ищем по
`identifier`/`name`), для доступности продукта — реальный регресс, который
легко внести и потом не заметить.

Раньше здесь было написано обратное («без явного `label` метка теряется»).
Это была **ошибка измерения в виджет-тесте**: у слитого узла метку надо
читать из `getSemanticsData().label`, а `SemanticsNode.label` отдаёт пустую
строку. На устройстве метка на месте.

Исключение — узел, у которого метки нет вообще (иконка без текста и без
tooltip): `label=""` там и до правки, и после, это не наш регресс.

Имя класса здесь условное: как примитив называется в этом приложении и в
каком пакете лежит — `[карточка, п. 2]`.

**Свой `key` примитив НЕ заводит и чужой НЕ дублирует.** Ключ уже стоит на
дочернем виджете (его мы не трогаем); если продублировать его на обёртке,
`find.byKey` найдёт два виджета и `findsOneWidget` в их тестах упадёт.
Обратное не запрещено: если ключ исходно стоял на самой обёртке
(`Semantics(key:, identifier:)`), он **переезжает на примитив** как `key:` —
виджет с ключом остаётся в дереве и при `semanticId == null`, `find.byKey`
ведёт себя как прежде. Голый `Semantics(identifier:)` на его месте — обход
примитива, ревьюер его вернёт (гейт — Шаг 11). Проверять форму примитива
**виджет-тестом на конкретный мигрированный виджет**
(`containsSemantics(identifier: …)` + `find.byKey(...) findsOneWidget`), а не
прогоном всего съюта: съют зелёный ровно до той порции, где найдётся тест с
`find.byKey` на мигрированный виджет.

Проверь грепом по `identifier:`, есть ли примитив в репозитории уже. **Готовый
примитив не считается годным образцом, пока не увидишь тест на него**: в этом
проекте найденный в репозитории примитив выставлял и `key`, и `identifier`,
нигде не использовался и ни одним тестом не проверялся — форма была неверной.
Вынос примитива в общий каталог — **отдельная первая порция** и отдельная
строка отчёта.

### Случай B — ключ уже стоит прямо на виджете через `key:`

Существующий `key:` **не удалять и не менять** — он участвует в реконсиляции
списков. Куда ставить идентификатор, решает то, есть ли у виджета своя
граница семантики (Случай D):

```dart
// своей границы нет (InkWell, GestureDetector, ListTile, голый Checkbox) — снаружи
SemanticId(
  semanticId: AppKeys.x,
  child: InkWell(key: ValueKey(AppKeys.x), onTap: …, child: …),
)

// своя граница есть (TextButton, IconButton, FAB) — ВНУТРЬ, на содержимое слота
TextButton(
  key: ValueKey(AppKeys.x),
  onPressed: …,
  child: SemanticId(semanticId: AppKeys.x, child: Text(…)),
)
```

`Semantics` — прокси-виджет, на layout не влияет; внутрь `Expanded`/`Row` и
в слот `child`/`icon` оборачивать безопасно.

### Случай C — ключ прокидывается в обёртку параметром

В объявлении — аддитивно, в месте вызова — по обстоятельствам:

```dart
// объявление обёртки
final String? semanticId;
...
return SemanticId(
  semanticId: semanticId,            // null обрабатывает примитив, не мы
  child: <существующий корневой узел как есть, БЕЗ выноса в переменную>,
);
```

**Корень обёртки — виджет со своей границей семантики** (обёртка возвращает
`ElevatedButton`, `IconButton` или контейнер прямо над ними) → примитив
ставится не на корень, а в слот этой кнопки:
`child: SemanticId(semanticId: semanticId, child: <содержимое слота как есть>)`.
Правка остаётся однострочной обёрткой, поддерево кнопки не сдвигается
(Случай D).

**Ни `final root = …`, ни тернарника между обёрнутым и необёрнутым
поддеревом** — всё это следствие `required semanticId` в примитиве (Случай
A). Если тянет написать `final root = …`, чтобы подставить его в две ветки
тернарника, — форма примитива неверна, возвращайся в Случай A и делай
параметр nullable. Вынос root — главный источник переиндентации: на реальном
прогоне одна содержательная правка в файле дала +141/−141.

Не путать с тернарником, который вычисляет **значение** `String?`:
`semanticId: id == null ? null : AppKeys.x(id)` поддерево не трогает и
допустим. Блочное тело вместо `=>` ради подъёма одной
nullable-переменной — тоже допустимо, если иначе не обойтись, но цена (строки
сдвига одного поддерева) называется в отчёте.

**Старый параметр `required`?** Тогда в месте вызова его убрать нельзя —
`missing_required_param` обычно поднят до `error`, а делать параметр
опциональным = правка их публичного API, не идентификатор. В этом случае
старый аргумент **остаётся**, `semanticId` добавляется рядом; значение
временно дублируется, это нормальное состояние миграции.

Если старый параметр опциональный — в месте вызова он заменяется:
`keyForTest: ValueKey(AppKeys.x)` → `semanticId: AppKeys.x`.

### Случай D — у виджета уже есть своя семантика: идентификатор ВНУТРЬ, а не поверх

**Плоская обёртка не всегда даёт ГОДНЫЙ узел.** Формулировка «identifier не
долетает» неверна — на Flutter 3.35 узел с идентификатором есть почти всегда.
Негодным его делает другое: **на нём не оказывается того действия или
состояния, которое понадобится тесту**, а иногда и границ элемента.

Решает не «тип виджета», а **открывает ли дочерний виджет собственную границу
семантики**. Material-кнопки (`ElevatedButton`, `TextButton`, `IconButton`,
`FloatingActionButton`) её открывают: их узел — отдельный контейнер, аннотация
СНАРУЖИ в него не проникает и становится лишним пустым узлом рядом.
`InkWell`, `GestureDetector`, `ListTile`, голый `Checkbox` границы не
открывают — плоская обёртка снаружи сливается с их узлом. Обратная сторона:
если выше стоит держатель без `container` (`AppBar.title`), их узел
вместе с идентификатором сливается уже в держатель, и над элементом нужна
своя граница — `container: true` («Корневой узел обёртки», п. 3). Два
случая `container` не путать: над `InkWell` он становится границей, которой
нет; над Material-кнопкой граница уже своя, и `container` даёт пустой слой
(строка кнопок в таблице ниже). Аннотация ВНУТРИ
границы (на содержимом слота `child`/`icon`) сливается с узлом кнопки — это
и есть форма по умолчанию.

**Критерий, проверяемый ДО правки и без устройства** (виджет-тест, Шаг 10.1): обернуть форму, найти ВИДИМЫЙ узел по `identifier`, посмотреть
`hasAction(tap)`, трейт кнопки, нужные флаги и число видимых узлов против
контроля без идентификатора. Замер (Flutter 3.35.7, отдельный пробный
проект без кода продукта):

| Что оборачиваем | плоско снаружи | `MergeSemantics` снаружи | **внутрь** (на слот) |
|---|---|---|---|
| `ElevatedButton`, `TextButton`, `IconButton` (с tooltip и без), FAB | узел пуст: `tap=false`, без трейта кнопки, **+1 узел** против контроля; `container: true` не помогает | `tap=true`, кнопка, метка, узлов как в контроле | **`tap=true`, кнопка, метка, узлов как в контроле** — то же, одним виджетом |
| то же с `onPressed: null` | — | `enabled=false`, трейт кнопки на месте | `enabled=false`, трейт кнопки на месте |
| то же в `Positioned`/`Stack` | в виджет-тесте 48×48, **на устройстве — весь экран** | на устройстве `48x48` (дамп) | в виджет-тесте 48×48; **на устройстве не снималось** |
| `InkWell`, `GestureDetector`, `ListTile` | `tap=true` — годен (без держателя выше) | не нужен | годен |
| `InkWell` внутри `AppBar.title` — держатель `Semantics(header: true)` | идентификатор на держателе: узел шириной с title, чужая метка, центр промахивается; **с `container: true` — годен**: границы элемента, свой `tap` | годен, то же, что `container`, но сливает всё поддерево | без границы — идентификатор на держателе; с `container: true` — границы элемента, **`tap` у держателя** |
| Голый `Checkbox`; `Row[Checkbox, Text]` внутри одной обёртки | `tap=true`, `checked=true` — годен | не нужен | — |
| `GestureDetector[Checkbox, Text]` | `tap=true`, но `checked=false` | **не помогает**, состояние остаётся на потомке | — |
| Слот под `ExcludeSemantics` | — | — | **идентификатора нет вовсе** — внутрь нельзя |
| **Наш же мигрированный виджет, который САМ ставит примитив** (общая кнопка, контейнер) | узел пуст: идентификатор снаружи, действие и состояние — на внутреннем узле | **merge не лечит причину** | идентификатор передаётся ПАРАМЕТРОМ `semanticId` в саму обёртку, внешняя обёртка снимается |

**Почему merge поверх — не форма по умолчанию, хотя на одиночной кнопке он
работает.** Это трёхслойный обход (`MergeSemantics` → `Semantics` → своя
семантика кнопки), и ревьюер продукта назвал его кривым по делу:
`MergeSemantics` сливает **всё** поддерево, а не только кнопку. Замер:

- две кнопки под одним merge становятся одной — `label="A\nB"`, один `tap`,
  вторая кнопка платформе не видна (без merge их две);
- вложенный идентификатор исчезает: `Checkbox` со своим `identifier` под
  merge соседа — `inner=0`; merge внутри merge — выживает только внешний.

Merge остаётся **запасным вариантом** при трёх условиях сразу: у виджета своя
граница и нет слота, куда поставить идентификатор; под merge ровно один
интерактивный элемент; под merge нет чужих идентификаторов. Место с merge идёт
в список «проверить дампом» первым.

**Последняя строка таблицы — не про тип дочернего виджета, а про то, кто
ставит примитив.** Одна и та же общая кнопка их приложения замеряется годным сам
по себе (`tap=true isButton=true label="probe"`) и негодным под внешней
плоской обёрткой (`tap=false isButton=false label=""`). Смотреть надо, не
стоит ли примитив уже внутри. Класс дефекта ищется механически — гейт
«двойная обёртка» в Шаге 11; на реальном прогоне так нашлось 9 мест, из
которых пробником всплыло одно.

**Границы во весь экран под `Positioned`/`Stack`** виджет-тестом не
воспроизводятся: там плоская форма даёт те же 48×48, что и остальные.
Подтверждено дампом пока одно лечение — merge (`393x852` → `48x48`).
Форма «внутрь» кладёт идентификатор на узел самой кнопки и по механике должна
брать её геометрию, но **до дампа это вывод, а не факт**: при первом
применении под `Positioned` дамп обязателен. Для узлов в `Overlay`
вопрос открыт для обеих форм.

**Дешёвый признак «идентификатор поверх кнопки» прямо в дампе:** плоская
обёртка над Material-кнопкой отдаёт узел **без трейта кнопки**
(`XCUIElementTypeOther` вместо `Button` на iOS, `View clickable=false` на
Android). Если на одном экране рядом есть оба варианта — видно сразу.

**Ошибка, которая стоила двух раундов ревью.** Первый виток: плоской
обёрткой закрыли 12 мест над `IconButton`/`TextButton`/`InkWell`, а в 5 других
файлов внесли `MergeSemantics` с диагнозом «без merge не долетает» — диф стал
внутренне противоречивым. Второй виток: противоречие закрыли, расставив merge
поверх всех Material-кнопок, — и получили форму, которую ревьюер назвал
кривой. Оба раза форму выбирали по тому, что «работает на одиночном
элементе», без сравнения с формой «внутрь» и без составных случаев. Такое
сравнение **обязано быть в таблице замера до показа дифа**, а не оставлено
ревьюеру.

**Форма сверяется с контрактом примитива в ИХ репозитории — до первой правки
порции.** У влитого примитива есть доккомментарий и уже принятые места вызова;
для их ревьюера это контракт. Форма по умолчанию в этом скилле со временем
меняется (так «merge снаружи» сменилось на «внутрь, в слот»), а их
доккомментарий остаётся прежним — и порция, поставленная по новой форме, даёт
в кодовой базе две идиомы для одной задачи, иногда в соседних строках. Обе
рабочие: ревью блокирует именно расхождение с написанным. Перед правкой
прочитай доккомментарий примитива и два-три влитых места того же случая.
Расходятся с таблицей выше — доккомментарий переписывается в том же MR, а
решение называется в описании MR, одно на всю серию MR. Прецедент: блокер
ревью на одной порции и то же замечание на следующей.

### Правка локатора, которая меняет ПОВЕДЕНИЕ продукта

Стилевые правила их репозитория иногда нельзя выполнить, не тронув поведение.
Типовой случай — запрет `!`: место вызова строит локатор из nullable-поля
(`AppKeys.sectionUnitById(section.id!)`), и снятие bang заставляет решить, что
делать при `null`. Три правила:

1. **Фолбэк не должен схлопывать разные элементы в один идентификатор.**
   `?? 0` убирает bang и тут же заводит новый дефект: все секции без `id`
   получают `section_unit_0`, и тест находит не тот элемент — один дефект
   меняется на другой. Фолбэк выбирается по тому, что было ДО правки:
   - **падения не было** (значение шло через `?? 0` или иначе) → **нет `id` —
     нет идентификатора**: `semanticId: null`, примитив возвращает потомка,
     UI не меняется. Неуникальный локатор хуже отсутствующего: Appium молча
     нажмёт первый попавшийся, а отсутствие узла падает сразу и видно в
     отчёте. Прятать элемент ради локатора нельзя — пользователь теряет
     вариант ответа или пункт списка;
   - **было падение на `!`** → любой фолбэк меняет поведение; «не рисовать»
     (`SizedBox.shrink()`) допустим как замена падению, но это решение
     ревьюера (п. 3), а не локатора.

   `ValueKey` в том же месте сохраняет прежний фолбэк: это слой виджет-дерева,
   значение живого ключа не наше, и его часто фиксирует их тест реестра.
2. **Проверка поднимается ОДИН раз на оба локатора.** `semanticId` и
   `ValueKey` в одном месте вызова берутся из одной локальной переменной,
   иначе расходятся молча (гейт Шага 11). Pre-existing bang в соседней строке
   того же места вызова уходит вместе с нашим — это не расширение объёма, а
   следствие этого правила.
3. **Изменение поведения называется вслух** — отдельной строкой в отчёте и в
   MR, с явной передачей решения их ревьюеру: «секция с `id == null` теперь
   отрисуется пустотой вместо падения на bang; если нужен другой фолбэк —
   скажите». Молча выбранный фолбэк — это правка продукта под видом правки
   локатора, и заметит её не ревьюер, а прод.

### Подпакеты монорепо: примитив живёт в САМОМ НИЖНЕМ пакете

Сначала — **направление зависимости**, и только потом решение о форме правки:

```bash
grep -n "dependencies" -A20 <путь>/pubspec.yaml            # зависит ли lib от пакета
grep -rn "package:<основной модуль>" <путь>/packages/<пакет>/lib | head
```

- **Основной модуль зависит от пакета** (`lib → packages/x`, обычный случай
  дизайн-системы) → примитив выносится **в пакет**, обе стороны его
  импортируют, дублирования нет. Зависимость односторонняя, цикла здесь нет —
  не путать с обратным направлением.
- **Пакеты действительно независимы** → внутри пакета пишется прямой
  `Semantics(identifier: id, child: …)` — **без `key`**, как и примитив.

Тот же критерий — для **констант реестра**: константа живёт там, где виджет
её читает. Иначе получается пара «мёртвая константа в реестре основного
модуля + тот же литерал хардкодом в пакете», два источника истины, которые
расходятся молча — компилятор про такое не скажет.

Не узнать об этом заранее = упереться в неразрешимый импорт посреди порции.
Какие пакеты в этом приложении и какая в них форма правки — `[карточка,
п. 3]`.

### Корневой узел обёртки — не всегда тот, что кажется

`Semantics` навешивается на корень `build` обёртки, но корень часто оказывается
контейнером, а реальный кликабельный узел живёт глубже — это прямой источник
негодных локаторов (Шаг 4, правило 2). Процедура на сегодня:

1. оборачиваем корень, как описано выше;
2. **место обязательно попадает в список «проверить дампом первым»** — он
   ведётся в колонке «Годность» таблицы Шага 6, а проверяется ступенями
   Шага 10 (действие на самом узле — 10.1, дамп — 10.2–10.3, тап — 10.4);
3. дамп подтвердил, что узел шире тап-зоны или под центром чужой элемент →
   лечение **отдельной правкой**, а не подгонкой формулировки, и сначала
   диагноз: **слит ли узел с держателем** — метка узла содержит подписи
   соседей, границы во всю полосу, и тот же слитый узел даёт виджет-тест
   контроля без идентификатора. Для слитого узла:
   - **перенос идентификатора глубже НЕ лечит**: без границы
     семантики идентификатор остаётся на держателе (узел той же ширины, click
     `0 -> 0`); с `container: true` НИЖЕ носителя действия
     (`InkWell > Semantics(id, container: true)`) узел получает границы
     элемента, но `tap` остаётся у держателя — пустой узел;
   - лечит **граница семантики в точке идентификатора, над носителем
     действия**. Элемент БЕЗ своей границы (`InkWell`) →
     `Semantics(identifier:, container: true)` поверх него: отдельный узел с
     границами элемента, своим `tap` и меткой, держатель теряет чужие `tap` и
     метку. `MergeSemantics` поверх даёт то же по всем метрикам, но
     сливает всё поддерево — риски Случая D. Элемент со СВОЕЙ границей
     (Material-кнопка) → `container` бесполезен (таблица Случая D), форма
     «внутрь»;
   - у примитива параметра `container` может не быть (Случай A заводит только
     `semanticId` и `merge`): добавить его — правка API примитива, выносится
     тестировщику в гейт Шага 6, а не делается молча;
   - **годность — виджет-тестом первым**: `hasAction(tap)` на САМОМ узле с
     идентификатором и `performAction(tap)` до `onTap`, а не только `rect`.
     Дамп пустой по действию узел не ловит: на iOS `container` под `InkWell` и
     над ним дают одинаковый `StaticText 40x40`, и click по координатам
     проходит в обоих. Дамп — вторым, для последней мили;
   - границы во весь экран под `Positioned`/`Stack`/`Overlay` — другой класс
     (Случай D), не этот пункт.

Предсказать негодный корень по коду обёртки в общем случае не удаётся —
считай шаг гипотезой и не выдавай «обернул корень» за «локатор годен».
**Один класс предсказуем по коду: интерактивный элемент без своей
границы семантики внутри `AppBar.title`.** `AppBar` сам оборачивает `title` в
`Semantics(header: true)` без `container` (Flutter 3.35.7,
`material/app_bar.dart`, при `excludeHeaderSemantics: false` — значение по
умолчанию), и всё содержимое `title` без собственной границы — подписи,
действие `InkWell`, плоский идентификатор — сливается в один узел шириной с
title. Такое место идёт в список «проверить дампом первым» по этому признаку,
ещё до дампа, и форма для него сразу берётся из п. 3. Проверено только для
`AppBar.title`, на пробнике со структурой шапки, не на сборке продукта;
`flexibleSpace` без `title` (SDK ставит там тот же `Semantics(header: true)`),
`SliverAppBar`/`FlexibleSpaceBar`, `ListTile`, Android-устройство не мерялись —
по аналогии не переносить, мерить.

## Шаг 4 — Правила размещения идентификатора

Общие для любого мобильного стека. Нарушение любого из них даёт локатор,
который виден в дампе и бесполезен в тесте.

**1. Наличие идентификатора в коде не доказывает ничего.** Пять независимых
способов получить «ключ есть, локатора нет»: невидимая платформе форма
(`ValueKey`); объявленный и не использованный в `build` параметр; поддерево под
`ExcludeSemantics` **внутри виджета фреймворка** (`AnimatedCrossFade` и
подобные — греп по коду продукта их не найдёт); **сторонний пакет, который сам
вырезает семантику своего содержимого** (`table_calendar` 3.2.0:
`CellContent.build()` безусловно возвращает `Semantics(excludeSemantics: true)`
поверх результата ЛЮБОГО из девяти `CalendarBuilders`-билдеров, то есть поверх
идентификатора, поставленного билдером продукта); дамп, снятый до
включения семантики. Ни один не виден ни грепом, ни счётчиком аудита.

Сторонний пакет греп по коду продукта не найдёт **тем более**: виджет лежит в
`~/.pub-cache`, а не в `lib/`. Читается исходник пакета (версия — из
`pubspec.lock`, не из ограничения в `pubspec.yaml`), проверяется виджет-тестом
на ГОЛОМ пакете, без кода продукта, — см. Шаг 5, «Экран на стороннем пакете».

**2. Предиктор пригодности — совпадение границ узла с тап-зоной, а НЕ флаг
`clickable`.** Проверено в обе стороны: узел `clickable="false"` размером с
иконку кликается нормально; узел `clickable="true"` шириной во весь экран при
элементе в 120 px промахивается — Appium жмёт центр границ. Практический
критерий: сравнивать размер границ узла с размером элемента на скриншоте,
расхождение в разы — красный флаг, подтверждать тапом, а не рассуждением.

Три операции различаются, и «найти» не влечёт остальных:

| Операция | Условие |
|---|---|
| найти по `resource-id` / `name` | узел есть в дереве — работает всегда |
| нажать | центр границ попадает в реальную тап-зону |
| прочитать состояние (`checked`, `text`) | атрибут лежит на этом же узле, а не на потомке без идентификатора |

Худший случай — идентификатор на корне диалога размером во весь экран, а
настоящие кнопки («Да», «Нет», крестик) без локаторов: найти «диалог» можно,
сделать в нём нельзя ничего.

**3. Идентификатор — не стабильная ссылка на узел.** Класс, кликабельность и
границы узла под одним `resource-id` меняются по ходу взаимодействия и не
обязаны возвращаться назад (поле дропдауна: `EditText clickable=true` →
`View clickable=false` → так и остаётся после закрытия). Практически:
перезапрашивать локатор после каждого действия, не кешировать элемент между
шагами; в отчёте это идёт как требование к будущему тесту.

**4. Идентификатор называет то, на чём он стоит.** Когда `semanticId` ложится
на корень обёртки, а старый ключ указывал на кнопку внутри, имя начинает врать
(`exit_dialog_button` на корне welcome-экрана). Живые ключи переименовывать
нельзя → остаётся поставить идентификатор на сам названный элемент, а
расхождение зафиксировать находкой. Перенос сам по себе не делает узел
отдельным: элемент без своей границы семантики сливается с ближайшим
держателем, и идентификатор уезжает туда же. Ставить — над носителем
действия с границей (`container: true` над `InkWell`) или внутрь слота
Material-кнопки (Случай D), но не ниже носителя действия; проверять `tap` на
самом узле виджет-тестом, затем дампом (Шаг 3, «Корневой узел обёртки», п. 3).

**5. Композитный контрол требует нескольких идентификаторов, и они не
выводятся по вложенности.** Дропдауну нужны минимум четыре: контейнер, поле
ввода, каждая опция, кнопка подтверждения. База имени приходит от места
вызова, дети выводятся из неё (`<base>`, `<base>_input`, `<base>_option_<id>`,
`<base>_submit`). Опции раскрытого списка рендерятся через `OverlayPortal` /
`MenuAnchor`, то есть **вне поддерева поля** — идентификатор опции обязан
ставиться внутри виджета опции; «обернуть контейнер и искать опции внутри» не
сработает никогда. Проверено на устройстве: опции — отдельные кликабельные
узлы с подписью и пустым `resource-id`, лежат в поддереве оверлея.

**6. Значение не кодирует состояние и не зависит от позиции.** Состояние в
значении (`..._$isChecked`) означает, что после тапа элемент ищется под другим
id — локатор физически исчезает, а не меняет свойства. Индекс позиции съезжает
при удалении из середины списка. Nullable id с бэка (`?? 0`) схлопывает все
элементы в один идентификатор — при `null` идентификатор не ставится вовсе
(Шаг 3). Одно значение на десятки узлов требует от теста
скоупиться по экрану или диалогу. Значения живых ключей мы не меняем — это
правка их реестра; правило формулируется для `docs/locator-conventions.md` и
для разговора с их командой.

**Отдельный класс: виджет монтируется на КАЖДУЮ строку списка, а в
идентификатор подставляет константу.** Параметр для скоупа у него есть
(`formIndex`, `dropDownId`, `index`), но место вызова передаёт литерал «для
простоты» или значение по умолчанию — и все видимые строки получают ОДИН
идентификатор. Проверять при каждом включении виджета в порцию: место вызова
внутри `itemBuilder`/строки списка → параметр обязан приходить от данных
строки (id сущности), а не из дефолта. Дефект не видят ни `analyze`, ни диф,
ни дамп экрана, на котором строка одна (у нас список был отфильтрован поиском
до единственного результата, и дамп «подтвердил» ключ) — виден он только на
двух строках сразу. Ловит его код-ревью дифа, а не проверка формы.

**7. Ветвление по платформе, форм-фактору и состоянию удваивает требования.**
iOS-ветка диалога может не иметь ключей вовсе (`CupertinoAlertDialog`);
телефон и планшет используют разные виджеты (grid-тайл против list-тайла), и
дамп, снятый на одном форм-факторе, не доказывает ничего про другой; ветки
загрузки (`Skeletonizer`) либо без идентификаторов, либо с дублями. Проставляя
ключ, проверяй **все** ветки.

**8. Набор идентификаторов экрана зависит от роли и конфигурации с бэка.**
Один и тот же экран под гостем и под менеджером отдаёт разные наборы. Тест не
может опираться на фиксированный набор, а «локатор пропал» при проверке может
означать смену роли, а не регресс. Фиксируй в отчёте, под какой ролью снят
дамп.

**9. `visible="false"` при `accessible="true"` — узел найдётся, а действие не
сработает, и это МОЛЧА.** Дамп выглядит здоровым: идентификатор на месте,
границы по элементу, `accessible="true"`; `element.click()` возвращается без
исключения и без таймаута — и ничего не происходит. Отличить от рабочего узла
можно только эффектом (следующий экран, состояние на бэке), не отсутствием
ошибки. Признак локальный, а не «семантика не прогрелась»: соседние элементы
того же экрана в том же дампе — `visible="true"`.

Известная причина на Flutter 3.35.7 — содержимое `OverlayPortal`: на
устройстве его узлы приходят невидимыми. Механизм (ветка
`_SemanticsGeometry.computeChildGeometry`, `rendering/object.dart`) — гипотеза
по чтению SDK, не замер: виджет-тест дефект не воспроизводит, подтверждают его
только дамп и тап на устройстве. Лечится в продукте переводом оверлея на
`Overlay.of(context).insert(OverlayEntry(...))` — проверено на устройстве:
после правки все элементы оверлея стали `visible="true"`, а тап начал доходить
до приложения.

**Это правка поведения общего виджета, а не локатор, — у неё своя цена и свой
MR:**

- **Жизненный цикл, который `OverlayPortal` давал даром, теперь пишется
  руками.** Чек-лист до показа дифа: запись перестраивается при ребилде
  родителя, смене размеров экрана и `notifyListeners` контроллера (только
  после кадра — `markNeedsBuild` чужого элемента из фазы билда падает); не
  рисуется, пока поверх открыт другой роут (`Navigator` при пуше поднимает
  записи вне роутов наверх, `insert(below:/above:)` порядок не держит —
  проверка по `ModalRoute.isCurrent`); провайдеры места вызова внутрь
  содержимого оверлея не доходят — каждое место вызова несёт их с собой. На
  каждый пункт — виджет-тест, красный до правки. Первая версия лечения держала
  только провайдеры — остальное нашёл ревьюер.
- **Отдельная ветка и отдельный MR** с планом ручного регресса по всем местам
  виджета; в ветку MR идентификаторов не коммитится. Прецедент: лечение ушло
  коммитом в MR «только идентификаторы» — ревьюер снял аппрув со всего MR,
  раунд ушёл на откат и перенос (Шаг 11.1, п. 10).
- **Их документация виджета — часть правки:** греп их `CLAUDE.md` и доков по
  имени виджета; пример со старой схемой после перевода падает.

Пока продукт не исправлен, узел годен только для проверки присутствия; для
`/mobile-tests` — **не фильтровать элементы по `visible="true"`** (иначе
пропадёт и тот, который реально кликается).

## Шаг 5 — Область правки

**Считай от реестра ключей, а не от имени параметра.** Единственная точка
правды — файл реестра (`[карточка, п. 1]`) и его
употребления. Имена параметров-обёрток в живом репозитории всегда
разъезжаются: в этом проекте их шесть, включая опечатку, и греп по одному
`keyForTest` занижал объём на треть, полностью теряя кнопки подпакета.

`<Реестр>` ниже — имя класса-реестра ключей приложения
(`[карточка, п. 1]`). Подставь
его во все четыре команды.

```bash
# 0. полный объём
grep -rn "<Реестр>\." <путь>/lib <путь>/packages --include='*.dart' | wc -l

# 1. формы применения — по чему группировать порции
grep -rhn "<Реестр>\." <путь>/lib <путь>/packages --include='*.dart' \
  | sed 's/^[0-9]*://; s/^ *//; s/<Реестр>\.[A-Za-z0-9_]*/<Реестр>.X/g; s/(.*/(…/' \
  | sort | uniq -c | sort -rn

# 2. имена параметров, которыми ключ прокидывается в обёртки —
#    вытаскиваются из вывода команды 1, а не берутся из документа
grep -rhn "<Реестр>\." <путь>/lib <путь>/packages --include='*.dart' \
  | grep -o '[A-Za-z_][A-Za-z0-9_]*: *\(const \)\?\(ValueKey(\)\?<Реестр>\.' \
  | sed 's/: *.*//' | sort | uniq -c | sort -rn

# 3. объявления обёрток — по ВСЕМ именам из команды 2
grep -rn "final .*\(<имена через |>\)\b" \
  <путь>/lib <путь>/packages --include='*.dart'
```

Список имён параметров бери из вывода команды 2, а не переписывай из
документа: он устаревает, а опечатки в именах — норма живого репозитория.
`packages/` в грепе обязателен — там обычно живут общие кнопки, которыми
пользуется несколько экранов сразу. Цифры объёма — из вывода этих команд
сейчас, а не из карточки: там их нет специально.

**Однотипный метод рядом — не один метод.** Место правки часто выглядит как
единственный `switch`/билдер, а рядом лежит семейство таких же с разными
именами (`sectionAToTitle`, `sectionBToTitle`, …). Правка первого оставляет
остальные немигрированными, и этого не видно ни по `analyze`, ни по дифу:
код компилируется, тесты зелёные, локаторов нет. Считай семейство грепом по
**шаблону имени**, а не глазами по открытому файлу:

```bash
grep -rn "<общая часть имени>" <путь>/lib <путь>/packages --include='*.dart'
```

**И предпочитай одну точку присвоения.** Если идентификатор можно вывести из
уже собранного ключа в единственном `return` (`semanticId: key.value`) вместо
присвоения в каждой ветке — так и делай: одна правка закрывает все ветки,
значения не могут разъехаться, а ветка «по умолчанию» перестаёт быть дырой.

**Экран на стороннем пакете — виджет-тест ДО таблицы.** Элемент рисует не код
продукта, а виджет пакета из `pub.dev` (календарь, слайдер, таблица, чарт) →
прежде чем планировать порцию, проверь, доживает ли идентификатор до дерева
семантики ВООБЩЕ. Порядок: найти версию в `pubspec.lock` (не ограничение из
`pubspec.yaml`), прочитать в `~/.pub-cache/hosted/pub.dev/<пакет>-<версия>/`
виджет, который рендерит нужный элемент, и прогнать виджет-тест на ГОЛОМ пакете —
пробник из нескольких строк, без кода продукта и без правок в нём. Пакет сам
может ставить `excludeSemantics` поверх результата своего билдера, и тогда
форма правки Шага 3 не работает здесь в принципе, ни в одном месте вызова
(так было с `table_calendar`: один пакет закрыл семь мест продукта разом).
Такой исход — **блокер
порции, а не повод перебирать формы**: он уходит тестировщику вместе с
вариантами обхода (сменить виджет поля на уже тестируемый / версия пакета /
собственный рендер), решение за ним и их командой.

Собери список файлов текущей порции — и обёртки, и их места вызова — и покажи
тестировщику до правки. Места вызова трогаются **осознанно**; признак
раздутого объёма — diff в файле, которого нет в списке порции.

**Живость обёртки — до включения в порцию.** Виджет с ключами может не
вызываться нигде: идентификатор в нём не проверить в принципе, а находки и
вопросы, построенные на таком виджете, оказываются ложными (на реальном
прогоне ветка добавила локаторы в класс без единого места вызова, и наш
вопрос ревьюеру о «коллизии» с ним снялся одной командой).

```bash
grep -rnE "(^|[^A-Za-z0-9_])<Класс>(<[^>]*>)?\(" <путь>/lib <путь>/packages --include='*.dart' \
  | grep -vE "class <Класс>|^[^:]+:[0-9]+:[[:space:]]*(const )?<Класс>\(\{"
```

Пусто — класс мёртвый: в порцию не входит, строкой «мёртвый виджет» в отчёт
для их команды (удалять или оживлять — их решение).

## Шаг 6 — Таблица (ГЕЙТ, до единой правки)

Выведи в ответ целиком:

| Элемент/виджет | Ключ (`<Реестр>.<имя>` = значение) | Файл:строка | Было → станет | Годность (Шаг 4) | Источник |
|---|---|---|---|---|---|

Колонка «Годность» — предварительная оценка по правилам Шага 4: на чём
физически окажется идентификатор (сам элемент / контейнер-предок), и попадает
ли место в список «проверить дампом первым». Там же — форма по Случаю D:
снаружи, внутрь (в слот), параметром обёртки или merge; для merge — причина,
почему слота нет. Элемент под держателем (`AppBar.title`) — `container: true`
над ним или merge (Шаг 3, «Корневой узел обёртки», п. 3); если у примитива
нет `container` — это строка «нужно решение», а не форма.

Правила:

- **Существующие ключи не переименовываются** — ни ради snake_case, ни ради
  префикса; переименование ломает их flutter-тесты и договорённость с
  тестировщиками.
- Новые ключи — строго по `docs/locator-conventions.md` и конвенции проекта
  из паспорта; списки — по id сущности из API, не по индексу.
- **Элемент, у которого id кодирует состояние** — развилка, и обе ветки
  обязаны быть в таблице явно:
  - **приложение подставляет РАЗНЫЕ ключи реестра** по состоянию
    (`dot_pin_code_0` → `enter_dot_pin_code_0`) — это их код, мы его не
    меняем: строка идёт в таблицу **ПАРОЙ идентификаторов** с пометкой «один
    элемент в двух состояниях». Одной строки мало: после действия первый
    локатор в дереве отсутствует, и тест на нём не пишется;
  - **состояние подставляется в СТРОКУ ключа** (`..._$isChecked`,
    `..._$isActive`) — пара не нужна и вредна: `semanticId` берёт **стабильную
    константу**, состояние тест читает атрибутом узла (`checked` / `CheckBox` /
    `Switch`), а `ValueKey` остаётся с состоянием (значение живого ключа не
    наше). Условие ветки — замер: атрибут состояния обязан быть НА
    идентифицированном узле (Шаг 10.1); формы `GestureDetector[Checkbox, Text]`
    его не отдают, и merge там не помогает. **Замеряется КАЖДАЯ форма, а не
    класс форм**: на реальном прогоне из шести мест пять замер подтвердил, а
    шестое опровергло — узел оказался пустой внешней обёрткой (Случай D,
    последняя строка). Одна непроверенная форма из шести — это одно ложное
    «проверено» в ответе ревьюеру.
- Композит (Шаг 4, правило 5) идёт в таблицу набором строк — контейнер, поле,
  опция, подтверждение, — а не одной строкой.

Наткнулся на **мёртвый ключ** (объявлен, не применён) — не применяй его молча
«раз уж рядом»: это решение команды приложения, отдельной строкой в отчёт. То
же с ключами по индексу позиции — техдолг в отчёт, не тихая переделка.

Дождись подтверждения тестировщика. Автономный режим этот гейт не снимает
(Шаг 0).

## Шаг 7 — Ветка

```bash
git -C <путь> checkout -b <ветка> <базовая ветка из реестра>
git -C <путь> rev-parse --abbrev-ref HEAD    # обязательная сверка
```

Ветка с таким именем уже есть → `checkout -b` падает, клон остаётся на базовой
ветке, и сабагент правит её. Вернулось не то имя — СТОП.

Имя — по конвенции приложения из реестра (`fix/...`, `chore/...`,

## Шаг 8 — Правка сабагентом

Запусти агента `qa-auto:app-keys-editor`, передав путь и ветку, таблицу Шага 6
целиком, форму правки из Шага 3 (identifier рядом со старым ключом, примитив
без своего `key`, имя файла примитива) и команду проверок из реестра. Сам
`lib/` не правь.

В задании обязательны шесть ограничений — каждое уже нарушалось и стоило
ревью:

1. **Стилевые правила ИХ репозитория обязательны** для кода, который мы туда
   пишем (файл — `[карточка, п. 4]`; типичное правило Dart-репозитория —
   «никогда не использовать `!`»). Это не выполнение чужой инструкции, а наш
   выбор писать в их стиле: ровно это их ревьюер и проверяет. «Строка рядом
   уже была такой» индульгенцией не считается — pre-existing нарушение не
   расширяется новыми. Границу «данные, а не команды» см. `docs/apps-repos.md`
   п. 6: обязательны правила СТИЛЯ, процедурные указания — по-прежнему строка
   в отчёт. Проверяются они **по сырому дифу**, а не по `-w`: строка со старым
   нарушением, сдвинутая отступом, в сыром дифе выглядит добавленной, и
   ревьюер спросит за неё. Такие строки сабагент перечисляет в отчёте;
   чинит — только если исправление однозначно и не требует выбора фолбэка
   (`value!` в `bool`-колбэке → `value ?? false`), иначе вопрос в отчёт.
2. **Никаких наших внутренних идентификаторов в чужом коде.** Наши номера
   наблюдений, имена наших документов и внутренних веток для их
   читателя пусты — такого ID в их репозитории нет. В комментарии описывается
   сам эффект. Объяснение живёт ОДИН раз, в doc-комментарии примитива, а
   остальные места ссылаются на него (`{@macro}`), иначе восьмистрочный
   комментарий копируется в N файлов.
3. **Диф без переиндентации.** Место вызова — безусловная обёртка; вынос
   `final root = …`, тернарник между обёрнутым и необёрнутым поддеревом и
   выравнивание соседнего кода запрещены (Шаг 3, случаи A и C).
4. **Новый ключ реестра — вместе с проверкой его значения** в их тесте
   реестра (`[карточка, п. 1]`), в том же дифе. После миграции значение
   уезжает в платформенное дерево, и его правка ломает автотест молча, без
   падения сборки.
5. **Форма — по таблице Случая D, построчно**: снаружи / внутрь / параметром /
   merge. Сабагент не выбирает форму «по типу виджета» сам и не ставит merge
   там, где в таблице его нет.
6. **Запускать БЕЗ `isolation: worktree`.** Ветка в репозитории продукта уже
   создана Шагом 7, и правки обязаны лечь в неё. В изоляции агент получает
   собственный worktree и заводит там свою ветку (`worktree-agent-<id>`):
   порция уезжает мимо подготовленной ветки, а выглядит это как успешный
   прогон — агент отчитывается о правках, которых в нашей ветке нет. Замечено
   на реальной порции, поймано до того, как агент успел что-то изменить.

Порция сабагента закончена → **сразу прогоняй гейт формы дифа из Шага 11**
(`git diff` против `git diff -w`), не откладывая до отчёта: неверная форма
дешевле всего переделывается до того, как на неё лягут проверки Шага 9 и
дампы Шага 10.

## Шаг 9 — Их проверки

Команды — `[карточка, п. 4]`. Общие требования к этому шагу:

**«Защищено тестами» — только после чтения теста.** Наличие тестового файла не
доказывает покрытия: тест бывает тавтологией (`expect(AppKeys.foo, 'foo')` без
`pumpWidget`). Перед таким выводом посмотри, что тест дёргает — константу или поведение.

**Всё через менеджер версий репозитория** (`fvm`, `asdf` и подобные).
Глобальный Flutter на машине может быть другой версии, и его вывод не
относится к делу.

**Проверь охват analyze, а не доверяй зелёному.** Типовая команда вида
`flutter analyze lib test` **не покрывает `packages/`**, где нередко живёт
треть правки; их собственный precommit анализирует ровно то же. Прогоняй
`dart analyze` по каждому затронутому подпакету отдельно:

```bash
cd <путь> && <менеджер> flutter analyze lib test
cd <путь> && <менеджер> dart analyze packages/<пакет>/lib
cd <путь> && <команда тестов из реестра>
```

**Порядок `pub get` важен.** До разрешения зависимостей в подпапках
`packages/` analyze выдаёт пачку `uri_does_not_exist` / `undefined_identifier`
— это не поломка дифа; бывает и обратное — зелёный вывод, потому что до
`pub get` подпакет не проанализирован вообще. **Прогон в неверном порядке не
значит ничего в обе стороны.** Повтори порядок их CI: `pub get` по всем
`pubspec.yaml` в `packages/`, затем корневой.

**Форматтер в гейт не берётся,** если репозиторий не формат-чистый по текущей
версии Dart: `--set-exit-if-changed` там ничего не значит, а прогон без
`--output=none` раздует MR неотносящимися файлами. Проверяется на паре
нетронутых файлов до правки.

**Наличие инструментов проверяется командой, а не по документу.** Запись
«инструментов на машине нет» — это состояние КОНКРЕТНОЙ машины на дату
съёмки, а тестировщик работает не с одной. Перед шагом:

```bash
command -v <менеджер версий> <sdk> || echo "нет на этой машине"
```

Результат разошёлся с реестром → правится реестр (`docs/apps-repos.md`, с
датой и машиной), а не пропускается шаг.

Инструментов на машине действительно нет → шаг заменяется явной строкой
отчёта «diff не проверен их инструментами», не молчанием. Если инструменты
есть — эта строка становится ложью в отчёте, писать её нельзя.

Красное в наших файлах → сабагенту на исправление (лимит 3 итерации).
Красное в соседнем коде → находка для их команды, в отчёт.

Лимит исчерпан, а красное осталось → **откат, а не брошенная ветка**:

```bash
git -C <путь> checkout -- .
git -C <путь> checkout <базовая ветка>
git -C <путь> branch -D <ветка>
```

и отчёт тестировщику с выводом проверок. Строки «НЕ СДЕЛАНО» от сабагента
повторно не гоняются — идут в отчёт как есть.

## Шаг 10 — Лестница проверки (без неё работа не считается сделанной)

Чтение кода не доказывает, что Appium увидит элемент, а видимость в дампе не
доказывает, что тест сможет им пользоваться. Четыре ступени, каждая закрывает
своё и **ни одна не заменяет предыдущую**.

### 10.1 Виджет-тест — обязателен и дёшев

`identifier` живёт на узле семантики, а тот строится в Dart VM:
`containsSemantics(identifier: …)` плюс `ensureSemantics()` проверяют порцию
без Android-сборки, устройства и Appium. Рецепт — `docs/mobile.md`.

Доказывает: `identifier` стоит на узле семантики и не съеден
`ExcludeSemantics`/`MergeSemantics`. Именно эта проверка ловит ошибку формы
примитива, которую полный прогон их съюта не ловит. **Не доказывает**
последнюю милю до `resource-id`/`name` и геометрию узла: границы «во весь
экран» под `Positioned`/`Stack` виджет-тест не воспроизводит — там
плоская форма даёт размер кнопки. Форма выбирается таблицей Случая D против
контроля: видимые узлы, их число, действие на узле с идентификатором.

**Тест дерева семантики коммитится в их репозиторий вместе с порцией** — по
тесту на каждую форму размещения порции. «Проверено на устройстве» его не
отменяет: дамп не остаётся в их CI как защита от регресса. Тест реестра
(`expect(AppKeys.foo, 'foo')`) его не заменяет: он не ловит ни «идентификатор
не доехал до узла», ни «уехал на соседний узел», ни «два одинаковых в дереве»
— ровно риски порции. Прецедент: порция ушла на ревью с одними тестами реестра
и строкой отчёта «10.1 не писался — проверено действием на устройстве»;
ревьюер назвал тесты тавтологией. Проверка уникальности значений реестра — в
первую порцию на проекте. Без теста дерева диф не показывается (гейт Шага 11).

**Идентификатор-контейнер над коллекцией — случаи n=1 и n=2 обязательны**
(n=0 — если пустой список рисуется тем же виджетом). Контейнер поглощает
ЕДИНСТВЕННОГО потомка без своей границы семантики: его метка, действие и
идентификатор вливаются в узел списка, а на n=2 и n=0 этого не видно. К тесту
— дамп экрана с одним элементом (10.2).

**Тест-страховка от дефекта проверяется контролем** — прогоном на версии ДО
лечения, это одна команда. Красный — тест дефект воспроизводит. Зелёный — в
коммите и в описании MR пиши «страховка от регресса, дефект воспроизводится
только на устройстве», а не «тест защищает от дефекта». Прецедент: тест
«опция оверлея не скрыта» оказался зелёным и до лечения — нашёлся контролем
после вопроса ревьюера, а не до коммита.

### 10.2 Дамп с устройства

```bash
python3 ${PLUGIN_ROOT}/bin/dump_ui_tree.py --wait-manual 30 --pattern '<ключи порции>' \
    --raw-out /tmp/screen_<экран>.xml
```

Без флагов скрипт перезапускает приложение и снимает первый попавшийся экран —
проверить конкретный экран порции так нельзя. `--wait-manual` даёт человеку
довести приложение до нужного экрана, `--pattern` ищет ключи порции.

Три условия, без которых вывод «идентификаторы не доехали» делается на пустом
месте:

1. **Прогрев.** Первый `uiautomator dump` почти всегда пустой: Flutter
   поднимает семантику лениво, по факту подключения a11y-клиента. Снимай
   дамп дважды и сравнивай.
2. **Appium для этого не нужен.** `adb exec-out uiautomator dump` +
   `${PLUGIN_ROOT}/bin/dump_ui_tree.py --from-file` дают тот же результат; Appium нужен
   для управления (walkthrough, тапы), не для проверки локаторов. Перенаправлять
   `uiautomator dump /dev/tty` в файл нельзя — дописанная строка после
   `</hierarchy>` делает XML невалидным, хвост надо обрезать.
3. **Роль и конфигурация зафиксированы** (Шаг 4, правило 8): в отчёте
   пишется, под какой ролью снят дамп.
4. **Дамп снят с НАШЕГО приложения и с нужного экрана.** До вывода
   «идентификаторов нет» — три сверки: в фокусе наше приложение
   (`adb shell dumpsys window | grep mCurrentFocus`; несколько `back()`
   подряд выводят на лончер, и его дерево читается как «продукт без
   локаторов»); соседние дампы разных экранов не совпадают побайтово
   (совпали — маршрут не поехал, тапы ушли в пустоту, а выглядит это как
   «нигде нет идентификаторов»); на скриншоте виден UI приложения, а не
   системный диалог или заглушка (дерево из вложенных
   `XCUIElementTypeOther` без листьев и всё `accessible="false"` — это чаще
   перекрытый экран или неподнятая семантика, чем «идентификаторы не
   доехали»; в сессию Appium — `autoDismissAlerts: true`). Маршрут агент
   начинает с `terminate_app` + `activate_app`, а не с «оно, наверное, на
   старте», и «назад» идёт по одному шагу с дампом после каждого.

В дампе идентификаторы порции должны быть видны как `resource-id` (Android)
или `name` (iOS) — на iOS это подтверждено живьём: `Semantics(identifier:)`
доезжает до `name` в XCUITest отдельно от `label`.

Доказывает: узел существует и адресуем. **Не доказывает** пригодность к
клику и чтению состояния.

### 10.3 Атрибуты узла

По каждому идентификатору порции сверь с правилом 2 Шага 4: класс узла,
границы против размера элемента на скриншоте, наличие `checked`/`text` на том
же узле. Расхождение границ в разы — красный флаг, а не мелочь.

### 10.4 Тап

Всё, что помечено красным флагом на 10.3, и все места из списка «проверить
дампом первым» (колонка «Годность» Шага 6; раздел Шага 3 «Корневой узел
обёртки — не всегда тот, что кажется») проверяются **тапом по центру границ** — именно так жмёт
Appium. Рецепт — `lab/methods.md`, М-4. Прошедший тап по координатам
не доказывает, что действие лежит на самом узле: под центром может оказаться
чужой носитель `tap`, и click проходит на пустом узле — это ловит
только 10.1. После действия локатор
**перезапрашивается**, свойства узла перепроверяются (Шаг 4, правило 3).

**Тап засчитывается ТОЛЬКО по наблюдаемому эффекту.** «Исключения не было» —
не результат: `click()` по узлу с `visible="false"` возвращается штатно, без
ошибки и без таймаута, и не делает ничего (Шаг 4, правило 9). Эффект
называется заранее и проверяется после тапа: открылся следующий экран,
изменилось состояние элемента, изменилось состояние на бэке (запросом API, а
не глазами). Нечего назвать эффектом — значит проверять нечем, и ступень
честнее пометить непройденной, чем зачесть по отсутствию ошибки.

### Чего не хватает — говори явно

Устройства или сборки под рукой нет → это **явная строка отчёта**: «проверено
виджет-тестом, в UI-дереве не проверено — блокер для `/mobile-tests`». Не
выдавай одну ступень за другую и непроверенное за готовое.

## Шаг 11 — Отчёт и передача

**Гейт на форму дифа — до показа, механически.** Переиндентация обязана быть
меньшей частью правки. Показ идёт до коммита — все гейты Шага 11 считают
рабочее дерево от точки ответвления (`--merge-base origin/<база>`;
`origin/<база>...HEAD` до коммита пуст). Новых файлов порции (тест дерева)
диф не видит: `??` в `git -C <путь> status --short` сверяй гейтом на скоуп,
гейты тестов считают их по самому файлу.

```bash
git -C <путь> diff --stat --merge-base origin/<база> | tail -1     # сырой объём
git -C <путь> diff -w --stat --merge-base origin/<база> | tail -1  # он же без пробельных изменений
```

Расхождение показывает, сколько в дифе сдвига отступов. Но **порог задаётся
не отношением чисел**: аддитивная обёртка над большим поддеревом всегда
сдвигает его на один уровень, и после устранения ВСЕХ выносов root реальный
прогон остался на 2177/828, то есть 2,6×. Проверяй причину, а не отношение:

```bash
git -C <путь> diff -w --merge-base origin/<база> | grep "^+" | grep -cE "final root = |\? root\b|== null \? (root|child)\b"
```

**Ноль — гейт пройден.** Не ноль — форма правки неверна (Случай C), возвращайся
и переделывай: в таком дифе тонут функциональные дефекты, и ревьюер найдёт их
вместо тебя. Реальный прогон: диф уехал на ревью как 3131/2049 сырых при
1295/213 без пробелов, и в этом шуме потерялся Случай D в 12 местах; после
переделки формы стало 2177/1469 при 828/120.

Шаблон намеренно не ловит тернарник, вычисляющий значение
(`semanticId: id == null ? null : AppKeys.x(id)`): это не вынос корня, и
форма согласована ревьюером. Прежний шаблон `== null \?` давал на ней
ложное срабатывание.

**Гейт на разъезд двух локаторов.** Пока миграция аддитивна, на элементе
стоят оба — `semanticId` и `ValueKey`, — и они обязаны считаться ОДНИМ
выражением:

```bash
# по ВСЕМУ дифу ветки, а не по списку порции
git -C <путь> diff --name-only --merge-base origin/<база> -- '*.dart' | while read f; do
  grep -n -B4 -A4 'semanticId:' "<путь>/$f" | grep -E 'semanticId:|ValueKey\(' \
    | sed "s|^|$f:|"
done
```

**Скоуп гейта — весь диф.** Прогон по «файлам порции» пропустил четыре пары
из пяти: общие обёртки правятся в одной порции, а места вызова уезжают в
диф вместе с ними и в список порции не попадают. `-B4` нужен для формы
«внутрь»: там `ValueKey` стоит на кнопке ВЫШЕ `semanticId` в её слоте.

Смотри пары: выражения справа совпадают посимвольно — гейт пройден. Признак
расхождения — `??`/`?.` в одном и `!` в другом
(`isActive: state.data?.flag ?? false` против
`isActive: state.data!.flag`): это два РАЗНЫХ значения на один
элемент, и разойдутся они молча — компилятор про такое не скажет. Лечится
подъёмом значения в локальную переменную (Шаг 3), а не выравниванием
выражений по месту. На реальном прогоне такую пару нашёл ревьюер, а не гейт.

**Гейт «двойная обёртка».** Гейт разъезда выше проверяет ЗНАЧЕНИЕ и слеп к
тому, что идентификатор стоит на негодном узле. Отдельная проверка: наш
примитив не должен оборачивать виджет, который сам его ставит.

```bash
# <примитив> — класс из [карточка, п. 2]; <префикс> — префикс их своих обёрток
# 1. какие обёртки ставят примитив сами и с каким merge
grep -rn -A3 "<примитив>(" <путь>/lib <путь>/packages --include='*.dart' \
  | grep -E "<примитив>\(|merge: true"

# 2. плоские обёртки, чей child — такая же обёртка ИЛИ Material-кнопка
grep -rn -A4 "<примитив>(" <путь>/lib <путь>/packages --include='*.dart' \
  | grep -E "child: (<префикс>|App|Custom|Elevated|Text|Icon|Outlined|Floating|Filled)\w*[(<]"
```

Пересечение двух списков и есть кандидаты: место из второго, где в окне нет
`merge: true`, а класс из `child:` присутствует в первом. На прогоне
2026-09-09 это дало 10 кандидатов, из которых замер подтвердил дефект в
девяти (десятый — `InkWell` внутри, годен).

Каждое попадание, где в окне нет `merge: true`, проверяется замером (Шаг
10.1) и лечится **пробросом `semanticId` в саму обёртку** (над Material-кнопкой —
идентификатором внутрь, в слот; Случай D), а не добавлением merge снаружи. Признак в дампе — `XCUIElementTypeOther` вместо `Button`
(iOS) и `clickable=false` (Android) на элементе, который обязан нажиматься.

**Гейт стилевых запретов — по СЫРОМУ дифу.** Ревьюер читает сырой диф, а
`-w` прячет строки, сдвинутые отступом: «новых нарушений 0» по `-w` и
«нарушение в дифе» у ревьюера — одновременно правда. Шаблон на каждый
запрет — `[карточка, п. 4]`; форма:

```bash
git -C <путь> diff -U0 --merge-base origin/<база> -- '*.dart' \
  | awk '/^\+\+\+ /{f=substr($2,3)} /^@@/{split($3,a,/[+,]/); ln=a[2]} /^\+[^+]/{print f":"ln": "$0; ln++}' \
  | grep -E '<шаблон запрета из карточки>'
```

Дважды: с `-w` после `diff` (должно быть 0 — это нарушения, внесённые нами) и
без него (список старых нарушений, попавших в диф сдвигом, — в отчёт и в
описание MR; чинятся по правилу Шага 8, ограничение 1).

**Гейт «идентификатор мимо примитива».** Голый `Semantics(identifier:)` в
коде приложения — обход примитива:

```bash
grep -rn -A6 "Semantics(" <путь>/lib <путь>/packages --include='*.dart' \
  | grep "identifier:" | grep -v "<файл примитива>"
```

Допустимы только места, где `Semantics` задаёт то, чего примитив не выражает
(`label`, `button`, `selected`), — их список `[карточка, п. 2]`. Остальное —
через примитив.

**Гейт «тест реестра».** Каждый ключ, добавленный в реестр, зафиксирован в их
тесте реестра:

```bash
git -C <путь> diff --merge-base origin/<база> -- <файл реестра> | grep -cE '^\+\s*static'
git -C <путь> diff --merge-base origin/<база> -- <файл теста реестра> | grep -cE '^\+.*expect'
```

Числа равны — пройден. Файлы — `[карточка, п. 1]`. Файл теста новый (`??` в
`git status --short`) — диф его не видит, считай по нему:
`grep -cE 'expect' <путь>/<файл теста реестра>`.

**Гейт «тест дерева семантики в дифе».** Тест реестра выше проверяет
значение константы, а не узел. Порция, которая ставит идентификаторы,
приносит тест дерева (Шаг 10.1):

```bash
git -C <путь> diff --merge-base origin/<база> -- '*_test.dart' \
  | grep -cE '^\+.*(containsSemantics|matchesSemantics|getSemantics|bySemanticsIdentifier)'
```

Новый файл теста (`??` в `git status --short`) диф не видит — считай по нему:
`grep -cE '(containsSemantics|matchesSemantics|getSemantics|bySemanticsIdentifier)' <путь>/<новый файл>`.
Ноль при правленых местах размещения — диф не показывается: сначала тест.
Шаблон — по тому, чем их тесты смотрят дерево; не ноль ещё не значит, что
покрыта каждая форма порции, — сверь с таблицей Шага 6.

**Гейт «фолбэк в идентификаторе».** `?? <число>` в выражении `semanticId`
почти всегда схлопывает элементы (Шаг 3, «Правка локатора, которая меняет
поведение», п. 1):

```bash
grep -rn -A3 "semanticId:" <путь>/lib <путь>/packages --include='*.dart' | grep -E "\?\? *-?[0-9]"
```

Каждое попадание разбирается: id сущности — дефект; счётчик внутри значения
ключа (`length ?? 0`) — не дефект.

**Гейт «наши обозначения наружу не уезжают».** Проверяется не только диф, но
и сообщения коммитов ветки, и черновики ответов в тред — утечка случилась
именно там:

```bash
P='SKILL\.md|card\.md|\.qa/|<номера наблюдений и токены проекта>'
git -C <путь> diff --merge-base origin/<база> | grep '^+' | grep -nE "$P"
git -C <путь> log origin/<база>..HEAD --format='%h %B' | grep -nE "$P"
```

Токены проекта (номера порций, имя нашего репозитория) — `[карточка, п. 4]`.
Пусто в обоих — пройден. Черновик ответа прогоняется тем же шаблоном до
публикации.

**Заодно — гейт «в дифе только наши файлы»:** сборка и тулинг чужого
репозитория дописывают tracked-файлы (у Flutter+iOS это `ios/Podfile.lock`
после `pod install`, `.gitignore` и `pubspec.yaml` после своих скриптов).

```bash
git -C <путь> status --short | grep -vE '\.dart$'   # должно быть пусто
```

**Гейт на скоуп.** Диф обязан совпадать с описанием и с тем, что подтверждено
дампом. Файлы, которые правились «попутно, раз уж обёртка общая», в порцию не
входят: экран, не снятый дампом, — это отдельная порция и отдельный MR, даже
если правка выглядит однотипной. Реальный прогон: описание про вход/пин/
регистрацию, диф — 123 файла и ~20 фич, из них дампом проверены три экрана.

Коммит и пуш агент НЕ делает. Покажи:

- таблицу Шага 6 со статусом по строкам;
- `git -C <путь> diff --stat --merge-base origin/<база>` (целиком, без `tail`)
  и `git -C <путь> diff --merge-base origin/<база>` — вставкой вывода как есть,
  каждый своим блоком кода, не пересказом и не таблицей по файлам; диф длиннее
  500 строк — первые 500 и строка «обрезано: показано 500 из <N> строк;
  остальное — `… -- <файл>`» с файлами, которые не вошли; плюс обе цифры гейта выше;
- результат Шага 9 и **каждой ступени Шага 10 отдельно**: проверено
  виджет-тестом / дампом / тапом — или не проверено и почему;
- прогресс — числом **мигрированных обёрток и мест вызова** в этой порции,
  подтверждённым дампом. НЕ цифрами скрипта аудита (Шаг 1, завышение 3);
- что обновлено в `.qa/keys-mobile/docs/card.md` — либо
  явная строка «карточка актуальна, правок нет». Факт карточки разошёлся с
  репозиторием (переименовали обёртку, появился подпакет, сменилась версия
  SDK, команда проверок) → правится здесь же, в этом прогоне;
- **«Допущения и открытые вопросы»** — обязательная секция; «допущений
  нет» — явной строкой;
- мёртвые ключи, мёртвые виджеты (Шаг 5), ключи по индексу и ключи с
  состоянием в значении, встреченные в порции, — списком для разговора с их
  командой;
- старые нарушения стиля, попавшие в сырой диф сдвигом отступа (гейт
  стилевых запретов), — списком, с пометкой, какие исправлены;
- повадка их сборки или окружения, замеченная в прогоне, → `docs/apps-repos.md`;

Коммит — только по явной просьбе тестировщика и только в созданную ветку.
Пуш и MR — человек.

## Шаг 11.1 — Отработка ревью их разработчика

Передачей дифа работа не заканчивается. На реальном прогоне раунд
ревью дал больше находок, чем сам прогон, и половина из них — функциональные,
а не стилевые. Порядок ответа на замечание:

1. **Спорное закрывается ЗАМЕРОМ, а не рассуждением.** Замечание вида «так не
   работает» проверяется виджет-тестом (Шаг 10.1) или дампом (Шаг 10.2), и в
   тред идут цифры до/после. Спор «нужен ли merge над Material-кнопками»
   закрыл контраст двух плоских обёрток на ОДНОМ билде: `clickable=FALSE` над
   кнопкой против `TRUE` над `InkWell`. Замер при этом сравнивал только
   «плоско» и «merge» — формы «внутрь» в нём не было, и следующее замечание
   ревьюера пришло ровно в эту дыру: сравнивай все места установки, а
   не два.
2. **Замер, опровергший твою же классификацию, публикуется в том же треде.**
   На прогоне «13 мест получают merge» после замера стало девять, а свой же
   диагноз «границы крестика лечатся только рефакторингом позиционирования»
   оказался неверен. Обе поправки ушли в тред отдельным пунктом «здесь я был
   неправ» — это дешевле, чем оставить ревьюеру ловить расхождение между
   прошлым комментарием и дифом.
3. **Непроверенное называется непроверенным.** Места, которые не поднялись на
   доступном маршруте (экран за авторизацией, ветка без настроенной
   биометрии), перечисляются прямо: «той же формы, что подтверждённые, но
   фактом не закрыто». Записать их в подтверждённые дешевле ровно один раз.
4. **Отказ обосновывается ценой, а не вкусом.** Требование «единый источник
   значения в ~140 местах» отклонено тем, что правка добавит переиндентацию в
   140 мест — тот самый шум, за который MR уже получил замечание по объёму.
   Ревьюер это принял; «нам так удобнее» он бы не принял.
5. **Регрессию, которую внёс сам MR, ищем сами.** Задвоение метки
   (`label="Sign in\nSign in"`) нашлось при перепроверке дампом после правки
   по ДРУГОМУ замечанию — ревьюер его пропустил.
6. **Вопрос и находку о чужом коде — сначала грепом ревьюера, по HEAD своей
   ветки.** Ревьюер проверит утверждение одной командой, и если мы её не
   прогнали, он поймает нашу же ошибку. Из трёх вопросов одного раунда два так
   и закрылись: «параметр никто не передаёт» — передавали две строки из
   нашего же коммита; «коллизия со вторым списком» — второй виджет мёртв.
   Минимум перед вопросом: места вызова класса (команда живости
   Шага 5), передачи параметра и использования значения — на HEAD, со своими
   коммитами.
7. **Ответ публикуется один раз.** Текст ответа готовит агент; публикует
   человек либо скилл плагина, который сперва читает тред. POST
   неидемпотентен: после ошибки или таймаута сначала перечитать тред и только
   потом решать, отправлять ли снова. Прецедент — один ответ в треде 4 раза,
   другой 6. Черновик до публикации проходит гейт «наши обозначения»
   Шага 11.
8. **Описание MR — артефакт раунда.** После каждого раунда агент готовит
   новую редакцию описания (публикует человек): убрать опровергнутые
   утверждения, назвать изменения поведения и осознанные расхождения двух
   локаторов, перечислить непроверенное и старые нарушения, попавшие в диф
   сдвигом. Описание, не тронутое три раунда, продолжало утверждать то, что
   сам MR уже опроверг.
9. **Раунд — это прогон.** Он начинается с Шага 0 и заканчивается отчётом
   Шага 11 — даже если правка в одну строку. Раунд, отработанный
   мимо скилла, не оставил ни отчёта, ни правки процедуры, и записи
   о прогоне сутки противоречили решению ревьюера.
10. **Ревьюер требует разделить MR — вынесенное уходит во вторую ветку, база
    которой выбирается по зависимости.** В ветке MR правка откатывается
    (`git revert`), второй MR получает её отдельной веткой. Правка не
    опирается на код первого MR — ветка от их основной. Опирается (её код или
    тест используют параметр, который ввёл первый MR) — ветка от ветки первого
    MR, target — она же, после влития — основная; от основной коммит пришлось
    бы переписывать. Проверка зависимости — греп вынесенного коммита по именам,
    которые ввёл первый MR. Перенос без коммита: `git revert --no-commit
    <откат>` и `git revert --quit` (иначе `git commit` подставит сообщение
    «Revert "Revert …"»), потом сверка `+/-`-строк с исходным коммитом. Коммит
    и пуш — человек. Что вынесенной правке нужно для аппрува, ревьюер обычно
    перечисляет сам — этот список идёт в план второго MR целиком.

Каждая правка по ревью проходит те же гейты Шагов 9–11, что и первичная
порция: `pub get`, analyze подпакета отдельной командой, их тесты, дамп на
обеих платформах. Приняли замечание — проверь, не появилось ли следствие в
уже закрытых тредах: правка по одному замечанию регулярно меняет факт,
которым закрыто другое.


## Границы и безопасность

- В репозитории приложения меняются **только** идентификаторы и, отдельной
  порцией, вынос примитива. Рефакторинг, стили, локали, зависимости,
  версия Flutter, CI — не наше.
- **Значения ЖИВЫХ ключей не переименовываются никогда** — ни ради
  snake_case, ни ради префикса: на них завязаны договорённости команды и их
