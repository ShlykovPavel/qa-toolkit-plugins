# Настройка форка (setup-fork)

Одноразовая (и идемпотентная) настройка форка под реальный проект. Результат —
**паспорт проекта** `docs/project-profile.md`: постоянная память об авторизации,
ролях, URL и конвенциях API. Все рабочие скиллы читают паспорт вместо того,
чтобы переспрашивать человека, поэтому от полноты паспорта зависит качество
всей дальнейшей генерации тестов.

## Шаг 0 — Проверка состояния (первым действием, до любой другой работы)

Прочитай `docs/project-profile.md` и выбери режим строго по таблице —
не «на глаз». «Запрос про настройку» = про авторизацию/роли/URL/OpenAPI/БД,
про сам паспорт или про init/подключение форка к проекту.

| Паспорт | Запрос про настройку форка? | Действие |
|---|---|---|
| Нет | — | Свежий форк → полная настройка, шаги 1–6. |
| Есть | Да | Режим обновления (ниже). |
| Есть | Нет | Это НЕ настройка. Одной фразой скажи, что форк уже настроен (сошлись на паспорт), и верни управление — НЕ начинай интервью и НЕ трогай файлы. |

**Режим обновления:** прочитай паспорт, покажи пользователю краткую сводку
(«сейчас настроено так: ...») и спроси, что изменить. Дальше работай только
с изменяемыми блоками — не переспрашивай то, что уже записано и не менялось.

## Шаг 1 — Разведка репозитория

Перед вопросами собери факты сам — не спрашивай то, что можно увидеть:

1. `git status`; `.env` — только есть ли он (`test -f .env`), не читай и не пиши
   (секреты стенда). `.env.example` тоже закрыт — какие ключи заведены, видно в `config.py` (п. 4).
2. `src/` — есть ли уже реальные клиенты помимо `example_*`? Есть ли уже
   `src/auth.py`? (значит, настройка частично сделана — учти это).
3. `Tests/conftest.py` — адаптирован ли `initialize` или это ещё шаблон
   с `ExampleAuth`.
4. `config.py` — какие переменные уже добавлены.
5. Паспорт базы знаний проекта (`project-passport.md` в её папке, если есть) и вступление её `CLAUDE.md`
   (описание продукта от init, в нём роли) — роли, адреса стендов, вход там уже ответил человек: бери
   оттуда, не переспрашивай, вариант «рекомендую» им не противоречит. Ролей нет ни там, ни в спеке —
   спроси без рекомендации, не придумывай. Ключи шаблона (`ADMIN_*` в `config.py`) — образец, а не роли.

## Шаг 2 — Интервью

Правило №1: **если пользователь дал вводные в самом запросе — извлеки их
и не переспрашивай.** Задавай только вопросы, на которые ответа ещё нет.
Правило №2: спрашивай блоками (не по одному вопросу), предлагай варианты
ответов. Правило №3: ответ «не знаю» — нормальный: зафиксируй пункт
в паспорте в разделе «Открытые вопросы» и продолжай.

Блоки вопросов (полный чеклист — в `references/interview-checklist.md`,
прочитай его перед интервью):

1. **Авторизация** — схема (Bearer JWT / cookie / api-key), эндпоинт логина,
   поля тела запроса, имена полей токенов в ответе, есть ли refresh.
2. **Роли** — какие нужны тестам, имена ключей для `HttpClient.access_folder`
   (латиницей, по ролям проекта), откуда креды каждой роли (env-переменные).
3. **URL** — базовые URL сервисов (один или несколько).
4. **Спека** — где OpenAPI (URL/файл/нет); если нет — что источник правды
   о контрактах (Confluence, человек).
5. **БД** — есть ли доступ, строки подключения (имена env-переменных!),
   какие таблицы МОЖНО трогать тестам, ключевые колонки для выборок.
6. **Конвенции API** — коды успеха create/update/delete, конверт
   списков/пагинации, формат тела ошибок.
7. **Охват** — только API / +фронтенд / +мобилка (платформа, где APK).
   Если фронтенд: URL веб-интерфейса, есть ли data-testid, И **библиотека
   фронтенд-тестов** — `selenium` или `playwright`. В паспорт пиши СТРОГО
   одним из этих двух токенов в поле «Библиотека фронтенд-тестов»
   фронт-секции; ответ «не знаю / всё равно» → `selenium` (дефолт
   шаблона). Других значений у поля не бывает.

## Шаг 3 — Подтверждение

Собери ответы в сводку и покажи пользователю ДО генерации файлов:
что будет создано, что изменено, какие допущения. Дождись подтверждения.

## Шаг 4 — Генерация

Порядок и правила:

1. **`src/auth.py`** — реальный клиент авторизации. Возьми реализацию
   нужной схемы из `references/auth-variants.md` (там готовые варианты
   Bearer / cookie / api-key) и адаптируй под ответы интервью.
   `src/example_auth.py` НЕ трогай — example-файлы остаются эталонами.
2. **`Tests/conftest.py`** — перепиши `initialize` на `src/auth.py`:
   логин каждой ролью из паспорта, токены в `access_folder` под именами
   ролей. Сохрани структуру и докстринги файла (это по-прежнему образец).
3. **`config.py`** — добавь переменные проекта (URL, креды ролей) по
   существующему стилю: только `os.getenv()`, с комментариями.
4. **`.env.example`** — допиши только недостающие ключи (что есть — шаг 1), с
   заглушками. Читать или править его закрыто — не обходи командой, отдай ключи
   человеку списком: «допиши в `.env.example` и в `.env`». `.env` агент не
   создаёт и не пишет ни правкой, ни командой (`>>`, `cp`, `tee`) — закрыто хуком.
   Человеку: «`cp .env.example .env` и впиши: <ключи>» (`.env` есть — «допиши»).
   Пароли в чат не проси; логин — когда человек сказал, что заполнил `.env`.
5. **`docs/toolchain.md`**, строка «Настройки стенда», колонка «Переменные» — замени
   ключи эталона на ключи проекта из `config.py`: base URL и учётки ролей. По ней preflight
   называет пустые ключи `.env`; с `ADMIN_*` эталона он краснеет мимо дела. Больше файл не трогай.
6. **Спеки** — каждую OpenAPI-спеку сохрани локально в `specs/` (несколько
   сервисов/Swagger-страниц = несколько файлов), а в паспорт запиши источник
   (URL) и дату скачивания каждой — обновление должно быть воспроизводимым.
7. **`docs/project-profile.md`** — заполни по шаблону
   `references/project-profile-template.md`. В паспорт НИКОГДА не пиши
   значения секретов — только имена env-переменных.

## Шаг 5 — Верификация

1. `make verify` — компиляция + коллекция обязаны быть зелёными.
2. Живой контрольный логин: только если (а) креды уже заполнены в `.env`
   и (б) пользователь согласен дёрнуть стенд. Одним запросом:
   `python -c "from src.auth import ...; login()"`. Успех → отметь в
   паспорте «авторизация проверена: <дата>». Ошибка → покажи ответ
   сервера и разбери с пользователем (неверный эндпоинт? поля? креды?) —
   это самый ценный момент настройки, не пропускай его молча.
3. Если стенд недоступен/кредов нет — зафиксируй в паспорте
   «авторизация не проверена» в «Открытых вопросах».

## Шаг 6 — Отчёт

Покажи: созданные/изменённые файлы, содержимое паспорта (кратко),
открытые вопросы, и следующий шаг — человеку создать и заполнить `.env` (если
ещё не заполнен) и запускать `/api-tests` (или писать тесты по docs/api-layer.md,
пока скилла нет).

## Границы и безопасность

- Не изменяй `example_*` файлы и `docs/*.md` (кроме создания project-profile.md и п. 5 Шага 4).
- Не коммить ничего без явной просьбы; напомни про запрет коммита `.env`.
- Секреты: только имена переменных в коде/паспорте/`.env.example`; `.env`
  создаёт и заполняет только человек, агент его не читает и не пишет.
- Скилл настраивает контур API-тестов полностью; для фронтенда/мобилки
  фиксирует ответы в паспорте (инфраструктура этих слоёв — отдельные этапы).
