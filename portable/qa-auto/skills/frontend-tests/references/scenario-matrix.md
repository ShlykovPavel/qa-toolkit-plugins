# Матрица сценария UI-теста (референс для Шага 3)

Матрица показывается пользователю ДО кода в виде таблицы со столбцами:
**№ | Шаг сценария | Элемент | Локатор | Ожидание-механика | Источник |
Ожидаемый результат**, где источник — `dump` (снят с живой страницы
способом своей ветки, Шаг 2) / `запрос` (вводные пользователя) / `вики` (страница и раздел) /
`ДОПУЩЕНИЕ` (страница недоступна — сверить с живым DOM). Столбец «Ожидание-механика» зависит от
ветки (по паспорту, таблица ветвления в Шаге 0 SKILL.md): selenium —
`finder_type`; playwright — auto-wait действия либо `expect()`-ассерт.

## Главное правило

**Локаторы — только из дампа живой страницы или вводных запроса.**
Выдуманный локатор = красный тест на ровном месте. Страница недоступна →
каждый локатор в матрице помечается ДОПУЩЕНИЕМ, а в отчёт идёт строка
«сверить с живым DOM до прогона».

**Второе правило: есть `data-testid` — локатор по нему** (selenium —
`[data-testid="…"]`, playwright — `get_by_test_id`): тесты ищут по
стабильным id, по видимому тексту — никогда (`docs/locator-conventions.md`).
Это главнее любой лестницы, в том числе старой в `docs/frontend.md` проекта
и кандидата дампа (у элемента есть `data_testid` — бери его). **Ключа нет** — самый высокий доступный
якорь лестницы своей ветки (selenium: id → name → css → xpath → link_text;
playwright: get_by_role → get_by_label → get_by_placeholder → css-резерв)
и сразу пометка техдолга «попросить у фронтов data-testid».

## Ожидание-механика: selenium-ветка (finder_type, см. docs/frontend.md)

| Элемент в шаге | finder_type |
|---|---|
| Кнопка, ссылка, элемент под клик | `Clickable` |
| Инпут/селект под ввод, чтение текста, проверка наличия | `Dom_located` (default) |
| Тост, модалка, индикатор — появление как ожидаемый результат | `Visible` (Dom_located пройдёт и на скрытом — ошибка) |
| Исчезновение модалки/спиннера | `Invisible` |

## Ожидание-механика: playwright-ветка (auto-wait + expect)

| Шаг | Механика |
|---|---|
| Действие (клик, ввод) | auto-wait самого действия — в столбце так и пишется «auto-wait» |
| Тост/модалка появились | `expect(...).to_be_visible()` |
| Элемент исчез | `expect(...).to_be_hidden()` |
| Текст/значение результата | `expect(...).to_have_text/have_value(...)` |

Подсказка из дампа (обе ветки): элемент с `"visible": false` до действия —
почти всегда кандидат на Visible / `to_be_visible()` в ожидании результата.

## Структура матрицы

Каждый шаг пользовательского сценария (открыть → действие → ожидаемый
результат) — строка матрицы. У шага-действия ожидание — переход/состояние
страницы; у шага-проверки — конкретный элемент результата (тост, строка
таблицы, сообщение об ошибке).

**Обязательные строки** — если это есть на экране:
- отмена каждого действия через форму или окно с кнопкой «Отмена»: отмена
  создания и отмена удаления — разные строки;
- граница, которую интерфейс показывает человеку (лимит поля, ошибка
  сервера в форме): строки с граничными значениями — здесь, а не «вопрос к
  API-тестам»: ошибку в форме видит только фронт-тест;
- противоречие или «не проверено» в вики про этот экран (Шаг 1 SKILL.md),
  если его видно в интерфейсе: строки с граничными значениями обеих позиций
  (вики 100, стенд 80 → 80, 81, 100, 101). Проверка этих строк — часть
  задачи; апрув на запись — как обычно. Противоречие закрывается этой
  проверкой, а не новым «не проверено».

Исключённое из матрицы — списком под таблицей, у каждой строки причина.

Пример (selenium-ветка):

| № | Шаг сценария | Элемент | Локатор | Ожидание-механика | Источник | Ожидаемый результат |
|---|---|---|---|---|---|---|
| 1 | Открыть список пользователей | — | `FRONTEND_BASE_URL` из config | — | паспорт | страница загрузилась (title/якорный элемент) |
| 2 | Нажать «Создать пользователя» | кнопка | `[data-testid="create-user"]` | Clickable | dump | открылась форма создания |
| 3 | Заполнить имя | инпут | id `user-name` | Dom_located | dump | значение введено |
| 4 | Отправить форму | кнопка | `//button[@type="submit"]` | Clickable | dump | — |
| 5 | Проверить подтверждение | тост | `.toast-success` | Visible | dump | тост виден |

Пример (playwright-ветка, те же шаги):

| № | Шаг сценария | Элемент | Локатор | Ожидание-механика | Источник | Ожидаемый результат |
|---|---|---|---|---|---|---|
| 2 | Нажать «Создать пользователя» | кнопка | `get_by_test_id("admin_users_create_button")` | auto-wait | dump | открылась форма создания |
| 3 | Заполнить имя | инпут | `get_by_test_id("admin_users_form_name_field")` | auto-wait | dump | значение введено |
| 5 | Проверить подтверждение | тост | `get_by_role("alert")` — ключа нет, техдолг | `expect(...).to_be_visible()` | dump | тост виден |

## Чего в матрице быть НЕ должно

- Селекторов «из головы» без пометки ДОПУЩЕНИЕ.
- Предусловий данных через UI — данные готовятся API-клиентами `src/`
  (нет клиента — сначала `qa-auto:api-clients`, Шаг 5 SKILL.md; UI-обход
  не городить).
- Фиксированных имён/email в данных формы — только генераторы
  `src/data_generators.py`.
- `time.sleep` — ожидания уже в ButtonFinder (WebDriverWait), асинхронность
  вне элементов — `wait_until()`.
- Шагов «на всякий случай» вне запрошенного сценария — скоуп определяет
  запрос, а не фантазия. Отмена и границы запрошенных действий — не «на
  всякий случай» (обязательные строки выше).
