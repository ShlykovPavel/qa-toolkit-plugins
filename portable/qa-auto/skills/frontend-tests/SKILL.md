# Генерация фронтенд-тестов (frontend-tests)

Вход — страница или пользовательский сценарий (тикет, описание). Выход —
page object + браузерный тест + зелёная верификация (и живой headless-
прогон, если стенд доступен). Библиотека (Selenium или Playwright) —
по паспорту проекта, см. таблицу ветвления ниже. Локаторы скилл берёт
из дампа живой страницы — не из догадок.

## Шаг 0 — Pre-flight (первым действием, до любой другой работы)

**Карточка задачи.** Задача без карточки (скилл позван напрямую, не из
`qa:task`) — сначала заведи карточку через `qa:task`, он вернёт сюда;
разовая правка без задачи — без карточки. Карточка этой задачи в сессии
уже заведена (например, до `keys-admin`) — вторую не заводишь. Под
оркестратором (тебя запустил сабагентом `/test-flow`) — без карточки, её
ведёт оркестратор.

Прочитай `docs/project-profile.md` и выбери режим строго по таблице:

| Ситуация | Действие |
|---|---|
| Паспорта `docs/project-profile.md` нет | Одной фразой: «форк не настроен, запусти /setup-fork» — и СТОП. Файлы не трогать. |
| Паспорт есть, но БЕЗ фронтенд-секции (URL админки/веб-интерфейса, роль и креды UI-логина, есть ли data-testid) | Одной фразой: «в паспорте нет фронтенд-секции — запусти /setup-fork, он идемпотентен и дополнит паспорт (вопрос 7 интервью)» — и СТОП. URL админки НЕ выдумывать. |
| Запрос про API-тесты (ресурс/эндпоинт/спека) или мобилку (Appium/Flutter) | Одной фразой скажи, что этот скилл покрывает только веб-интерфейс, и верни управление. |
| Запрос про починку/рефакторинг СУЩЕСТВУЮЩИХ тестов | Одной фразой скажи, что скилл генерирует новое покрытие, а починка — вне его скоупа; верни управление. |
| У элементов страницы нет стабильных локаторов, а репозиторий фронтенда есть в `docs/apps-repos.md` | Есть карточка задачи — `qa-task step <id> add "локаторы" --skill qa-auto:keys-admin`. Одной фразой: «локаторы ставит `/keys-admin`, вернись сюда после выката на стенд» — и верни управление. Репозитория в реестре нет → работай как раньше: тест с пометкой техдолга + список недостающих `data-testid` в отчёт. |
| Запрос — только снять DOM/селекторы, без тестов | Сними дамп способом своей ветки (Шаг 2) и покажи результат; пайплайн тестов не запускай. |
| Иначе | Прочитай паспорт целиком (фронтенд-секция: URL, роль/креды UI, testid-политика, библиотека). Работай дальше. |

**Ветка библиотеки** — определи СРАЗУ после чтения паспорта по полю
«Библиотека фронтенд-тестов» фронт-секции; поля нет → `selenium` (дефолт,
зафиксируй допущением). Дальше ВСЯ работа идёт строго по строке выбранной
ветки — компоненты веток НЕ смешивать (selenium-тест не использует
`page`/`expect`, playwright-тест не использует `driver`/ButtonFinder):

| | `selenium` | `playwright` |
|---|---|---|
| Дамп (Шаг 2) | `${PLUGIN_ROOT}/bin/dump_dom.py --locators css` (дефолт) | скрипт на playwright из `.venv` проекта; `${PLUGIN_ROOT}/bin/dump_dom.py` — на selenium, не для этой ветки |
| Локатор (Шаг 3) | `[data-testid="…"]`; ключа нет — лестница справочника | `get_by_test_id`; ключа нет — лестница справочника |
| Эталон page object (Шаг 4) | `frontend/front_keys/example_service/example_admin_page_keys.py` → копия в `front_keys/<сервис>/` | `frontend/pw_keys/example_service/example_admin_page_pw.py` → копия в `pw_keys/<сервис>/` |
| Эталон теста (Шаг 5) | `Tests/Frontend_tests/ExamplePage/` | `Tests/Frontend_tests/ExamplePagePW/` (importorskip обязателен) |
| Ожидания | `finder_type` по смыслу элемента | auto-wait + `expect()` (finder_type НЕ существует) |

**Оснащение машины — прогоном, а не памятью.** В этом же шаге:

```bash
preflight.py --use-marker
```

Молчит, пока на машине ничего не менялось (маркер `.preflight-ok` привязан к
хосту, не к клону — репозиторий ездит между машинами). Красное **не чинишь и
ничего не ставишь**: называешь пользователю, какой класс работы закрыт (колонка
«без неё» в выводе прогона), и продолжаешь в оставшемся
объёме — недостача идёт в отчёт. Для этого скилла критичны: Chrome (иначе не снять DOM и не прогнать тест), `.env` с URL и кредами UI-логина.
Заполнен ли `.env` — тоже из вывода прогона (строки с колонкой «Переменные»
называют пустые переменные по имени): сам `.env` и `.env.example` не читай —
доступ к ним обычно закрыт, попытки уходят в отказы.

**Автономный режим** = пользователь недоступен или явно попросил без
вопросов: вместо любого «спроси» — зафиксируй ДОПУЩЕНИЕ и продолжай;
все допущения попадут в отчёт.

## Шаг 1 — Сценарий

Из тикета/описания выдели шаги пользователя: открыть → действие →
ожидаемый результат. Вводные из запроса (URL страниц, имена полей,
ожидаемые сообщения) фиксируй — не переспрашивай их. Сценария нет,
есть только страница — предложи happy-path её главного действия.

**База знаний** — что вики знает об экране: `qa-kb-slice --endpoint
"<МЕТОД> <путь>"` на эндпоинты действий экрана (пути — в API-клиентах
`src/`). Код 2 — вики нет, дальше как раньше. Правила, лимиты, баги из
среза — строки матрицы с источником `вики`; противоречие или «не
проверено» про этот экран — обязательная строка (справочник матрицы).
«Не проверено по решению человека» из прошлого ингеста — не запрет
проверять сейчас.

## Шаг 2 — Живой DOM (развилка с выбором пользователя)

Селекторы ТОЛЬКО с живой страницы, не выдумывать.

**Playwright-ветка** — `${PLUGIN_ROOT}/bin/dump_dom.py` не зови: он требует selenium, которого
в проекте нет, и это не блокер. Дамп снимаешь сам одноразовым скриптом на
playwright из `.venv` проекта (файл — вне репо, в коммит не идёт): вход —
через вход проекта (page object или API-клиент логина, учётка из
`config.py`: пароль подставляет конфиг, ты его не видишь и в форму браузера
не вводишь); разрешение входа агенту — раздел 7 паспорта базы (`qa:rules`);
базы нет — фронт-секция `docs/project-profile.md`. С каждой страницы и
каждого состояния сценария (окно, тост, ошибка формы) — `data-testid`, тег,
роль, текст, видимость интерактивных элементов. Браузер своей сессии — если
вход в нём не требует от тебя пароля. Учётки роли в разделе 7 нет (`?`) —
вопрос человеку по `qa:rules` («Вход в учётки стенда»); ответ «сам» — проход
с человеком: MCP-проход (таблица ниже) или браузер сессии, где входит человек.
Страницы нет — автономный режим, как в таблице ниже.

**Selenium-ветка** — способ снятия зависит
от ситуации — **скопируй пользователю ПРЯМО В ОТВЕТ** шпаргалку-таблицу
«ситуация → способ» и подходящие рецепты из секции docs/frontend.md
«Как показать агенту страницы — инструкция для человека» (не только
ссылку). Предложи варианты ВСЕГДА, рекомендуй по ситуации:

| Ситуация | Рекомендация |
|---|---|
| Страница открывается по URL без логина (или file-фикстура из паспорта — ОТНОСИТЕЛЬНЫЙ путь, резолвится от корня репо) | **Одиночный дамп** КАЖДОЙ страницы сценария: `python3 ${PLUGIN_ROOT}/bin/dump_dom.py --url <URL или путь> --out /tmp/dump_<страница>.json` |
| Страница за логином; сценарий из нескольких шагов; состояния без своего URL (модалки, тосты, шаги визарда, ошибки валидации) | **Проход сценария**: `python3 ${PLUGIN_ROOT}/bin/dump_dom.py --walkthrough dumps/<сценарий>` — одна живая не-headless сессия, человек логинится и ведёт сценарий, на выходе дампы+скриншоты по шагам и `steps.json`. |
| В СВОЕЙ сессии есть инструменты `mcp__playwright__*` | **MCP-проход**: смотри страницу им (снапшот + селекторы), логин и шаги — в диалоге с пользователем. Команды вроде `claude mcp list` не гонять. Для file://-страниц — только ${PLUGIN_ROOT}/bin/dump_dom.py (MCP блокирует file:// по умолчанию, см. docs/frontend.md). MCP — опция, не требование |
| Страница недоступна / стенда нет | **Автономный режим по DOM**: селекторы из вводных/допущений, КАЖДЫЙ помечен `ДОПУЩЕНИЕ`, в отчёт — строка «сверить с живым DOM до прогона» |

Из walkthrough/MCP-прохода бери ОБА артефакта: последовательность шагов
(`steps.json` — почти готовые шаги теста, см. Шаг 5) и селекторы по
шагам (`step_NN_*.json`). Скриншоты шагов — вспомогательный контекст для
матрицы, НЕ источник селекторов. Элементы `fragile` из любого дампа (в
самописном playwright-дампе — элементы без testid) — сразу кандидаты в
техдолг.

## Шаг 3 — Матрица сценария ДО кода

Построй матрицу по `references/scenario-matrix.md` (прочитай его: там и
обязательные строки — отмена, границы в интерфейсе): шаг →
элемент → селектор → finder_type → источник (`dump`/`запрос`/`вики`/`ДОПУЩЕНИЕ`)
→ ожидание. **Выведи таблицу ЦЕЛИКОМ в ответ ДО создания первого файла**
— «матрица готова» без самой таблицы не считается; матрица только в
финальном отчёте = нарушение процедуры. Якорь локатора — по справочнику
(второе правило), порядок на вопрос человеку не выносишь. Покажи
пользователю и дождись подтверждения; в автономном режиме — зафиксируй
допущения и продолжай.

## Шаг 4 — Page object

Строго по эталону СВОЕЙ ветки (таблица ветвления Шага 0) и её разделу в
`docs/frontend.md`: копия эталона, класс страницы, по `@property` на
элемент; локаторы — из матрицы, а не из эталона; selenium — `finder_type`
по смыслу элемента, playwright — без ожиданий. ТОЛЬКО локаторы — никакой
логики. Page object страницы уже существует — расширяй его, не создавай
дубль (и не заводи его копию в чужой ветке).

## Шаг 5 — Тест

`Tests/Frontend_tests/<Фича>/` — своя директория с `__init__.py`, conftest
и тестом (как домены API-слоя; эталон — по ветке из таблицы Шага 0).
Обязательно: `pytestmark = pytest.mark.frontend`, allure epic "Frontend",
браузер только через фикстуру (selenium — `driver` параметром, playwright —
`page` плагина; НЕ на уровне импорта/класса; pw-директория — под
`pytest.importorskip("playwright")` в conftest И модуле), уникальные
данные из `src/data_generators.py`. **Предусловия данных — через
API-клиенты `src/`**, не через UI (`docs/frontend.md`). Нужного API-клиента
нет → предложи человеку сначала `qa-auto:api-clients` (только клиент и
модели ресурса X), после «да» вызови его и вернись сюда; «нет», автономный
режим или оркестратор — строка отчёта «нужен клиент ресурса X».
UI-предусловия не городить. Сценарий снимался walkthrough/MCP-проходом → источник
последовательности шагов теста — `steps.json` (порядок и имена шагов),
селекторы — из пошаговых дампов через матрицу. Каждая строка матрицы
Шага 3 → шаг теста (или явная пометка в отчёте, почему нет).

## Шаг 6 — Верификация

1. `make verify` — до зелёного (лимит 5 починок; упёрся — честный отчёт,
   не бесконечный цикл).
2. Живой headless-прогон `pytest -x -q -m frontend Tests/Frontend_tests/<Фича>/`
   — только если страница доступна И пользователь просил прогон (или это
   file-фикстура — она доступна всегда). Падения классифицируй в терминах
   маршрутизатора `docs/tests.md` («Маршрутизация по классификации»),
   фронт-проекция трёх типов:
   - **баг теста** → чини на месте;
   - **расхождение со спекой** (= изменилась вёрстка/DOM, селектор
     не находит) → НЕ подгонять наугад: свежий дамп страницы (это и есть
     возврат на стадию «спеки» фронта) → обнови селектор из дампа →
     точечный перезапуск;
   - **баг стенда** (= баг самого фронта) → **вызови скилл
     `/bug-report`** (отсев бага теста, согласование короткого описания,
     репорт), тест `xfail` со ссылкой на этот репорт, техдолг — в отчёт.
     Под оркестратором — кандидатом в отчёт: репорт оформит основная сессия.
   Лимит 10 итераций; счётчик итераций — в отчёт (0 — тоже значение).
3. **Ревью своего дифа — обязательно, до отчёта.** Зелёные verify и живой
   прогон доказывают, что тест РАБОТАЕТ, но не что он СООТВЕТСТВУЕТ
   конвенциям (слепые паузы, проверяемый шаг в conftest, утечка данных при
   падении до `yield` проходят зелёными). Свой код сам не ревьюй — автор
   не видит своих нарушений. Спавни агента `qa-auto:test-reviewer` со скоупом = список файлов,
   созданных и изменённых в этом прогоне. Это шаг процедуры: отдельного
   разрешения пользователя он не требует.
   - **high и med** — чинишь в этом же прогоне; med не чинится только с
     причиной, записанной в отчёт. **low** — в отчёт.
   - После правок — `make verify`; был живой прогон — точечный перезапуск.
   - Были high → ОДИН повторный `test-reviewer` по тем же файлам. Больше
     кругов не заводи: остаток — в отчёт.
   - Находки по чужим файлам — «вне скоупа» в отчёт, не править.
   - **Под оркестратором** (тебя запустили сабагентом `/api-suite` или
     `/test-flow`, либо ты `test-fixer`) шаг пропусти: ревью у оркестратора
     отдельной фазой. В отчёте — строка «ревью — за оркестратором».

## Шаг 7 — Отчёт

**Отчёт — по шаблону ниже.** Заголовки копируй дословно и по порядку, `<…>`
заполняй; пустая часть — строка «нет». Часть не переименовывай, не своди к
фразе и не пропускай: «Допущения и открытые вопросы»
пишутся и тогда, когда сказать нечего. Прочее (вводная, вопрос о коммитах) —
до или после шаблона, не вместо его частей.

````markdown
## Файлы
<созданные и изменённые, путями>
Копилка ловушек проекта: <что дописано и куда> / нет

## Покрытие сценария
| Шаг матрицы | Итог |
|---|---|
| <каждая строка матрицы Шага 3> | написано / xfail: <ссылка> / требует человека: <почему> |

## Хрупкие селекторы
<техдолг и что попросить у фронтов (data-testid)> / нет

## Допущения и открытые вопросы
<копией из матрицы и шагов, не пересказом> / допущений нет

## Прогон и ревью
- Живой прогон: гонялся / нет: <почему>; итераций Шага 6: <N>
- Ревью Шага 6.3: high/med/low до <…> → после <…>, кругов <N>; незакрытые: <находка — причина> / нет / за оркестратором

## Для вики
| Находка | Страница и раздел | Что будет написано |
|---|---|---|
| <правило, расхождение, баг, вопрос продукту> | <…> | <…> |
Заносить по этой раскладке? / для вики: нет
````

**Сверка перед отправкой.** Пройди заголовки шаблона сверху вниз, до
последнего, и найди каждый в отчёте дословно. Нет — допиши часть; сказать
нечего — строка «нет». Своя часть («Что дальше», итог задачи) идёт после
шаблона и его часть не заменяет.

**Для вики** (правило, расхождение, баг, вопрос продукту): куда что ложится —
справочник «находка стенда» скилла `qa:kb-ingest`; вопрос один — на
раскладке. После «да» первым действием **вызови скилл `qa:kb-ingest`** с
находками и пометкой «раскладка показана, „да“ получено» — вики пишет он.
Сам по справочнику вики не правь: прочитать справочник — не вызвать скилл.
Под оркестратором — только блок находок, без вопроса. Автономный режим или
«нет» — блок с пометкой «не занесено». Вики нет (`qa-paths wiki` — ошибка) —
части «Для вики» нет.

Найденная в работе ловушка ПРОЕКТА (нестабильный селектор, особенность
стенда, флаки, расхождение доки с фактом) → допиши её коротко («сигнатура →
как избегать») в секцию «Копилка ловушек проекта» в `docs/frontend.md`

## Границы и безопасность

- Не изменяй `example_*` файлы и `docs/*.md` — они эталоны
  (единственная прямая запись — секция «Копилка ловушек проекта»).
- Не трогай чужие страницы в `frontend/front_keys/` и чужие директории
  в `Tests/` — только свой сценарий.
- Никаких значений секретов и хардкода URL — только `config.py`/`.env`
  (имена переменных — из колонки «Переменные» `docs/toolchain.md`).
- Не коммить без явной просьбы.
- Данные между тестами не передавать; scope='session' для тестовых данных
  запрещён (см. CLAUDE.md).
