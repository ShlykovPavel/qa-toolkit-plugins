# Генерация мобильных тестов (mobile-tests)

Вход — экран или сценарий фичи мобильного приложения (тикет, описание).
Выход — app_keys + Module + тест + зелёная верификация (и живой прогон на
эмуляторе, если доступен и запрошен). Локаторы скилл берёт ТОЛЬКО из
дампа UI-дерева живого приложения — не из догадок; единственный вид
локатора — стабильный идентификатор (Android `resource-id` / iOS
`accessibilityIdentifier`, для Flutter — `Semantics.identifier`).
Ветвления по платформе нет: слой один, различия — env и способ дампа.

## Шаг 0 — Pre-flight (первым действием, до любой другой работы)

Прочитай `docs/project-profile.md` и выбери режим строго по таблице:

| Ситуация | Действие |
|---|---|
| Паспорта `docs/project-profile.md` нет | Одной фразой: «форк не настроен, запусти /setup-fork» — и СТОП. Файлы не трогать. |
| В паспорте `Mobile: нет` или строки Mobile нет вообще | НЕ стопорись молча. Слова «в приложении / мобилка / регистрация в апе» часто означают НЕ Appium-экран, а API-слой мобильного флоу. Одной фразой: «мобилка не заявлена в паспорте. Если нужен именно нативный экран — запусти /setup-fork (идемпотентен, вопрос 7 интервью); если проверяешь бэкенд-флоу приложения (регистрация, логин) — это /api-tests». Уточни уровень (API/UI/Appium) и верни управление. |
| Запрос про API-тесты (ресурс/эндпоинт/спека) или веб-интерфейс (браузер, админка) | Одной фразой отошли к /api-tests или /frontend-tests и верни управление. |
| Запрос про починку/рефакторинг СУЩЕСТВУЮЩИХ тестов | Одной фразой: скилл генерирует новое покрытие, починка вне скоупа; верни управление. |
| Запрос — только снять дамп/идентификаторы экрана, без тестов | Помоги снять дамп (Шаг 2, включая выдачу рецептов человеку) и покажи разбор `${PLUGIN_ROOT}/bin/dump_ui_tree.py`; пайплайн тестов не запускай. |
| Иначе | Прочитай паспорт целиком, `docs/mobile.md`. Работай дальше. |

**Контракт с паспортом**: setup-fork пишет ОДНУ строку
`Mobile: да (платформа, где APK)` — больше ничего не гарантировано.
Фреймворк приложения (native/Flutter/Compose — нужен для текста блокера
Шага 3), флоу UI-логина и префикс идентификаторов (дефолт `app_`) паспорт
может не содержать: возьми из расширенной мобильной секции, если форк её
дописал, иначе спроси пользователя в Шагах 1–2 или зафиксируй допущением.
НЕ стопорись из-за их отсутствия и НЕ расширяй замороженный setup-fork.
«Флоу логина» = UI-вход в приложении (логин/пин), НЕ HTTP-авторизация.

**Оснащение машины — прогоном, а не памятью.** В этом же шаге:

```bash
preflight.py --use-marker
```

Молчит, пока на машине ничего не менялось (маркер `.preflight-ok` привязан к
хосту, не к клону — репозиторий ездит между машинами). Красное **не чинишь и
ничего не ставишь**: называешь пользователю, какой класс работы закрыт (колонка
«без неё» в выводе прогона), и продолжаешь в оставшемся
объёме — недостача идёт в отчёт. Для этого скилла критичны: Appium и его драйвер, `adb` для Android либо Xcode для iOS, `.env` с секцией устройства.
Заполнен ли `.env` — тоже из вывода прогона (строки с колонкой «Переменные»
называют пустые переменные по имени): сам `.env` и `.env.example` не читай —
доступ к ним обычно закрыт, попытки уходят в отказы.

**Автономный режим** = пользователь недоступен или явно попросил без
вопросов: вместо любого «спроси» — зафиксируй ДОПУЩЕНИЕ и продолжай;
все допущения попадут в отчёт.

**Блокер — сразу человеку, а не перебором.** Действует на любом шаге: проход
по сценарию, дамп, живой прогон. Шаг не проходит штатным способом (тап или
ввод по идентификатору), и вторая разумная попытка тоже не прошла — это
блокер. Одна быстрая проба вроде «проходит ли в этом диалоге хоть какой-то
тап» допустима; перебирать в одиночку обходы (координаты, смещения, жесты,
соседние узлы, повтор того же вызова после отказа) — нет. Остановись и спроси
человека одним сообщением: какой шаг, что пробовал, что видно (скриншот или
дамп), варианты — копать дальше, пропустить шаг с пометкой, `/keys-mobile`,
пауза. Дождись ответа. Сценарий, который идёт к красному тесту или `xfail`,
до ревью и полировки кода — тоже вопрос человеку: падающий тест сам по себе
результатом не считается. В автономном режиме спросить некого — перебора нет
и тогда: шаг пропускается с пометкой, блокер — первой строкой отчёта.

## Шаг 1 — Сценарий

Из тикета/описания выдели фичу, экран(ы) и шаги пользователя: открыть →
действие → ожидаемый результат. Вводные из запроса (имена полей, ожидаемые
тексты, id сущностей) фиксируй — не переспрашивай. Сценария нет, есть
только экран — предложи happy-path его главного действия. Уточни попутно
(если не в паспорте): платформа прогона, фреймворк приложения, флоу входа.

## Шаг 2 — Дерево экрана (развилка с выбором пользователя)

Мобильная автоматизация для большинства людей — диковинка. Объясняй как
новичку: что такое дамп («глаза» — XML-дерево элементов экрана), зачем он
(из него берутся локаторы), какие предусловия (эмулятор/устройство,
тестовый билд, Appium-сервер, `.env`). **Скопируй пользователю ПРЯМО В
ОТВЕТ** шпаргалку-таблицу «ситуация → способ» и подходящие рецепты из
секции docs/mobile.md «Как показать агенту экраны приложения — инструкция
для человека» (не только ссылку: рецепты передают коллеге без доступа к
репо). Предложи варианты ВСЕГДА, рекомендуй по ситуации:

| Ситуация | Рекомендация |
|---|---|
| Сценарий из нескольких экранов/действий, живое устройство есть | **Проход сценария**: `python ${PLUGIN_ROOT}/bin/dump_ui_tree.py --walkthrough dumps/<сценарий>` — ДЕФОЛТ для тест-кейса. Одна сессия, человек делает шаги и жмёт Enter, на выходе дампы+скриншоты по шагам и `steps.json` |
| То же + в сессии подключён appium-mcp (скажет паспорт/пользователь; сверься с доступными MCP-инструментами) | **MCP-проход**: кейс описан заранее → веди сам (жесты/ввод, дамп после каждого шага — шаги проверены исполнением); иначе человек тапает, ты снимаешь. MCP — опция, не требование |
| Пользователь просит снять САМОМУ (или автономный режим), устройство и `.env` живые (по прогону `preflight.py`), appium-mcp нет | **Проход по сценарию-файлу**: опиши шаги JSON (`tap`/`type`/`back` + `wait_for` по идентификатору) и запусти `python ${PLUGIN_ROOT}/bin/dump_ui_tree.py --walkthrough dumps/<сценарий> --script dumps/<сценарий>.json --reset-app`. Правила ниже таблицы |
| Нужен один конкретный экран | `--wait-manual 30 --raw-out screen.xml`. НЕ гонять по кругу для сценария: каждый запуск пересоздаёт сессию и перезапускает приложение |
| Устройства нет / дамп снимет коллега | Выдай рецепты (adb / curl WDA / скрипт) и попроси файл(ы); разбор — `--from-file` |

**Проход по сценарию-файлу — правила** (формат шага — шапка
`${PLUGIN_ROOT}/bin/dump_ui_tree.py`):

- **Одноразовые скрипты на драйвере не пишешь.** Не прошёл шаг — скрипт
  остановился и снял `step_NN_<имя>_FAILED.xml`: разбери этот дамп, поправь
  ФАЙЛ сценария и перезапусти проход. Идентификатора под следующий шаг в
  дампе нет — это Шаг 3, а не повод искать элемент по тексту или координатам.
  **Повторное падение в том же месте — первым действием скриншот** текущего
  экрана, а не новая гипотеза по стектрейсу: однажды два полных цикла
  «правка → пересборка → прогон» ушли на несуществующие причины, а скриншот
  сразу показал забытую заглушку стенда. Держи чек-лист известных
  предусловий стенда вместо перебора гипотез.
- **`--reset-app` на каждом запуске.** Иначе второй проход стартует с
  экрана, где закончился первый (вход, PIN, сессия переживают перезапуск), и
  половина попыток уходит на грязное состояние. Нужны `IOS_UDID`,
  `IOS_BUNDLE_ID`, `IOS_APP_PATH` (iOS) или `ANDROID_APP_PACKAGE`.
- **Проход создаёт данные на стенде** (регистрация, заявка) так же, как
  тест: что создал — в отчёт, убрать API-клиентом `src/`; нет клиента —
  явной строкой «осталось на стенде».
- **Секреты — через `text_env`**, не литералом в файле сценария. Но XML-дамп
  шага хранит текст обычного поля в `value`: секрет безопасен только в поле
  пароля, папку прохода не коммитить и не пересылать.
- **Логика прохода — не черновик модуля.** Файл сценария проверяет, какие
  экраны и идентификаторы есть; Module пишется заново по чеклисту Шага 5,
  а не переносом шагов прохода вместе с их обходными приёмами.

Из walkthrough/MCP-прохода бери ОБА артефакта: последовательность шагов
(`steps.json` — почти готовые методы Module) и идентификаторы по шагам.
Скриншоты шагов — вспомогательный контекст для матрицы, НЕ источник
локаторов (координаты/текст запрещены). БЕЗ дерева дальше не идти —
идентификаторы не выдумывать.

**Вход — не один экран.** После принятого кода или OTP приложение может вести
через обязательный гейт (создание PIN → повтор PIN → модалка биометрии →
разблокировка) и только потом пускать на главную. Последовательность экранов
после аутентификации снимается живым проходом до матрицы, а не достраивается
логикой; каждый промежуточный экран — свой Module с ожиданием по
идентификатору.

## Шаг 3 — ГЛАВНАЯ РАЗВИЛКА: в дампе нет идентификаторов

`no_keys_found: true` или нет ключей под элементы сценария → НЕ строить
локаторы по тексту/координатам/XPath. Вместо кода — отчёт-блокер:

1. Список недостающих идентификаторов: экран → элемент → предлагаемое имя
   по конвенции паспорта (`<префикс>_<экран>_<элемент>`). В список входят
   не только интерактивные элементы, но и КОНТЕЙНЕРЫ (список, область,
   форма), по которым сценарий проверяет появление/отсутствие — пройдись
   по будущим проверкам матрицы: каждой нужен свой идентификатор.
2. Что именно проставить — код ПОД ФРЕЙМВОРК ПРИЛОЖЕНИЯ из
   `docs/locator-conventions.md` (Flutter → `Semantics(identifier:)`,
   ValueKey НЕ подходит; Compose → `testTag` + `testTagsAsResourceId`;
   Android View → `android:id`; iOS → `accessibilityIdentifier`).
3. Дальше — развилка по доступу к репозиторию приложения:
   - **репозиторий есть в `docs/apps-repos.md`** (команда автотестов сама
     проставляет локаторы) → скажи одной фразой «идентификаторов нет,
     доступ к репозиторию приложения есть — это `/keys-mobile`» и верни
     управление. Промпт для чужого агента в этом случае не нужен;
   - **репозитория нет** → предложи пользователю готовый промпт для
     ИИ-агента в репозитории приложения (из locator-conventions.md,
     скопируй с подстановками).

И ОСТАНОВИСЬ — файлы слоя не создавать. Идентификаторы есть частично →
покрой что можно, остальное тем же списком в отчёт.

**Третий исход — идентификатор есть, но для ДЕЙСТВИЯ негоден.** Ключ в
дампе нашёлся, а тап по нему промахивается или ничего не делает: драйвер
жмёт центр границ узла, а узел — не сам элемент. Признаки в дампе:
границы узла в разы больше элемента на скриншоте (на всю строку, шапку,
экран — атрибуты `width`/`height` на iOS, `bounds` на Android), чужая
метка (текст соседей через `\n`), идентификатор на контейнере, а не на
кнопке. Подтверждение — действием, не рассуждением: шаг `tap` с `wait_for`
следующего экрана в проходе по сценарию-файлу падает.

**Четвёртый признак — его отсутствие.** Дамп здоровый: границы по элементу,
`accessible="true"`, метка своя; `click()` возвращается без исключения и без
таймаута — и не происходит НИЧЕГО. Такой узел отличается от рабочего только
эффектом, поэтому каждый тап проверяй результатом, который назван заранее
(следующий экран, состояние элемента, состояние на бэке через API-клиент
`src/`), а не отсутствием ошибки. Замеченный сигнал в дампе iOS —
`visible="false"` при `accessible="true"` у элементов внутри оверлея
(`OverlayPortal` на Flutter 3.35.7: опции дропдауна, тултипы, поповеры), при
том что соседние элементы экрана — `visible="true"`. Отсюда же правило:
**элементы по `visible` не фильтруй** — узел может быть `visible="false"` и
при этом присутствовать, читаться и (после правки продукта) кликаться.
Лечится это в приложении, не в тесте: перевод оверлея на
`Overlay.of(context).insert(OverlayEntry(...))` вернул и `visible="true"`, и
работающий тап.

- Такой ключ годится только для проверки ПРИСУТСТВИЯ («экран открыт»,
  «вошли») — ей и покрывай, в матрице строка помечается «присутствие;
  действие — блокер».
- Действие по координатам, по тексту или по соседнему узлу не строить.
  Нужное действие без годного узла — пропуск шага с пометкой в отчёте, а
  если без него сценарий дальше не идёт — это блокер всего сценария.
- Недостача — тем же списком, что и отсутствующие идентификаторы, с
  доказательством (размер узла против элемента, упавший шаг прохода);
  репозиторий приложения доступен → `/keys-mobile` (форма правки там).

## Шаг 4 — Матрица сценария ДО кода

Таблица: **№ | Шаг сценария | Элемент | Идентификатор | Источник
(`дамп`/`запрос`/`ДОПУЩЕНИЕ`) | Проверка**. Тексты в проверках — ключи
локализации (`assert_text`), не строки. **Выведи таблицу ЦЕЛИКОМ в ответ
ДО создания первого файла слоя** — «матрица готова» без самой таблицы не
считается. Покажи пользователю и дождись подтверждения; в автономном
режиме — та же таблица в ответ, зафиксируй допущения и продолжай.

## Шаг 5 — Код

Строго по `references/screen-checklist.md` (прочитай его) и docs/mobile.md:

1. `Appium/app_keys/<фича>_buttons.py` — класс наследует **ScreenActions**
   (НЕ BaseElements), только локаторы.
2. `Appium/Modules/<фича>_module.py` — взаимодействия,
   `Logger.log_mobile_action` на КАЖДОЕ действие; шаги из steps.json →
   методы модуля.
3. Тест в `Tests/Mobile_tests/` — сценарии и ассерты; фикстура `driver`
   инфраструктурная (уже есть), логин — фикстурой форка, предусловия
   данных — API-клиентами `src/`. Нет клиента ресурса X → предложи
   человеку сначала `qa-auto:api-clients` (только клиент и модели), после
   «да» вызови его и вернись сюда; «нет», автономный режим или оркестратор —
   строка отчёта «нужен клиент ресурса X». Предусловия через UI не городить.

Каждая строка матрицы Шага 4 → шаг теста (или явная пометка в отчёте,
почему нет).

**Ждать данные, а не локатор.** Экран под `Skeletonizer`/шиммером рендерит
плейсхолдер загрузки ТЕМ ЖЕ виджетом и с тем же идентификатором, что и
контент (внутри — текст-заглушка вроде `fake data`). Ожидание «локатор
появился» закончится на скелетоне, и следующий шаг ткнёт в пустоту.
Условие ожидания — значение из данных (текст, количество элементов,
конкретный id), а не факт присутствия узла.

## Шаг 6 — Верификация

1. `make verify` — до зелёного (лимит 5 починок; упёрся — честный отчёт,
   не бесконечный цикл).
2. Живой прогон `pytest -x -q -m mobile Tests/Mobile_tests/<Фича>/` —
   ТОЛЬКО если эмулятор доступен И пользователь просил прогон. Мобильный
   цикл обратной связи самый медленный — ЛИМИТ 5 итераций, и на КАЖДОМ
   падении собирай ВЕСЬ пакет диагностики сразу (скриншот + page_source +
   свежий дамп экрана), только потом чини. Классификация падений — по
   маршрутизатору `docs/tests.md`: баг теста → чини; расхождение с
   приложением (id переименован/экран изменился) → свежий дамп → обнови
   идентификатор → точечный перезапуск; баг приложения → блокер: стоп и
   вопрос человеку (Шаг 0, «Блокер»), `xfail` со ссылкой — только с его
   согласия. Счётчик итераций — в отчёт (0 — тоже значение).
3. **Ревью своего дифа — обязательно, до отчёта.** Зелёные verify и живой
   прогон доказывают, что тест РАБОТАЕТ, но не что он СООТВЕТСТВУЕТ
   конвенциям (паузы, перенесённые из отладочных скриптов прохода,
   проверяемый шаг в conftest, несброшенное состояние приложения проходят
   зелёными). Свой код сам не ревьюй — автор не видит своих нарушений. Спавни агента
   `qa-auto:test-reviewer` со
   скоупом = список файлов, созданных и изменённых в этом прогоне. Это шаг
   процедуры: отдельного разрешения пользователя он не требует.
   - **high и med** — чинишь в этом же прогоне; med не чинится только с
     причиной, записанной в отчёт. **low** — в отчёт.
   - После правок — `make verify`; был живой прогон — точечный перезапуск.
   - Были high → ОДИН повторный `test-reviewer` по тем же файлам. Больше
     кругов не заводи: остаток — в отчёт.
   - Находки по чужим файлам — «вне скоупа» в отчёт, не править.
   - **Под оркестратором** (тебя запустили сабагентом `/api-suite` или
     `/test-flow`, либо ты `test-fixer`) шаг пропусти: ревью у оркестратора
     отдельной фазой. В отчёте — строка «ревью — за оркестратором».

## Шаг 7 — Отчёт

Покажи:

- созданные/изменённые файлы;
- покрытие сценария: шаги матрицы → написано / xfail / требует человека;
- недостающие идентификаторы и идентификаторы, негодные для действия
  (Шаг 3, третий исход), — блокеры для разработчиков приложения
  (+ напоминание про промпт из locator-conventions.md);
- был проход по сценарию-файлу — что он создал на стенде и убрано ли;
- **«Допущения и открытые вопросы»** — обязательная секция: перенос
  КОПИЕЙ из матрицы/шагов, не пересказ; «допущений нет» — явной строкой;
- статус живого прогона (гонялся/нет и почему) и счётчик итераций Шага 6;
- итог ревью Шага 6.3: high/med/low до и после правок, число кругов,
  незакрытые находки с причиной;

Найденная в работе ловушка ПРОЕКТА (нестабильный локатор, особенность
стенда/устройства, флаки, расхождение доки с фактом) → допиши её коротко
(«сигнатура → как избегать») в секцию «Копилка ловушек проекта» в
`docs/mobile.md` или в паспорт проекта И упомяни это в отчёте.
