# Соглашения по локаторам с разработчиками приложения

Автотесты находят элементы **только по стабильным идентификаторам**
(мобилка: Android `resource-id` / iOS `accessibilityIdentifier`; веб:
атрибут `data-testid`). Экран или страница без идентификаторов — это
**блокер**: тесты на них не пишутся, вместо них разработчикам уходит список
недостающих идентификаторов (Шаг 3 скилла `/mobile-tests`, Шаг 2
`/frontend-tests`). Этот документ — контракт: что именно и как проставить.
В конце — готовые промпты для ИИ-агента в репозитории приложения (мобилка)
и фронтенда (веб).

Если доступ к репозиториям продукта есть у команды автотестов и
идентификаторы проставляет агент — правила такой правки (ветка, размер
диффа, порядок «локатор → выкат → тест») лежат в
[apps-repos.md](apps-repos.md); контракт по именам остаётся этот.

## Общие правила (любой фреймворк)

1. **Каждому интерактивному или проверяемому элементу — стабильный id**:
   кнопки, поля ввода, переключатели, плитки списков, заголовки экранов,
   тосты/снекбары, индикаторы состояния.
2. **Именование**: `snake_case`, латиница, по схеме
   `<префикс>_<экран>_<элемент>` — например `app_login_submit_button`,
   `app_tasks_create_button`. Префикс — из паспорта проекта
   (`docs/project-profile.md`, по умолчанию `app_`). Форк, где ключи уже
   заведены без префикса, его не вводит задним числом: переименование
   существующих идентификаторов ломает уже написанные тесты — паспорт в
   таком случае фиксирует «префикс не используется».
3. **Элементы списков/повторяющиеся** — стабильная база + id сущности:
   `app_task_tile_<uuid>` (uuid — идентификатор из API, не индекс позиции:
   порядок в списке меняется). Каждый элемент внутри строки (название,
   кнопки) — тоже с id сущности: `app_tasks_delete_button_<uuid>`; без него
   одно имя получат все строки сразу.
4. **Идентификаторы НЕ зависят** от локали, видимого текста, позиции на
   экране; **не меняются** между сборками; **присутствуют в release-сборке**
   (не только в debug).
5. Что тесты НЕ используют никогда (и что не спасёт вместо id): видимый
   текст (ломается локализацией), XPath по структуре (ломается любым
   рефакторингом вёрстки), координаты (ломаются размером экрана).

## Android, нативные View (XML-вёрстка)

```xml
<Button android:id="@+id/app_login_submit_button" ... />
```

В дампе UI это `resource-id="com.example.app:id/app_login_submit_button"`.
Обычно id уже есть — проверить, что они осмысленные и стабильные.

## Android, Jetpack Compose

Compose по умолчанию **не** отдаёт testTag в accessibility-дерево. Нужно два
шага:

```kotlin
// 1. На корневом composable экрана (или в теме приложения) — один раз:
Modifier.semantics { testTagsAsResourceId = true }

// 2. На каждом элементе:
Modifier.testTag("app_login_submit_button")
```

Без `testTagsAsResourceId = true` тег НЕ виден как `resource-id` — это самая
частая ошибка.

## iOS, UIKit

```swift
loginButton.accessibilityIdentifier = "app_login_submit_button"
```

## iOS, SwiftUI

```swift
Button("Войти") { ... }
    .accessibilityIdentifier("app_login_submit_button")
```

**Не путать** с `accessibilityLabel` — label читается VoiceOver и
локализуется, для тестов нужен именно `accessibilityIdentifier`.

## Flutter

```dart
// у виджета своя семантика (кнопки Material, IconButton, FAB) — ВНУТРЬ, на слот
ElevatedButton(
  onPressed: submit,
  child: Semantics(
    identifier: 'app_login_submit_button',
    child: const Text('Войти'),
  ),
)

// своей семантики нет (InkWell, GestureDetector, ListTile, Checkbox) — снаружи
Semantics(
  identifier: 'app_tasks_row_42',
  child: InkWell(onTap: open, child: row),
)
```

- Требуется **Flutter ≥ 3.19**: `identifier` пробрасывается платформе как
  `resource-id` (Android) / `accessibilityIdentifier` (iOS).
- **`ValueKey` / `Key` НЕ работают**: это ключи виджет-дерева Flutter,
  нативным драйверам (UiAutomator2/XCUITest) они не видны. Существующие
  ValueKey в коде не считаются выполнением контракта.
- **Кнопку снаружи не оборачивать.** Material-кнопки открывают собственный
  узел семантики: `Semantics` поверх даёт отдельный пустой узел (найти можно,
  нажать нельзя), а `MergeSemantics` поверх сливает всё поддерево — соседние
  кнопки становятся одной, вложенные идентификаторы пропадают.
  Идентификатор ставится на содержимое `child`/`icon`.
- Не оборачивать целевой элемент в `ExcludeSemantics` — и не ставить
  идентификатор в поддерево под ним: он пропадёт.
- `MergeSemantics` — только над одним интерактивным элементом, у которого нет
  слота для идентификатора, и без чужих идентификаторов внутри; результат
  проверять дампом.
- Тосты/снекбары и прочие временные элементы тоже получают Semantics —
  тесты проверяют их появление.
- **Оверлеи (выпадающие списки, тултипы, поповеры) — через
  `Overlay.of(context).insert(OverlayEntry(...))`, а не `OverlayPortal`.**
  Содержимое `OverlayPortal` на Flutter 3.35.7 приходит в нативное дерево с
  `visible="false"` (ветка `_SemanticsGeometry.computeChildGeometry` в
  `rendering/object.dart`): элемент видно в дампе, а тап драйвера до
  приложения не доходит — молча, без ошибки. Проверено на опциях дропдауна:
  после перевода на `OverlayEntry` те же опции стали `visible="true"`, и тап
  начал менять данные.
- **Виджет, который монтируется на каждую строку списка, обязан получать
  идентификатор ОТ ДАННЫХ строки.** Параметр, захардкоженный константой в
  месте вызова внутри `itemBuilder`, даёт один и тот же идентификатор всем
  видимым строкам сразу: тест адресует первую попавшуюся, а не нужную.
- **Сторонний пакет может вырезать идентификатор, поставленный вашим
  билдером.** Пример: `table_calendar` 3.2.0 оборачивает результат любого
  `CalendarBuilders`-билдера в `Semantics(excludeSemantics: true)` внутри
  `CellContent.build()`. Если элемент рисует чужой пакет, идентификатор
  проверяется виджет-тестом до того, как считать контракт выполненным.
- В release-сборке Semantics-дерево строится, когда подключён
  accessibility-клиент (Appium/uiautomator включают его сами). Проверять
  идентификаторы дампом, снятым через Appium/adb, а не «глазами» в
  приложении — иначе легко сделать ложный вывод «Semantics не работает».

## Веб: React / Vue / Angular / любой HTML

```jsx
<button data-testid="admin_users_create_button">Создать</button>
```

- **Атрибут — именно `data-testid`.** Его по умолчанию ищут
  дамп страницы и `get_by_test_id()` в playwright-ветке; свой
  вариант (`data-qa`, `data-test`) допустим только если он записан в
  паспорт проекта.
- **Имена — snake_case, как в мобилке**, схема
  `<префикс>_<страница>_<элемент>`: `admin_users_create_button`,
  `admin_login_email_field`. Единая схема на всех слоях — чтобы имя
  локатора читалось одинаково в мобильном и веб-тесте (kebab-case из
  привычек React-экосистемы здесь сознательно не используется).
- **Списки и таблицы** — стабильная база + идентификатор сущности из API:
  `admin_user_row_<uuid>`, и так же каждый элемент внутри строки:
  `admin_users_delete_button_<uuid>`. Индекс позиции нельзя: сортировка и
  пагинация меняют порядок.
- **Атрибут — на сам интерактивный элемент**, не на обёртку-`div`: клик по
  контейнеру может не дойти до кнопки, а `disabled`-состояние проверяется
  на самом элементе.
- **Проверяемые состояния тоже получают testid**: тосты и снекбары,
  сообщения валидации, пустое состояние списка, индикатор загрузки,
  строки итогов. Тест проверяет не только клики, но и результат.
- **testid должен пережить прод-сборку.** Некоторые пресеты
  (`babel-plugin-react-remove-properties`, `vite` с плагином чистки
  data-атрибутов) вырезают их в проде — тогда локатор есть в исходниках и
  отсутствует на стенде. Проверяется дампом со стенда, не чтением кода.
- **Не годится вместо testid**: видимый текст (ломается локализацией и
  правкой копирайта), CSS-классы вроде `css-1x2y3z` (генерируются
  сборкой, меняются от билда к билду), XPath по структуре (ломается любым
  рефакторингом вёрстки), `id` от библиотеки компонентов (часто
  автогенерируемый и непостоянный).
- **Осмысленные ARIA-роли и `<label for>` — не замена, но приветствуются**:
  по ним playwright-ветка ищет элементы, у которых testid ещё нет; есть
  testid — тест ищет по нему.

## Как проверить, что идентификаторы видны

Со стороны приложения (без тестового фреймворка):

<!-- слой: mobile -->
- Android: открыть экран на эмуляторе →
  `adb exec-out uiautomator dump /dev/tty` → искать свои id в атрибутах
  `resource-id`.
- iOS: через Appium/WebDriverAgent `page_source` (атрибут `name`) — см.
  `docs/mobile.md`; либо Accessibility Inspector в Xcode (поле Identifier).
<!-- /слой -->
<!-- слой: frontend -->

- Веб: открыть страницу в браузере → DevTools → в консоли
  `$$('[data-testid]').length` и
  `[...$$('[data-testid]')].map(e => e.dataset.testid)` — проверять на
  **стенде**, а не на локальном dev-сервере (прод-сборка могла вырезать
  атрибуты).
<!-- /слой -->

Со стороны автотестов — скрипт дампа своего слоя:
<!-- слой: mobile -->
`dump_ui_tree.py` (мобилка, см. `docs/mobile.md`);
<!-- /слой -->
<!-- слой: selenium -->
`dump_dom.py` (веб, см. `docs/frontend.md`);
<!-- /слой -->
<!-- слой: playwright -->
скрипт на playwright (веб, `/frontend-tests`, Шаг 2);
<!-- /слой -->
в сводке дампа есть счётчик «с testid» и «хрупких».

## Готовый промпт для ИИ-агента в репозитории МОБИЛЬНОГО приложения

Скопируйте блок целиком, подставьте значения в `<...>` и отдайте ИИ-агенту
(Claude Code и т.п.), запущенному в репозитории приложения:

```text
Задача: добавить стабильные тестовые идентификаторы для UI-автотестов
(Appium, UiAutomator2/XCUITest). Идентификаторы должны попадать в
accessibility-дерево платформы: resource-id на Android,
accessibilityIdentifier на iOS.

Область: экраны <СПИСОК ЭКРАНОВ, например: Login, Tasks, Task creation form>.
Если список не задан — все экраны с интерактивными элементами.

Каких элементов это касается: кнопки, поля ввода, переключатели,
элементы списков, заголовки экранов, тосты/снекбары, индикаторы
загрузки/пустого состояния.

Конвенция имён: snake_case, латиница, схема <префикс>_<экран>_<элемент>,
префикс "<ПРЕФИКС, по умолчанию app_>". Примеры: app_login_submit_button,
app_tasks_create_button, app_login_email_field. Повторяющиеся элементы
списков: стабильная база + идентификатор сущности из данных, например
app_task_tile_<id задачи>, и так же каждый элемент внутри строки
(app_tasks_delete_button_<id задачи>); индекс позиции использовать нельзя.

Как проставлять — строго по фреймворку:
- Flutter: Semantics(identifier: '<имя>', child: ...). Требуется
  Flutter >= 3.19. ВАЖНО: ValueKey/Key НЕ подходят — они не видны
  нативным драйверам; существующие ValueKey не заменяют задачу.
  Кнопки Material (ElevatedButton, TextButton, IconButton,
  FloatingActionButton) снаружи НЕ оборачивать: Semantics ставится на их
  child/icon. Снаружи получится пустой узел (найти можно, нажать нельзя),
  а MergeSemantics поверх сольёт соседние элементы и вложенные
  идентификаторы в один узел. InkWell, GestureDetector, ListTile,
  Checkbox — оборачивать снаружи. Не прятать элемент под ExcludeSemantics.
- Jetpack Compose: Modifier.testTag("<имя>") на элементе И
  Modifier.semantics { testTagsAsResourceId = true } на корневом
  composable экрана (без второго testTag не попадёт в resource-id).
- Android View/XML: android:id="@+id/<имя>" (проверить осмысленность
  существующих id, недостающие добавить).
- UIKit: view.accessibilityIdentifier = "<имя>".
- SwiftUI: .accessibilityIdentifier("<имя>") (НЕ accessibilityLabel).

Требования:
- Идентификаторы должны присутствовать и в release-сборке.
- Не менять существующие работающие идентификаторы без необходимости.
- Никакого попутного рефакторинга — только добавление идентификаторов.
- Идентификаторы не зависят от локали и текста на экране.

Результат: (1) изменения в коде; (2) итоговая таблица
"экран -> элемент -> идентификатор" в ответе, чтобы команда автотестов
перенесла её в паспорт проекта.
```

## Готовый промпт для ИИ-агента в репозитории ФРОНТЕНДА

Тот же принцип, для веба. Подставьте значения в `<...>`:

```text
Задача: добавить стабильные тестовые идентификаторы для UI-автотестов
(Selenium/Playwright). Идентификатор — HTML-атрибут data-testid.

Область: страницы <СПИСОК СТРАНИЦ или маршрутов, например: /login,
/users, модалка создания пользователя>.

Каких элементов это касается: кнопки, поля ввода, селекты, чекбоксы,
ссылки навигации, строки таблиц и карточки списков, заголовки страниц,
тосты/снекбары, сообщения валидации, пустое состояние списка,
индикаторы загрузки.

Конвенция имён: snake_case, латиница, схема
<префикс>_<страница>_<элемент>, префикс "<ПРЕФИКС, например admin_>".
Примеры: admin_users_create_button, admin_login_email_field,
admin_users_empty_state. Строки списков: стабильная база +
идентификатор сущности из API, например admin_user_row_<uuid>, и так же
каждый элемент внутри строки (admin_users_delete_button_<uuid>);
индекс позиции использовать нельзя.

Как проставлять:
- Атрибут data-testid ставится на САМ интерактивный элемент (button,
  input, a), не на обёртку-div.
- Если элемент рендерит библиотека компонентов, пробросить data-testid
  через её пропсы до нативного DOM-узла и проверить в DevTools, что
  атрибут реально оказался в разметке.
- Условно отображаемые элементы (тосты, ошибки валидации, пустое
  состояние) тоже получают data-testid.

Требования:
- Атрибуты должны присутствовать в ПРОД-сборке: если в проекте
  подключён плагин удаления data-атрибутов
  (babel-plugin-react-remove-properties и аналоги) — сообщить об этом,
  НЕ отключать его самостоятельно.
- Никакого попутного рефакторинга, переименований, переформатирования
  и правки логики — только добавление атрибутов.
- Не менять существующие data-testid без необходимости: на них уже
  могут быть написаны тесты.
- Идентификаторы не зависят от текста, локали и позиции элемента.

Результат: (1) изменения в коде; (2) итоговая таблица
"страница -> элемент -> data-testid" в ответе, чтобы команда
автотестов перенесла её в page object.
```
