# Как добавить новый API-домен

Рецепт создания клиента и тестов для нового ресурса (далее в примерах —
ресурс `projects`). Эталон каждого файла — соответствующий `example_*`:
копируй и адаптируй, сами example-файлы не трогай.

---

## Шаг 0 — Что спросить у человека ДО написания кода

Семантику реального API из шаблона узнать нельзя. Не гадай — спроси
(или возьми из OpenAPI-спеки, если она дана):

1. **Путь эндпоинта**: `/api/projects`? `/api/v2/projects`?
2. **Тело запроса create/update**: обязательные и опциональные поля, вложенность.
3. **Коды ответов**: create — 200 или 201? update/delete — 204 или 200?
   delete несуществующего — 404 или идемпотентный 204?
4. **Конверт списка**: `GET /projects` возвращает массив напрямую или
   `{"data": [...], "total": ...}`? (в example-тесте стоит защитная догадка
   `response.get('data', response)` — замени на реальную структуру!)
5. **Роль доступа**: под каким токеном дергать эндпоинты? Имя роли должно
   совпадать с ключом, который фикстура авторизации кладёт в
   `HttpClient.access_folder` (см. Tests/conftest.py).

Если ответов нет — построй план тестов, пометь допущения и подтверди у
человека, прежде чем фиксировать код.

## Шаг 1 — Чеклист файлов (ничего не забыть!)

Для домена `projects` создаются **все** эти файлы:

```
src/projects/__init__.py                              # пустой
src/projects/projects.py                              # API-клиент
src/projects/models.py                                # pydantic-модели ответов
Tests/Regression_tests/projects/__init__.py           # пустой
Tests/Regression_tests/projects/conftest.py           # фикстуры домена ← ЧАСТО ЗАБЫВАЮТ
Tests/Regression_tests/projects/test_projects.py      # регрессия
```

Если нужен smoke — добавь тесты в существующую smoke-директорию фичи или
создай новую по образцу `Tests/Smoke_tests/ExampleFeature/` (тоже с conftest!).

Без соседнего `conftest.py` фикстуры (`create_project`, `project_cleaner`)
не разрешатся — тесты упадут на коллекции. pytest ищет фикстуры только в
conftest.py той же директории и выше.

## Шаг 2 — Клиент (эталон: `src/example_resource/example_resource.py`)

```bash
cp -r src/example_resource src/projects
mv src/projects/example_resource.py src/projects/projects.py
```

Правила клиента (все видны в эталоне):

- **Один класс на ресурс, только `@staticmethod`** — состояния нет,
  токены живут в `HttpClient.access_folder`.
- **`status_code=` в каждом методе** с дефолтом = успешный код.
  Негативный тест выглядит так: `Projects.get(999999, status_code=404)`.
  При ожидаемой ошибке (>=400) метод возвращает `None` — результат
  в негативных тестах НЕ разыменовывать.
- **`**kwargs` + `deep_merge(default_body, kwargs)`** — точечное
  переопределение полей тела: `Projects.create(name="x", ownerId=5)`.
  Вложенные словари и списки словарей поддерживаются (см. докстринг
  `src/deep_merge_json.py`).
- **`access="<роль>"`** — имя токена из access_folder. Не передавай
  токен руками и не лови ошибку отсутствия токена — чини фикстуру.
- **Query-параметры — только через `query_params=` (dict)** у
  `HttpClient.get` — requests сам кодирует значения. Query-строку,
  собранную руками через f-строки, сломает первый же `search` с пробелом
  или кириллицей.
- **Ответы парсятся в pydantic-модели** из `models.py` домена (см. секцию
  «Модели ответов (pydantic)» ниже); тесты работают с атрибутами
  (`resource.name`), а не с ключами dict.
- Возврат: create → id, get → модель, get_list → модель-конверт или
  список моделей, update/delete → None.
- Докстринги на русском.

### Если сервисов (спек) больше одного — src/<сервис>/<домен>/

Домены разных сервисов одного продукта часто пересекаются по именам
тегов (у клиентского и админского API один и тот же ресурс). Плоская
раскладка `src/<домен>/` в этом случае — гарантированная коллизия имён
пакетов и рефакторинг задним числом. Правило: **если в паспорте больше
одной спеки — клиенты сразу раскладываются по подпакету сервиса**
`src/<сервис>/<домен>/` (внутри — та же пара файлов и тот же паттерн).
Общие модули (`http_methods.py`, `auth.py`, `db_config.py`, ...) остаются
на верхнем уровне `src/` — у них сервиса нет. При одном сервисе плоская
раскладка допустима.

## Шаг 3 — conftest домена (эталон: `Tests/Regression_tests/example_resource/conftest.py`)

Два стандартных паттерна фикстур:

```python
from src.teardown_utils import report_teardown_failure


@pytest.fixture()
def create_project():
    """Создаёт проект до теста, возвращает его id, удаляет после."""
    project_id = Projects.create(name=generate_name("project"))
    yield project_id
    try:
        Projects.delete(project_id)
    except Exception as e:
        report_teardown_failure(f"проект {project_id} не удалён: {e}")


@pytest.fixture()
def project_cleaner():
    """Собирает id проектов, созданных прямо в тесте, удаляет в teardown."""
    created_ids = []
    yield created_ids
    for project_id in created_ids:
        try:
            Projects.delete(project_id)
        except Exception as e:
            report_teardown_failure(f"проект {project_id} не удалён: {e}")
```

- Teardown всегда терпим к ошибкам: тест удаления сам удалил ресурс —
  повторное удаление не должно ронять прогон. Отказ уборки — через
  `report_teardown_failure` (`src/teardown_utils.py`), не `print`: pytest
  выбрасывает stdout прошедших тестов, и неудалённый ресурс становится
  невидимым. Функция пишет в лог прогона и в сводку warnings pytest, а
  «ресурса уже нет» (404) не шумит.
- Тест, который сам создаёт данные, обязан регистрировать их в cleaner:
  `project_cleaner.append(project_id)`.

## Модели ответов (pydantic) — базовая конвенция

Ответы API-клиентов парсятся в pydantic-модели, а не возвращаются сырым
`dict`: форма ответа (типы полей, обязательность) проверяется уже при
парсинге, тесты берут данные через атрибуты (`resource.name`) и оставляют
себе только содержательные assert. Эталон пары клиент+модели —
`src/example_resource/` (`example_resource.py` + `models.py`). Правила:

- Рядом с клиентом домена — второй файл `models.py`: pydantic
  `BaseModel` на каждую схему ответа, которую клиент отдаёт вызывающему коду.
- **Имена полей — как в спеке** (обычно camelCase), без перевода в
  snake_case: модель обязана совпадать с JSON 1-в-1, иначе парсинг молча
  теряет данные.
- **Тело запроса остаётся dict** (`default_body` + `**kwargs` +
  `deep_merge`) — моделей на запросы не заводят.
- Методы возвращают `Model.model_validate(data)`; списки —
  `[Model.model_validate(x) for x in data]`; при ожидаемой ошибке
  (`status_code >= 400`) — по-прежнему `None`, причём **ранним return ДО
  парсинга**: JSON-тело ошибки — тоже dict, проверка `isinstance(data,
  dict)` его не отсеет, и `model_validate` уронит негативный тест
  ValidationError'ом вместо None.
- Формы, повторяющиеся как конвенция самого API (ответ create `{"id": ...}`,
  конверт пагинации, пара токенов), живут в `src/common_models.py`, который
  домены ИМПОРТИРУЮТ — единственное исключение из правила «доменные пакеты
  самодостаточны». Заготовки в нём (`ResponseId`, `PageResult[T]`,
  `TokensPair`) форк правит под свой API и дополняет своими общими формами,
  когда одна схема начинает повторяться в нескольких доменах.
- Enum-поля спеки типизируются как `str` — фиксируем наличие и тип поля,
  Python-`Enum` на каждый спековый enum не заводим.
- Имя пакета домена не должно совпадать с используемой библиотекой
  (тег `requests` → файл `requests_<суффикс>.py`, не `requests.py`).
- **Ловушка read-modify-write в `update()`**: `existing.model_dump()`
  кладёт в тело PUT и `id`, и все `None` Optional-полей — реальный API
  может это отвергнуть. Реши явно, что исключать
  (`model_dump(exclude_none=True)`, явный список полей), и проверь на
  живом стенде, а не предполагай. В эталоне стоит `exclude_none=True` —
  это стартовое решение, не истина для любого API.

## Шаг 5 — Верификация (без живого стенда)

```bash
make verify        # компиляция + коллекция одной командой
# или по отдельности:
python3 -m compileall -q src Tests                     # синтаксис
.venv/bin/python -m pytest --collect-only -q           # импорты + фикстуры
.venv/bin/python -m pytest --collect-only -q -m regression   # маркер работает
```

Коллекция должна пройти **без .env**. Если упала — читай ошибку: чаще всего
это забытый conftest, опечатка в импорте или фикстура вне зоны видимости.
Прогон против стенда возможен только в форке с настроенным .env.

**Клиентский слой отдельно сверяется со спекой механически.** `compileall`
видит только синтаксис: вызов `HttpClient` без обязательного аргумента,
тип в аннотации, который никто не написал, модель ответа не от той схемы,
потерянные query-параметры — всё это проходит мимо него. Перед словом
«готово»:

```bash
.venv/bin/python "$(command -v api_client_check.py)" --spec specs/<спека> --package src/<сервис>
```

Скрипт импортирует каждый модуль клиента и сверяет со спекой пути, методы,
коды, query-параметры, тела запросов и поля моделей; ошибки (exit code 1)
означают, что слой не готов, предупреждения — что стоит посмотреть.

**Полнота покрытия спеки — только механически, не пересчётом руками.**
Когда клиенты пишутся «на все домены спеки», перед словом «готово»:

```bash
coverage_check.py --spec specs/<спека>.json --package src/<сервис>
```

Скрипт сравнивает теги спеки с доменными пакетами и падает, если у тега
нет клиента. Сознательно не покрываемые теги — через `--ignore <тег>`,
каждый такой ignore фиксируй в паспорте.

## Частые ошибки

| Ошибка | Как правильно |
|---|---|
| Скопировал тест, забыл conftest домена | Чеклист из Шага 1 — все 5 файлов |
| `assert Projects.get(id, status_code=404)['id']` | Негативный вызов возвращает None — не разыменовывать |
| Оставил `response.get('data', response)` не глядя | Уточнить реальный конверт пагинации (Шаг 0.4) |
| Взял коды 200/204 из эталона как истину | Сверить с реальным API (Шаг 0.3) |
| Придумал имя роли `access="service"` | Имена ролей — только те, что кладёт фикстура авторизации |
| Захардкодил URL/креды в клиенте | Только config.py / .env |
| Собрал query-строку f-строкой | `HttpClient.get(url, query_params={...})` — requests кодирует сам |
| «Все домены покрыты» посчитал руками | `coverage_check.py` — сверка тегов спеки с пакетами |
