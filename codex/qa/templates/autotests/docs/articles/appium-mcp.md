# Appium MCP: живое устройство как глаза агента

Официальный MCP-сервер команды Appium даёт AI-ассистенту (Claude Code)
прямой доступ к живому эмулятору/устройству: page source, поиск элементов,
скриншоты, жесты. Для тестировщика это значит: агент может САМ осмотреть
экран приложения и проверить локатор до того, как тот попадёт в код, — без
ручного снятия дампов.

Статья — практическая выжимка оценки сервера (v1.87.4, июль 2026; полная
оценка с таблицей всех 31 тулов — в истории git,
`APPIUM_MCP_ASSESSMENT.md`). Как MCP встраивается в процесс написания
мобильных тестов этого шаблона — [../mobile.md](../mobile.md), секции
«appium-mcp» и «Как показать агенту экраны приложения».

---

## Что это

| Параметр | Значение |
|---|---|
| Пакет | npm **`appium-mcp`** (НЕ `@appium/mcp` — такого нет) |
| Репозиторий | https://github.com/appium/appium-mcp (org appium — официальный) |
| Лицензия | Apache-2.0 |
| Транспорт | stdio (FastMCP), Node.js ≥ 22 формально (на 20 работает с EBADENGINE-предупреждением) |
| Драйверы | UiAutomator2 + XCUITest + WDA **встроены** — отдельный Appium-сервер для локальных сессий не нужен |

Релизится почти ежедневно (200+ релизов) — **версию пиновать**, `@latest`
означает, что набор и схемы тулов могут поменяться под ногами.

## Подключение к Claude Code

```bash
claude mcp add appium-mcp --env ANDROID_HOME="$ANDROID_HOME" \
    --env NO_UI=true -- npx -y appium-mcp@1.87.4
```

- `ANDROID_HOME` обязателен для Android; для iOS нужен Xcode (prebuilt WDA
  сервер скачает сам через `prepare_ios_simulator`).
- **`NO_UI=true` — ставить всегда**: токен-экономные ответы (болтливость
  признана мейнтейнерами, issue #452 «Token compression»).
- Первый запуск `npx` долгий: тянет оба драйвера и WDA (~сотни МБ) —
  в CI кэшировать или ставить заранее.

## Что реально полезно (ядро)

**Сессия и устройство:** `select_device` → `appium_session_management`
(create/attach; поддерживает `remoteServerUrl` для внешнего
Appium-сервера) → для iOS `prepare_ios_simulator` (бут симулятора +
установка WDA — снимает главную боль XCUITest-настройки) →
`appium_app_lifecycle` (установить билд, открыть экран deep link'ом).

**Инспекция (ради чего всё):**

| Тул | Зачем тестировщику |
|---|---|
| `appium_get_page_source` | XML-дерево текущего экрана — главный источник идентификаторов; Flutter Semantics видны как accessibility id |
| `appium_find_element` | проверить локатор ДО того, как он попадёт в app_keys |
| `generate_locators` | готовые кандидаты локаторов для всех интерактивных элементов экрана |
| `appium_get_element_attribute` / `appium_get_text` | сверить состояние/текст — будущие ассерты теста |
| `appium_screenshot` | скриншот: Claude мультимодален и читает его сам |
| `appium_context` | переключение NATIVE_APP / WEBVIEW для гибридных экранов |

**Навигация до целевого экрана:** `appium_gesture` (tap, swipe,
scroll_to_element, back), `appium_set_value` (ввод в формы/логин),
`appium_alert` (системные алерты).

Отдельно на заметку (не ядро, но пригодится вручную):
`appium_screen_recording` — MP4-запись прогона для разбора флаки-тестов;
`attach` в session_management — подключение к сессии, которую уже держит
запущенный pytest (отладка).

## Что НЕ используем и почему

- **`appium_generate_tests`** — кодоген. Генерирует generic-код; в этом
  шаблоне конвенции свои (app_keys на ScreenActions / Modules / фикстуры /
  `wait_until`), тесты пишет скилл `/mobile-tests`.
- **`appium_ai`** (vision-поиск элемента, opt-in через
  `AI_VISION_ENABLED`) — требует внешний VLM-ключ (DashScope/Google;
  Anthropic-провайдера нет). Не нужно: Claude сам мультимодален —
  `appium_screenshot` + чтение картинки покрывает тот же кейс без второго
  API-ключа.
- **`appium_documentation_query`** — отдельная установка доков; знания
  Appium у модели и так есть.
- Периферия (`clipboard`, `file`, `device_control`, `device_info`, сырые
  W3C Actions) — не про написание тестов.

## Грабли (проверено локальной пробой)

1. Сервер **не завершается по EOF stdin** — висит «Waiting for client
   connections...». Claude Code управляет жизненным циклом сам, но в
   своих скриптах нужен явный kill (на macOS нет `timeout` из коробки).
2. Без устройства сервер поднимается и отвечает на `tools/list`, но все
   содержательные тулы бесполезны: `select_device` вернёт пустой список,
   создание сессии упадёт. Живой эмулятор — обязательное предусловие.
3. Page source большого экрана и `generate_locators` токеноёмки даже с
   `NO_UI=true` — для гигантских экранов дампы могут забивать контекст.
4. **Flutter:** отдельного Flutter-драйвера в бандле нет — работа идёт
   через UiAutomator2/XCUITest, элементы видны только через проставленные
   `Semantics.identifier`. Экран без них «слеп» и для page source, и для
   generate_locators — это блокер разработчикам
   ([../locator-conventions.md](../locator-conventions.md)), MCP его не
   обходит.
5. У проекта нет CI-тестов (issue #379) + ежедневные релизы — регрессии
   возможны; пин версии и периодическая ревизия обязательны.

## Когда MCP, а когда скрипт

Базовый путь шаблона работает БЕЗ MCP: `dump_ui_tree.py`
(`--walkthrough`) снимает те же дампы и скриншоты по шагам сценария.

| Ситуация | Что брать |
|---|---|
| Интерактивная инспекция: жест → скриншот → page source в диалоге с агентом | **MCP** («агент за рулём» — см. рецепт Б в [../mobile.md](../mobile.md)) |
| Подготовка iOS-симулятора с WDA | **MCP** (`prepare_ios_simulator`) |
| Разовый дамп экранов, окружение без node/npx, CI | **dump_ui_tree.py** |
| Слабый канал/лимиты токенов | **dump_ui_tree.py** (дампы — файлами, агент читает выборочно) |

Правило шаблона то же, что и у фронтенда: MCP используется, если подключён
и доступен, иначе — скрипт; результат один — локаторы только с живого
экрана, не выдуманные.
