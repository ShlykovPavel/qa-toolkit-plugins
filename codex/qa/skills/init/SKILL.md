# `/qa:init` — QA-проект из пустой папки

Запускается в папке будущего **корня**. Корень — git-репо проекта и точка входа: база знаний и
автотесты лежат в нём папками без своих `.git`, агент работает из него, пуш один (решение 2026-09-29).
В корне человек уже поставил ядро `qa` на эту папку (`claude plugin install qa@qa-toolkit --scope
project`); корень может быть и склонированным с GitHub репо — README, лицензия и свой `.gitignore` в нём
не мешают, его git и берётся. `apply` делает `git init` в корне (если его ещё нет) и кладёт туда карту
проекта `CLAUDE.md` (что где лежит, куда за чем, кого звать), `.gitignore` (в свой — дописывает
недостающие строки) и в `.claude/settings.json` — каталог, плагины и разрешения автотестов. Рядом с
принятым репо со своей историей (приём ниже) git остаётся в каждой папке. Где git — поле `git` в выводе
`scan` и `apply`: `root` — один git в корне, `repos` — свой в каждой папке; по нему — что обещаешь в
плане, где ставишь плагины и коммитишь.
Механику делает скрипт `${PLUGIN_ROOT}/bin/qa-init.py` (зови по имени, он в PATH), решения и тексты — ты.

**Правила на весь заход:**
- Файлы пишутся только после «да» на план (шаг 2). До него — только чтение и вопросы.
- Чужое не перезаписываешь, ничего не удаляешь. Секретов не читаешь и не просишь: пароли и токены
  человек вписывает сам в `.env`.
- В систему ничего не ставишь, удалённых репо без отдельного «да» не создаёшь, не пушишь.
- Коммит — только тот, что называет шаг этого скилла, и только после «да» человека на этот шаг (план,
  «подтверждаю», «записываю?», «Правлю?»); своих коммитов сверх названных не делаешь. Пуш — только по
  отдельному «да» на показанную команду (шаг 7).
- Каждое «да» — прямой ответ человека в этом заходе, а не вывод из молчания.
- Файлы плагина, на которые ссылается скилл, открывай по пути как написан — он полный, искать
  по диску не нужно.
- Всё, что видит человек, — на его языке, включая короткие реплики между командами. Человек пока не
  написал ни слова текстом (только `/qa:init` и клики по формам) — говори на языке этого скилла,
  по-русски (полигоны `init-7`, `init-9`: без его текста реплики уходили в английский).

## Шаг 0 — что за папка

1. `${PLUGIN_ROOT}/bin/qa-init.py scan` в корне. `git: conflict` — корень уже git, а в нём папка со своим `.git`: покажи
   `git_problem` как есть одним сообщением и закончи — склейку истории человек делает руками. Иначе — по
   `state`:
   - `empty` — дальше, к шагу 0.2.
   - `project` — это уже QA-проект: не init, а раздел «Готовый проект» ниже.
   - `inside-repo` — запустили изнутри репо проекта. Одним сообщением: что за репо (продукт, роль) и
     что корень проекта — `root_hint`; `/qa:init` запускается там (`cd <root_hint> && claude`). Здесь
     ничего не делаешь, заход кончается.
   - `adopt` — в корне лежит наш старый репо без маркера, по `role` в `found`: `kb` — раздел «Приём
     готового ручника» ниже, `autotests` — «Приём готовых автотестов» (шаг 0.2 — и для них).
   - `unmarked-repo` — запустили изнутри нашего старого репо. Одним сообщением: что узнал (`repo`) и что
     принимает его `/qa:init` из папки уровнем выше — `root_hint`: она станет корнем проекта
     (`cd <root_hint>`, там `claude plugin install qa@qa-toolkit --scope project`, `claude`, `/qa:init`).
     Лежит там чужое — лучше новая папка-корень, а репо переложить или склонировать в неё. Здесь
     ничего не делаешь, заход кончается.
   - `occupied` — одним сообщением покажи, что нашёл, и скажи прямо: сейчас `/qa:init` умеет пустую
     папку, готовый QA-проект и наши старые ручник и автотесты; приём чужих репо, вики и коллекций —
     позже.
     Предложи новую пустую папку рядом. На этом заход кончается.
2. Проверь: `git config user.name` и `user.email` заданы (иначе коммиты шага 3 не пройдут — скажи
   человеку, какие две команды выполнить). В списке каталогов машины (`claude plugin marketplace
   list`) найди `qa-toolkit` и запомни его источник — он идёт строкой в план (шаг 2); не спрашиваешь.

## Шаг 1 — интервью

Спрашиваешь **формами с выбором** (вопросник, где человек кликает вариант), а не простынёй текста —
так человеку удобно отвечать. Формы готовы — раздел «Формы» `${PLUGIN_ROOT}/skills/init/references/interview.md`: задавай их
по порядку как есть, подставляя только значения в `<…>`; своих вариантов не добавляй. Поле «другое»
форма добавляет сама — вариант, который отсылает в него («укажу в „другое“», «поправлю сам»), не
давай: клик по нему теряет ответ. Формы нет в среде — одно сообщение теми же вопросами.

Что видно из шага 0 — не спрашивай. «Не знаю» — нормальный ответ: пишется как `— решим позже`.
Исключение — форма «Границы»: без неё плана нет, дожми отдельным вопросом.

Авторизацию, роли, БД и конвенции API **не спрашивай** — их спрашивает `/qa-auto:setup-fork` после
init и сразу пишет по ним код (шаг 7).

## Шаг 2 — план → «да»

Одним сообщением, три части:

1. **Создаю:** корень → `<продукт>-kb/`, `<продукт>-autotests/` (или имена из ответа) — по `git` из
   `scan`: `root` — папками одного git в корне, пуш один (корень уже git — «беру его git»); `repos` —
   каждой папке свой git; в корне — карта `CLAUDE.md` и `.gitignore` (своя карта — не трогаю, в свой
   `.gitignore` — дописываю недостающие строки);
   слои автотестов и библиотека фронта; источник каталога; плагины — в корень: `qa`, `qa-manual`,
   `qa-auto` (агент работает оттуда); коммиты — «шаблон как есть» сразу после раскладки и «паспорт» после
   твоего «подтверждаю».
2. **Заполняю из ответов:** по таблице «куда пишется» из `${PLUGIN_ROOT}/skills/init/references/interview.md` — какие файлы и
   какие места в них.
3. **Оставляю на потом:** всё с пометкой `— решим позже`, настройку автотестов (`setup-fork`), первый
   ингест, удалённый репо и пуш (если человек их хочет — отдельное «да» в шаге 7).

Ждёшь «да». Правка — новый план целиком, снова «да».

## Шаг 3 — раскладка и плагины

1. Собери план для скрипта в `plan.json` в корне (формат — докстринг `${PLUGIN_ROOT}/bin/qa-init.py`: `product`, `title`,
   `catalog`, `repos` со слоями) и выполни `${PLUGIN_ROOT}/bin/qa-init.py apply plan.json`. Код 2 — план не принят и
   ничего не записано: покажи причину, поправь, вернись к шагу 2. `root_kept` в выводе — свои файлы
   корня, которые `apply` не тронул: строками в отчёт как есть.
2. Плагины — командами из `${PLUGIN_ROOT}/bin/qa-init.py verify` в корне (при `git: root` он просит их только в корень);
   список «что куда» сам не собирай и автоподключению не доверяй. Каждая строка «включён, но не установлен …» кончается готовой командой
   `cd <папка> && claude plugin install <плагин>@qa-toolkit --scope project` — выполни её как есть, по
   одной, потом `verify` снова, пока таких строк нет. Прочие его проблемы на этом шаге — дело следующих
   шагов.
3. Установка переписывает `.claude/settings.json` папки по-своему — зафиксируй это в манифесте:
   `${PLUGIN_ROOT}/bin/qa-init.py filled <репо> .claude/settings.json` для каждого репо, куда ставил (при `git: root` —
   ни для какого: в папки не ставишь).
4. Первый коммит — шаблон как есть: при `git: root` один в корне (`git add -A` там), при `git: repos` —
   в каждом репо; `init: проект из шаблона qa-toolkit <версия плагина>`. Заготовка целиком — одним
   коммитом, зоны карты корня — для работы после. Твоих правок в нём нет — так видно, что пришло из
   шаблона, а что заполнено.

## Шаг 4 — паспорта → «подтверждаю»

1. Впиши ответы интервью по таблице «куда пишется». Меняешь только места-заглушки (`?`, `<…>`,
   `ГГГГ-ММ-ДД`), остальной текст шаблона не трогаешь; «решим позже» пишешь явно, пустых мест не
   оставляешь среди обязательных. Закончив, пройди таблицу построчно по каждому файлу: каждое её
   место заполнено ответом или `— решим позже`, заглушек в нём не осталось.
2. Покажи человеку одним сообщением раздел 8 «Границы» паспорта `kb` дословно и таблицу оснащения
   автотестов (`docs/toolchain.md`, строки уже отобраны по слоям). Спроси: «подтверждаешь?»
3. Только после «подтверждаю» проставь дату в «Подтверждён человеком» паспорта и в «Подтверждён»
   `docs/toolchain.md`. Кивок в чате без даты в файле — не подтверждение.
4. `${PLUGIN_ROOT}/bin/qa-init.py filled <репо> <каждый заполненный файл>`, затем второй коммит — там же, где первый:
   `meta: паспорт и специфика проекта`.

## Шаг 5 — проверка

1. `${PLUGIN_ROOT}/bin/qa-init.py verify` в корне. Код 1 — перечисли проблемы, почини, что в твоей зоне, остальное —
   в отчёт.
2. `${PLUGIN_ROOT}/bin/preflight.py` в репо автотестов: недостачи печатай с тем, что без каждой закрывается, и командой
   установки из вывода. Ставит человек, по одному инструменту.
3. `make verify` в автотестах — только если `.venv` уже есть; нет — строка в отчёте «после установки
   `.venv`».
4. Всё зелёное — удали `plan.json` из корня.

## Шаг 6 — отчёт

Одним сообщением:
- что где лежит (дерево корня на один уровень; карта корня `CLAUDE.md` — из шаблона, или строки
  `root_kept` как есть), версии плагинов по папкам — строками блока
  «установлено» из вывода `verify`, как есть (`claude plugin list` не годится: печатает установки
  всех проектов машины без папки), слои;
- что заполнено; что стоит `— решим позже` — строками «Отложено…» из `report_lines` вывода
  `${PLUGIN_ROOT}/bin/qa-init.py scan` в корне, как есть (счёт и места — из одной описи);
- недостачи оснащения и что без них закрыто;
- **что делать дальше**, по порядку: перезапустить `claude` в корне (плагины подхватываются при
  старте); вписать секреты в `.env` автотестов (`cp .env.example .env`); `/qa-auto:setup-fork` с готовой
  строкой вводных (шаг 7) — при `git: root` в корне, как всё остальное (плагины стоят только там), при
  `git: repos` — в папке автотестов; первый источник в `raw/` вики и ингест.

## Шаг 7 — передача дальше

1. **Вводные для `setup-fork`.** Дай человеку готовую строку для запуска — где, как в шаге 6; при
   `git: root` пути в ней — от корня, с папкой автотестов в начале (`<папка>/specs/…`):
   `/qa-auto:setup-fork вводные: API …, спека …, слои …, фронт …, библиотека …, мобилка …` — только
   то, что уже известно, настоящими значениями. Неизвестное выбрасывай из строки целиком, без заглушек
   и «решим позже»: `setup-fork` берёт вводные из запроса и спрашивает только то, чего в них нет.
2. **Удалённый репо** — если человек в интервью сказал «да»: покажи точные команды создания и
   первого пуша — при `git: root` один репо для корня, при `git: repos` — для каждого — и выполняй
   только после отдельного «да» на них.

## Готовый проект

`scan` вернул `project`: в корне уже лежат репо с маркерами. Проект не создаёшь заново и не
перезаписываешь; повторный заход ничего не ломает.

1. `${PLUGIN_ROOT}/bin/qa-init.py verify` в корне — только чтение.
2. **Сводка** одним сообщением: продукт; каждое репо — папка, роль, слои и библиотека фронта, версия
   шаблона из маркера (`plugin_version`); какой роли нет (`missing_roles`); что чужое лежит в корне
   (`entries` — не трогаешь); проблемы `verify` с командами из вывода и его блок «установлено»;
   строки `report_lines` из `scan` — **как есть, не пересобирая**: про отставший шаблон и `/qa:sync`
   и отложенное со счётом и местами (собирая их сам, агент путал версии шаблона и плагина).
3. **Что делаем** — формой с множественным выбором, только применимые варианты: «доставить
   плагины» — `verify` нашёл неустановленные (его готовые команды `cd … && claude plugin install …`, как есть); «досоздать репо
   <роль>» — роль в `missing_roles`; «доспросить отложенное (N мест)» — есть места в `later`;
   «положить карту корня» — `verify` сказал, что её нет (его команда `${PLUGIN_ROOT}/bin/qa-init.py root`, как есть);
   «ничего, только сводка» — всегда. Выбранное выполняешь в этом порядке: плагины → карта корня →
   второй репо → доспрос. Применимых, кроме последнего, нет — скажи, что проект собран полностью, и закончи.
4. **Доспросить отложенное.** По местам из `later`: какой вопрос интервью за каждым — по таблице
   «куда пишется» `${PLUGIN_ROOT}/skills/init/references/interview.md`; одно значение, записанное в два файла (адрес фронта в
   паспорте и в `site-notes.md`), спрашивай один раз. Формами — тот же вопрос с теми же вариантами,
   что в «Формах» `${PLUGIN_ROOT}/skills/init/references/interview.md`. Потом одним
   сообщением — список «файл:строка → что впишу» и «записываю?»; до «да» — ничего. Снова «решим
   позже» — место остаётся как есть. Ответ противоречит уже записанному вне отложенных мест (в
   паспорте «трекера нет», а критерии — «из трекера») — уточни и внеси то место в тот же список;
   молча не правь.
5. Вписываешь только места из списка и дату в «Обновлено» тех же файлов. Задет раздел 8 «Границы»
   паспорта — покажи его итоговый текст дословно и спроси «подтверждаешь границы?» **отдельным
   вопросом** от «записываю?» (можно в той же форме), как в шаге 4; после «подтверждаю» — новая дата
   в «Подтверждён человеком». Затем `${PLUGIN_ROOT}/bin/qa-init.py filled <репо> <файлы>` и коммит в каждом задетом
   репо: `meta: дозаполнено из /qa:init`. `verify` и `scan` ещё раз; отчёт: что вписано (по списку),
   что осталось отложенным — строки «Отложено…» из `report_lines` повторного `scan`, как есть.
6. **Досоздать репо.** Продукт, название и каталог — из маркера и settings готового репо, их не
   спрашиваешь. Интервью — только формы новой роли: автотестам — «Слои» из формы 1 и форма 2, `kb` —
   «База знаний» и «Трекер» из формы 1, формы 4–6; имя папки — `<продукт>-<роль>` по умолчанию. Дальше шаги 2–5 для одного
   репо: план на «да», `apply` (в `plan.json` — только новый репо; продукт, каталог или роль разошлись
   с готовым — код 2), плагины — по `verify` (при `git: root` только в корень: плагин роли), паспорта на
   «подтверждаю». `apply` вписывает соседа в маркер готового репо, дописывает нетронутую карту корня
   (правленую оставляет — `root_kept`: скажи в отчёте, что строк про новую папку в ней нет) и settings
   корня. Коммиты при `git: root` — в корне, в таком порядке, `git add -A` — не раньше второго:
   сначала `meta: сосед <папка>` — всё, кроме новой папки (`git add -A -- . ':!<папка>'`), потом шаблон
   новой папки (`git add <папка>`, шаг 3.4), потом её паспорт. При `git: repos` — `meta: сосед` в готовом
   репо, остальное — в новом. Потом `verify` и отчёт, как в шаге 6.

## Приём готового ручника
