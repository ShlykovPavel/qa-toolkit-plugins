# Шаблон баг-репорта (референс для Шага 4)

Структура ниже проверена на реальном репорте, который читал и правил
разработчик с доступом к бэкенд-репозиторию: она выдержала обратную связь по
всем пунктам, кроме перечисленных в «Чего делать НЕ надо» — эти пункты и
появились из его правок.

Порядок разделов не случаен: разработчик должен получить **репро раньше
теории**. Гипотезы о внутренностях кода читаются последними или не читаются
вовсе.

---

<2–4 предложения: где, при каком запросе, чем противоречит контракту.>

| # | Поле/операция | Контракт (спека) | Факт (стенд) | Поведение |
|---|---|---|---|---|

    POST /api/<ресурс> с телом {"<обязательное поле>": "Test"}

## Чего делать НЕ надо (в самом репорте)

Правила выведены из реальных правок разработчика к первой ревизии репорта.
Конкретика в скобках — из одного проекта (ASP.NET-бэкенд), сами правила
переносимы на любой стек.

- **Не предлагать фикс во внутренностях, которых не видел.** Предложение
  «добавить валидацию в бизнес-слое» оказалось избыточным: во фреймворке
  бэкенда уже работала декларативная валидация, дававшая 400 автоматически
  (`[ApiController]` + DataAnnotations). Не видишь код — описывай поведение и
  развилку, не реализацию.
- **Выясни, откуда берётся спека, прежде чем предлагать «поправить спеку».**
  Она может генерироваться из аннотаций/атрибутов моделей — тогда отдельного
  файла, который «поправят», не существует, и правильная правка одна: аннотация
  в модели (лечит и контракт, и поведение сразу).
- **Не цитировать артефакт по памяти.** Номер строки в стек-трейсе был взят из
  другого, не связанного падения и указывал на неверный участок кода. Каждый
  артефакт — `grep` по логу прогона перед утверждением.
- **Не сужать радиус без проверки.** Дефект затрагивал три префикса путей
  (разные группы API переиспользовали один бизнес-слой), а репорт заявлял один.
- **Не описывать инфраструктуру по догадке.** «Отдельный сервис» оказался
  группой эндпоинтов внутри монолита. Не уверен — не утверждай или помечай `⚠️`.

## Приоритет: что «хуже 500»

Отдельно и заметно выделяй дефекты, при которых API отвечает **успехом**, но
данные некорректны (молча сохранённый default даты, `0`, пустая строка).
Они опаснее 500: 500 виден сразу в прогоне и в мониторинге, а некорректная
запись расходится по системе и обнаруживается много позже — уже как порча
данных. В сводке такие строки должны быть видны, а не спрятаны в конце.
