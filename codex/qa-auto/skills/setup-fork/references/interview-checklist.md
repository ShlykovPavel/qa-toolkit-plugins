# Чеклист интервью — полный список вопросов с вариантами

Задавай блоками. Перед каждым блоком проверь: нет ли ответа уже
(в запросе пользователя, в существующем паспорте, в коде из разведки).

## Блок 1 — Авторизация

- Какая схема? Варианты: Bearer JWT (токен в заголовке Authorization) /
  cookie-сессия / постоянный api-key / другое.
- Эндпоинт логина: метод + путь (например, POST /api/auth/login).
- Поля тела запроса логина (email/login/username? password? ещё что-то —
  tenant, deviceId?).
- Что в ответе: имена полей access- и refresh-токена. Refresh есть вообще?
- Refresh-эндпоинт и его контракт (если есть).
- Есть ли особенности: 2FA у тестовых учёток (должно быть отключено!),
  капча (нужен обход для тестового контура), IP-allowlist.

## Блок 2 — Роли

- Какие роли нужны тестам? Роли из паспорта базы и описания продукта (SKILL.md,
  шаг 1) уже известны — их не спрашивай; набора «по умолчанию» нет.
- Для каждой роли: короткое имя-ключ для access_folder латиницей и имена
  env-переменных с кредами — формат: `<РОЛЬ>_LOGIN` / `<РОЛЬ>_PASSWORD`
  (или `_EMAIL`, если логин — почта).
- Это постоянные учётки или их надо создавать? (если создавать —
  каким эндпоинтом; это уйдёт в фикстуры позже)

## Блок 3 — URL

- Базовый URL основного API.
- Есть ли другие сервисы, которые будут дергать тесты? (второй бэкенд,
  admin-API) — URL каждого + имя env-переменной.
- Это стенд/staging? (не прод! если прод — предупреди о рисках тестовых данных)

## Блок 4 — Спека / контракты

- Есть ли OpenAPI/Swagger? Где: URL (…/openapi.json, …/swagger/v1/...)
  или файл в репо?
- Спека одна или несколько? Монолит с несколькими Swagger UI-страницами
  (клиентская/админская/публичная) — это НЕСКОЛЬКО спек: каждая — своя
  строка в таблице «Сервисы» паспорта и свой подпакет `src/<сервис>/`
  (см. docs/api-layer.md, «Если сервисов больше одного»).
- Каждую спеку сохранить локально в `specs/` и записать в паспорт
  источник (URL) + дату скачивания — обновление должно быть
  воспроизводимым.
- Если нет — где правда о контрактах: Confluence, Postman-коллекция,
  исходники бэкенда, «спрашивать разработчиков»?

## Блок 5 — База данных

- Нужен ли тестам доступ к БД? (проверки персистентности, чтение
  токенов/кодов)
- Если да: тип БД, имена env-переменных строк подключения
  (DB_PRIMARY, DB_SECONDARY).
- Какие таблицы тестам МОЖНО читать, по каким колонкам искать
  (например: accounts — по email; orders — по external_id).
- Есть ли таблицы, которые трогать запрещено?
- Можно ли тестам ПИСАТЬ в БД (update_record) или только читать?

## Блок 6 — Конвенции API

- Код успешного create: 200 или 201? Возвращает ли тело с id (имя поля)?
- Код успешного update / delete: 204 или 200?
- Delete несуществующего: 404 или идемпотентный 204?
- Формат списков: голый массив или конверт (data/items + total)?
  Параметры пагинации: page+limit / offset / cursor?
- Формат тела ошибок (пример JSON ошибки валидации).

## Блок 7 — Охват

- Только API-тесты, или также фронтенд / мобилка?
- Фронтенд: URL веб-интерфейса, есть ли data-testid у элементов?
- Фронтенд: на какой библиотеке писать тесты? Варианты СТРОГО:
  `selenium` (дефолт; ничего доставлять не нужно) / `playwright`
  (потребуется requirements-playwright.txt + playwright install chromium).
  «Не знаю / всё равно» → `selenium`. Значение пишется в паспорт токеном
  в поле «Библиотека фронтенд-тестов».
- Мобилка: платформа (Android/iOS), откуда брать APK/бандл,
  есть ли ValueKey у виджетов?
