# Сырьё прогона: единый формат и адаптеры

Проблема, которую решает формат: выводы, скептик и подсчёт объёма выборки не должны зависеть от
инструмента, которым гоняли запросы. Меняется инструмент — меняется **только адаптер**.

## `evidence.json` — что в нём

Одна запись на выполненный запрос. Тела ответов лежат файлами рядом, а не внутри: сырьё нужно
целиком, но в контекст его тянуть незачем.

```json
{
  "schemaVersion": 1,
  "runner": "bruno",
  "suite": ["Seller Orders"],
  "env": "dev",
  "mutation": null,
  "requests": [
    {
      "name": "orders list",
      "case": "TC-12",
      "role": "seller",
      "method": "GET",
      "url": "https://api.example.test/api/seller/orders?page=1&pageSize=20",
      "status": 200,
      "observedAt": "2026-08-24T12:03:41+03:00",
      "writing": false,
      "bodyPath": "bodies/001.json",
      "counts": { "items": 4, "$.data.records": 4 },
      "totalCount": 4,
      "assertions": [
        { "name": "все записи имеют дату продажи", "status": "pass", "message": "" }
      ]
    }
  ],
  "totals": { "requests": 13, "assertions": 26, "passed": 26, "failed": 0, "writing": 0 }
}
```

| Поле | Смысл | Почему обязательно |
|---|---|---|
| `name` | имя запроса, стабильное между прогонами | по нему `vacuum` находит базу сравнения; без `name` имя берётся из URL, а мутация URL меняет — запись уйдёт в `unmatchedBaseline`, и проба может ложно объявить себя неприменившейся |
| `case` | номер кейса `TC-NN` | без него результат не вернуть в кейсы (шаг 13) |
| `role` | роль, под которой выполнялся запрос | вывод «под покупателем закрыто» иначе недоказуем |
| `observedAt` | момент наблюдения; заполнен у `run`, `null` у `import` | «какое значение в каком файле и когда» — вопрос, на котором рукотворное сырьё ошибалось систематически; у импорта время знает раннер, и подставлять сюда время импорта нельзя |
| `writing` | запрос меняет состояние | из этого собирается раздел «что изменилось на стенде» |
| `counts` | длина каждого массива в ответе | **основа подсчёта объёма выборки**: без него вакуумность не измерить |
| `assertions` | ожидания и их итог | пусто — значит ожидания в раннере не записаны, и об этом надо сказать в отчёте |

`counts` считает адаптер, а не ты глазами: ручной подсчёт — это класс «вакуумность», ждущий
своей очереди.

## Адаптеры

Адаптер отвечает на два вопроса: **как запустить** и **где машинный отчёт**. Оба ответа — в
паспорте, раздел «API: чем выполняются проверки».

### Есть машинный отчёт (Bruno, Newman, любой CLI с `--reporter json`)

```bash
<команда прогона с выгрузкой JSON-отчёта>
evidence.py import --runner bruno --report run.json -o evidence.json
```

Импорт нормализует отчёт в формат выше. Незнакомый формат — добавляется ветка в `import`, а не
переписывается всё остальное.

**Где именно импорт ищет номер кейса — не там, где кажется.** `TC-NN` вычитывается из **имени
файла запроса**, из `suitename` и **из текстов самих проверок** (описание `test(...)`, выражение
ассерта). Имя запроса, объявленное внутри файла раннера (у Bruno — `meta.name`), в этот список
**не входит**: номер, написанный только там, не найдётся. Замерено: восемь запросов с аккуратным
`TC-NN` в `meta.name` пришли в `audit` как «БЕЗ НОМЕРА КЕЙСА» все восемь.

Ошибка тихая — `audit` не падает, а печатает флаг в списке, и без внимательного чтения вывода
покрытие молча не считается. Поэтому: **пиши `TC-NN` в первую строку описания проверки** (или в
имя файла) и после первого же прогона убедись по выводу `audit`, что номер подхватился.

### Машинного отчёта нет (голый `curl`, `.http`, ручные запросы)

Опиши запросы списком и прогоняй скриптом — он сам выполнит и соберёт сырьё:

```json
[
  { "name": "orders list", "case": "TC-12", "role": "seller",
    "method": "GET", "url": "https://api.example.test/api/seller/orders?page=1",
    "headers": { "Authorization": "Bearer $TOKEN" } }
]
```

```bash
evidence.py run --runner curl --requests requests.json -o evidence.json
```

Ожиданий у такого прогона нет: `assertions` придёт пустым. Это честно и видно в `audit` —
объём выборки посчитается, а вывод придётся обосновывать вручную.

**Каждый прогон — в свой каталог вывода, и скрипт это проверяет сам.** Тела ложатся рядом
с `-o`, в подкаталог `bodies/`, и нумеруются по порядку запросов: второй прогон в тот же каталог
положил бы `001.json` поверх первого — после чего вывод первого прогона «доказывался» бы телом
второго. Другое имя файла в `-o` не спасает: каталог тел общий. Поэтому `run`, `import` и
`vacuum` в занятый каталог отказывают до первого запроса (код 2) и называют свободный:

```bash
evidence.py run --runner curl --requests requests.json \
    -o <каталог захода>/progon-2/evidence.json
```

Каталог заранее не создавай — его создаст скрипт. Занятый не чисти: в нём сырьё прошлого
прогона. Замерено трижды на одном проекте: правило было записано уроком, прочитано в фазе 0,
стояло здесь у самой команды — и всё равно нарушалось, поэтому проверка переехала в скрипт.

**Этот путь обязателен, а не предпочтителен: вывод не опирается на `curl`, набранный в
переписке.** Разница не в аккуратности, а в том, что `run` кладёт рядом с телом имя, кейс,
роль, метод, адрес, код и время наблюдения — а рукотворный дамп несёт только тело, и «какое
значение в каком файле и когда» держится на памяти пишущего. Замерено: три захода подряд
платили за это самой дорогой статьёй расходов — ошибка «число приписано не тому файлу»
случилась в одном заходе **трижды**, каждый раз на новом файле, и каждый раз её ловил скептик,
то есть самым дорогим способом из возможных.

**Одиночный `curl` остаётся законным ровно в двух местах:** разведка, из которой вывод не
делается, и запрос, который скриптом не выражается (multipart-загрузка, поток, ожидание
воркера). В обоих случаях файл обязан нести шапку — иначе он не сырьё, а заметка:

```bash
# в дамп идут и заголовки (-D -), и время, и чем/под кем снято
{ echo "# $(date -Is) · GET /api/instructor/profile · учётка instructor_x · канал curl"; \
  curl -sS -D - -H "Authorization: Bearer $TOKEN" \
       https://api.example.test/api/instructor/profile; } | tee raw/profile-after.txt
```

Шапка — это URL, время, учётка и канал. Без них два дампа одного эндпоинта под разными
учётками неразличимы, а вывод, построенный на «том, который свежее», недоказуем.

**`-o файл` сам по себе сырьём не делает.** Он сохраняет тело и теряет метод, URL и код
ответа: на `204` в файле остаётся пустота, неотличимая от неудачного вызова. К нему обязательны
`-D -` и шапка выше — в одной и той же команде, а не «допишу потом». Проверка перед тем, как
сослаться на вызов: **в файле видно, каким методом и по какому адресу это снято?**

## Обязательные шаги после любого прогона

```bash
evidence.py audit evidence.json
# проба по списку запросов, прогон через curl
evidence.py vacuum --baseline evidence.json --requests requests.json \
    --query from=2099-01-01 -o vacuum.json
# либо тем же раннером, своей командой
evidence.py vacuum --baseline evidence.json --runner bruno \
    --cmd '<команда прогона с подменёнными параметрами>' --report empty.json -o vacuum.json
```

Параметры подмены — из паспорта, раздел «Проба на вакуумность»: скрипт паспорт не читает и
подставить их за тебя не может.

`audit` печатает: объём выборки по каждому запросу, запросы с нулевыми массивами, чьи
проверки при этом прошли, запросы без объявленного `case`, список пишущих запросов.

`vacuum` — мутационная проба: тот же набор на заведомо пустой выборке. Смотри на две цифры:
сколько проверок осталось зелёными и **применилась ли проба вообще**. Не применилась — её
результат не значит ничего, и это отдельная претензия. Третье, что нельзя пропустить, —
блок «БЕЗ БАЗЫ СРАВНЕНИЯ» (`unmatchedBaseline` в `vacuum.json`): у этих запросов имя не
нашлось в baseline, сравнение «was/now» для них не проводилось, и вердикт «применилась»
на них не опирается. Сверка `now`/`was` с ожидаемым URL при многозначных query-параметрах
(`tagIds=A&tagIds=B`) делается глазами по самому `vacuum.json`, а не по одной строке итога.

**Ноль ожиданий — проба ничего не измерила, и это идёт в отчёт дословно.** У раннера без
ассертов (`curl`, ручной обход) `assertionsTotal: 0` и `survivors: []` означают не «проба
пройдена», а «мерить было нечего»: остаётся слабая проверка, что выборка вообще умеет
пустеть. Скрипт говорит это сам строкой «Ожиданий в прогоне нет» — **перенеси её в отчёт**.
Замерено: проба с нулём ассертов была подана в отчёте как выполненная, и по
отчёту это было неотличимо от настоящего измерения.

**Baseline и мутированный прогон не делят каталог тел.** Скрипт разводит их сам
(`bodies/` против `bodies-mutated/`), но если раннер свой — номера запросов совпадают, и
пустые мутированные ответы лягут поверх baseline молча.

## Раннер — браузер, критерий — текст экрана

Формат выше спроектирован под API: выборки, фильтры, пагинация. Для UI-раннера часть его
неприменима, и это надо оформить честно, а не подгонять.

| Понятие API | Чем заменяется на фронте |
|---|---|
| `counts`, объём выборки | сколько мест/страниц/образцов наблюдалось; для текста — что захват **непуст** |
| мутационная проба на пустой выборке | **позитивный контроль поиска** (ниже) |
| `assertions` из отчёта раннера | шаги кейса с наблюдаемым фактом; фиксируются вместе с дословным текстом |

**Позитивный контроль поиска** — обязательная замена мутационной пробы, когда вывод
отрицательный («слова нет», «блока нет», «ошибок в консоли нет»). Прогони **тот же метод
поиска** по корпусу, где искомое заведомо есть — по дампу первоисточника, по старому снимку, по
странице, где дефект ещё живёт. Нашёл там и не нашёл на стенде — вывод действителен. Не нашёл
нигде — искал не там, и «не встречается» ничего не значит.

Замерено: поиск `подпис` дал 6 вхождений в описании карточки и 0 в дампе стенда — только
этого «слово ушло» стало наблюдением, а не отсутствием наблюдения.

Отдельно проверяй **ложную широту подстроки**: `подпис` матчит и «подпись». Совпадение по
подстроке требует ручной проверки контекста.

**`evidence.py` фронтовые заходы не обслуживает, и это норма, а не пробел.** Формат
запрос-центричен: метод, адрес, код, длины массивов в теле. Единица наблюдения на фронте —
страница с сохранённым дампом, а не запрос, и натягивание одного на другое даёт файл, который
выглядит машинным, ничего при этом не измерив (следующий раздел про это отдельно).

Машинное сырьё у фронта своё, и его достаточно: JSON `probe.mjs`, перенаправленный в файл, и
дампы текста и разметки с длиной в символах, которую печатают сами скрипты. Адаптера
«дамп → `evidence.json`» не заводим намеренно — он бы производил ровно тот запрещённый
артефакт. Сверка витрины с API — по-прежнему два наблюдения: ответ бэкенда в `evidence.json`,
экран в дампе, и расхождение называется словами.

## Артефакт машинной формы, собранный руками, запрещён

`evidence.json` — это либо вывод скрипта, либо его нет. Нужно зафиксировать сырьё вручную —
делай это **файлом другого имени и другой формы**, с шапкой «собрано вручную, не вывод
скрипта».

Причина: файл, выглядящий как машинный отчёт, читается как машинный отчёт. Пометка внутри
теряется при первом же пересказе, а цифры из него начинают жить как измеренные. Замерено на
живом заходе: рукотворный `evidence.json` объявлял ручную замену пробы, которой в нём не было
ни одной строкой — поймал это только независимый скептик.

## Правила, из которых формат вырос

- **Ожидание, живущее только в коде раннера, считается незаписанным.** Поэтому `assertions`
  переносятся в сырьё, а кейс всё равно живёт отдельным текстом.
- **Число рядом с вердиктом.** Любой вывод в отчёте сопровождается объёмом выборки, и берётся
  он из `counts`, а не из памяти.
- **Скрипт, попавший в документ, обязан быть выполнен из документа.** Однажды в план попал
  скрипт, который никогда не запускался: работавший вариант выполнялся другим способом, а
  записан был переписанный по памяти. Проверять — прямым запуском.
- **Секреты в отчётах маскируются.** Маска в поле `Authorization` — это маска, а не
  отсутствие токена. Проверяй по коду ответа, а не по виду заголовка.
