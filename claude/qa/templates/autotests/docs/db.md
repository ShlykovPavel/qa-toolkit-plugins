# Как проверять состояние БД в тестах

Инфраструктура: `src/db_config.py` (подключения и сессии),
`src/db_functions.py` (класс `DbInfo` — выборки и обновления).
Образец использования в тесте — докстринг
`Tests/Regression_tests/example_flow/test_example_flow.py`.

---

## Когда БД-проверка уместна (а когда нет)

БД — не замена API-ассертам, а дополнение для того, что через API не
видно. Правило: **если состояние можно проверить ответом API — проверяй
ответом API**; в БД иди, когда:

- API не отдаёт нужное поле (служебные статусы, флаги, timestamps);
- проверяется **побочный эффект**: операция в одном сервисе должна
  породить запись в другой таблице/базе;
- проверяется **асинхронная пропагация** — запись появляется с задержкой
  (очередь, воркер), и API «ещё не знает»;
- надо убедиться в персистентности: API ответил 200, но действительно ли
  строка в таблице изменилась.

Тест, который дублирует каждый API-ассерт SELECT'ом, — шум: он медленнее,
хрупче (привязан к схеме) и ничего не добавляет.

**Какие таблицы можно трогать — вопрос паспорта.** Интервью `/setup-fork`
фиксирует в `docs/project-profile.md` список доступных тестам таблиц и
ключевые колонки. Таблиц нет в паспорте → это открытый вопрос команде,
а не повод исследовать схему наугад.

## Подключение

Строки подключения — только из env (SQLAlchemy-формат):

| Переменная | Что это |
|---|---|
| `DB_PRIMARY` | основная БД сервиса, напр. `postgresql+psycopg2://user:pass@host:5432/dbname` |
| `DB_SECONDARY` | вторая БД (опционально) — задай в `.env`, и `secondary_session()` заработает автоматически |

Движки создаются лениво: импорт модулей и `pytest --collect-only`
работают без `.env` и без доступной БД. Обращение к сессии без заданной
переменной падает с понятной ошибкой — это сигнал заполнить `.env`,
а не ловить исключение в тесте.

## Сессии: короткоживущие, через контекст-менеджеры

```python
from src import db_config
from src.db_functions import DbInfo

with db_config.primary_session() as session:
    uid = DbInfo.get_value_where(session, "accounts", "uid", "email", email)
```

Контекст-менеджер сам делает commit при успехе, rollback при ошибке и
всегда закрывает сессию — упавший запрос не оставит соединение в
сломанном состоянии для следующих тестов. Отсюда правила:

- **сессия — на одну проверку**, не на весь тест и тем более не на
  сессию pytest: открыл → выбрал → закрыл;
- старые точки входа `primary_db_session` / `secondary_db_session`
  удалены — только контекст-менеджеры (см. CLAUDE.md);
- `pool_pre_ping` уже включён — перезапуск стенда между тестами не
  оставляет мёртвых соединений.

## Чтение: какой хелпер брать

| Хелпер | Что делает | Когда |
|---|---|---|
| `get_value_where(session, table, column, where_column, where_value)` | значение колонки строки по известному ключу | **ОСНОВНОЙ способ** — безопасен при параллельном прогоне |
| `get_all_by_column(...)` | все строки с данным значением колонки | проверки принадлежности/количества строк своего ресурса |
| `get_latest_value(session, table, column)` | значение из последней (по id) строки | ТОЛЬКО когда ключа для WHERE физически нет |
| `get_second_latest_value(...)` | из предпоследней строки | то же предупреждение |

Почему «последняя строка» опасна: при pytest-xdist параллельный воркер
успевает вставить СВОЮ строку между твоим create и твоим SELECT — тест
читает чужие данные и флачит (см.
[articles/failure-triage.md](articles/failure-triage.md), пункт 3).
Выборка по ключу от этого свободна, но её безопасность держится на
УНИКАЛЬНОСТИ ключа: при нескольких строках под условие `get_value_where`
молча вернёт последнюю по id. Выбирай ключ, принадлежащий именно твоему
тесту (сгенерированный email, uid, id из ответа API), а не общее
значение вроде статуса.

Безопасность уже зашита в хелперы: значения всегда уходят
bound-параметрами (кавычки в данных ничего не ломают), имена
таблиц/колонок валидируются (`_check_identifier` — только
буквы/цифры/подчёркивание). Сырой SQL в тестах не пишем.

## Запись: `update_record` — точечно и осознанно

`DbInfo.update_record(session, table, column, value, record_id)` меняет
одну колонку строки по id. Легитимное применение — привести ресурс в
состояние, **недостижимое через API** (например, состарить timestamp,
чтобы проверить протухание). Что НЕ делаем:

- **не создаём тестовые данные INSERT'ами в обход API** — данные создаёт
  API-клиент (иначе тест проверяет выдуманное состояние, которого
  приложение не порождает);
- не «чиним» стенд UPDATE'ами в teardown — удаление данных тоже через
  API-клиент в фикстурах;
- commit не нужен — его делает контекст-менеджер при выходе.

## Асинхронность: `wait_until` вокруг выборки

Запись появляется в БД с задержкой → поллинг, не sleep:

```python
from src.wait_utils import wait_until

def _uid_in_db(email):
    with db_config.primary_session() as session:
        return DbInfo.get_value_where(session, "accounts", "uid", "email", email)

uid = wait_until(
    lambda: _uid_in_db(email),
    timeout=30,
    message=f"uid для {email} не появился в БД",
)
```

Сессия — ВНУТРИ условия: каждая попытка поллинга открывает и закрывает
свою. Ловушка `wait_until`: условие должно возвращать truthy — если
легитимное значение может быть falsy (0, "", False), оборачивай
`lambda: fn() is not None`.

## Частые ошибки

| Ошибка | Как правильно |
|---|---|
| SELECT-дубль каждого API-ассерта | БД — только для невидимого через API |
| `get_latest_value` «потому что проще» | ключ есть почти всегда — `get_value_where` |
| Сессия открыта на весь тест | контекст-менеджер вокруг каждой проверки |
| INSERT тестовых данных мимо API | данные создаёт API-клиент; `update_record` — только для недостижимых состояний |
| `time.sleep` перед SELECT «чтобы доехало» | `wait_until` с сессией внутри условия |
| Строка подключения в коде теста | только `DB_PRIMARY`/`DB_SECONDARY` из `.env` |
| Выборка из таблицы «на глаз» | список доступных таблиц — в паспорте проекта |
