# Как писать мобильные Appium-тесты (UiAutomator2 / XCUITest)

Эталоны: `Appium/app_keys/example_feature_buttons.py` (локаторы),
`Appium/Modules/example_module.py` (модуль фичи),
`Tests/Mobile_tests/test_mobile_example.py` (тесты).

Один слой покрывает нативный Android, нативный iOS и Flutter-приложения:
элементы ищутся по стабильным идентификаторам — Android `resource-id` /
iOS `accessibilityIdentifier`; Flutter ≥ 3.19 пробрасывает
`Semantics.identifier` в эти же атрибуты. Контракт с разработчиками
приложения (что и как проставить + готовый AI-промпт) —
[locator-conventions.md](locator-conventions.md).

---

## Архитектура: три слоя

```
Appium/app_keys/<фича>_buttons.py   # ТОЛЬКО локаторы: идентификатор → @property
Appium/Modules/<фича>_module.py     # взаимодействия: open/create/fill + логирование
Tests/Mobile_tests/test_<фича>.py   # сценарии и ассерты
```

Плюс инфраструктура (не трогать при добавлении фич):
`Appium/driver_func.py` (фабрика драйвера, жесты, диагностика),
`Appium/Appium_launcher/`, `Appium/Simulator/`,
`Tests/Mobile_tests/conftest.py` (сервер/эмулятор/драйвер — см.
[fixtures.md](fixtures.md)), `dump_ui_tree.py` (инвентаризация
идентификаторов экрана).

## Два базовых класса — не путать

| Класс | Файл | Роль |
|---|---|---|
| `ScreenActions` | `app_keys/screen_actions.py` | БАЗА всех app_keys: поиск/клики/ввод/скроллы/page_source. Новые классы локаторов наследуют ЕГО |
| `BaseElements` | `app_keys/base_elements_buttons.py` | Наследник ScreenActions с локаторами ОБЩИХ элементов (submit_button, exit_modal_button). Используется в модулях для общих кнопок |

Новый экран → `class MyScreenButtons(ScreenActions)`. `BaseElements` — не
база для наследования, а готовый набор общих элементов.

## Лестница локаторов — ЖЁСТКАЯ

Единственный источник локаторов — **стабильные идентификаторы**:

- Android: `resource-id` (нативные View — `android:id`, Compose — `testTag`
  + `testTagsAsResourceId`, Flutter — `Semantics.identifier`);
- iOS: `accessibilityIdentifier` (UIKit/SwiftUI/Flutter-Semantics).

Идентификатора нет → **БЛОКЕР**: тесты на экран не пишутся, разработчикам
приложения уходит список недостающих id (конвенция имён, примеры кода и
готовый промпт — [locator-conventions.md](locator-conventions.md)).
Локаторы по видимому тексту, XPath-по-структуре и координатам запрещены —
в `ScreenActions` их нет намеренно.

## Шаг 1 — Узнай реальные идентификаторы (не выдумывай!)

Идентификаторы снимаются с живого приложения; единица работы для
тест-кейса — **проход сценария целиком** (одна Appium-сессия, дамп +
скриншот на каждый шаг), а не одиночные снимки: каждый новый запуск
скрипта пересоздаёт сессию и перезапускает приложение, состояние экрана
теряется.

```bash
dump_ui_tree.py --walkthrough dumps/create_task   # проход сценария (дефолт)
dump_ui_tree.py --wait-manual 30 --raw-out screen.xml   # один экран
dump_ui_tree.py --from-file screen.xml            # разбор готового дампа
```

Скрипт выводит JSON со списком найденных идентификаторов (walkthrough —
папку `step_NN_*.xml` + `steps.json`). Все способы, включая appium-mcp и
рецепты для коллеги без репозитория, — в секции «Как показать агенту
экраны приложения — инструкция для человека» ниже; агент предлагает выбор
на старте.

## Шаг 2 — app_keys (эталон: example_feature_buttons.py)

```python
from Appium.app_keys.screen_actions import ScreenActions

class ProjectsButtons(ScreenActions):

    @property
    def create_button(self):
        return self.get_element("app_projects_create_button")

    def project_tile(self, project_id: str):        # динамический id — метод
        return self.get_element(f"app_project_tile_{project_id}")
```

Статичные элементы — `@property`, элементы с параметром (id сущности из
API) — методы. В `get_element` передаётся «голый» идентификатор без
`<package>:id/` — платформенную обвязку слой добавляет сам.

## Шаг 3 — Модуль (эталон: example_module.py)

```python
class ProjectsModule:
    def __init__(self, driver):
        self.driver = driver
        self.buttons = ProjectsButtons(driver)
        self.base = BaseElements(driver)

    def open_projects(self):
        Logger.log_mobile_action("Переход на экран Projects")
        self.buttons.click_element(self.buttons.nav_button)
```

- **Каждое действие — `Logger.log_mobile_action(...)`** — главный источник
  диагностики при падениях.
- Модуль знает «как сделать», тест знает «что проверить». Ассерты — в тестах
  (кроме внутренних ассертов шагов сложных сценариев).

## Шаг 4 — Тест (эталон: test_mobile_example.py)

- `pytestmark = pytest.mark.mobile`, allure epic "Mobile".
- Драйвер приходит autouse-фикстурой `driver` (свежий на каждый тест).
- Логин приложения — своей фикстурой (образец `login_in_app` закомментирован
  в Tests/Mobile_tests/conftest.py); флоу логина = UI-вход, не HTTP.
- Предусловия данных — через API-клиенты `src/`, не через UI.

## Семантика поиска элементов — ВАЖНО

`get_element(key)` (по умолчанию `element_expected=True`):
нашёл → вернул элемент; не нашёл за таймаут (env `MOBILE_ELEMENT_TIMEOUT`,
по умолчанию 5 с) → ValueError с именем ключа.

`get_element(key, element_expected=False)` — это АССЕРТ ОТСУТСТВИЯ:
дождался исчезновения/невидимости → None (ок); элемент видим →
ValueError. **Элемент этот вызов не возвращает никогда** — не используй
его, чтобы «достать элемент, если есть».

Правильная проверка отсутствия элемента:
```python
assert buttons.is_element_not_presented("app_project_tile_42")
```

## Тексты и локализация

Поиска по тексту в слое НЕТ — текст не локатор. Текстовые проверки:
элемент находится по идентификатору, его `.text` сверяется со строкой
локализации:

```python
title = buttons.screen_title
buttons.assert_text(title, "projects_screen_title")
```

Тексты лежат в JSON (`Appium/localization/`, путь — env
`LOCALIZATION_FILE_PATH`). Не хардкодь строки в тестах — они ломаются при
смене языка.

## Платформенные особенности

### Android (UiAutomator2)

- Caps (см. `driver_func.py`): `appPackage`/`appActivity` из env; capability
  `app` НЕ задаётся — установку APK делает фикстура `install_apk`
  (`Appium/Simulator/`), запуск — `open_app` через `activate_app`.
- `resource-id` имеет две формы: нативные View — полная
  `<package>:id/<ключ>`, Flutter Semantics — голая строка `<ключ>`.
  `ScreenActions` матчит обе одним запросом `resourceIdMatches`
  (префикс — из env `ANDROID_APP_PACKAGE`).
- Jetpack Compose: `testTag` виден как `resource-id` ТОЛЬКО при
  `testTagsAsResourceId = true` на корневом composable — самая частая
  причина «идентификаторов нет в дампе» (детали в locator-conventions.md).
- Дамп экрана БЕЗ Appium: `adb exec-out uiautomator dump /dev/tty`.
  **Грабля**: `uiautomator dump` НЕ работает поверх живой
  UiAutomator2-сессии (accessibility-канал занят) — из живой сессии
  снимай `page_source` (скрипт/`get_page_source()`). Правило: adb-dump —
  проверка без Appium (его же советует разработчикам
  locator-conventions.md), из живой сессии — только page_source.
- Системные диалоги разрешений — `DriverFunctions.allow_notifications`
  (системный UI, не приложение — единственное место, где допустим поиск
  по тексту кнопки).

### iOS (XCUITest)

- Caps: `bundleId`, `udid`, WDA-настройки из env (см. `driver_func.py`).
- `accessibilityIdentifier` виден в page_source как атрибут `name` и
  ищется через `ACCESSIBILITY_ID` — это ОДИН и тот же атрибут.
- Дамп экрана без скрипта: `curl http://127.0.0.1:8100/source?format=xml`
  при поднятом WebDriverAgent.
- Системные алерты — `driver.switch_to.alert` (обёртка та же
  `allow_notifications`).

### Flutter (через Semantics)

- Работают те же нативные драйверы; отдельного «Flutter-режима» нет.
- Разработчики приложения проставляют `Semantics(identifier: ...)`
  (Flutter ≥ 3.19). **`ValueKey`/`Key` нативным драйверам НЕ видны** —
  существующие ключи виджетов не заменяют контракт.
- В release-сборке Semantics-дерево строится при подключённом
  accessibility-клиенте (Appium/uiautomator включают его сами) — проверяй
  идентификаторы дампом, а не «глазами».
- Если идентификаторов нет — это блокер для разработчиков; какой код
  просить — по фреймворку приложения (Flutter/Compose/UIKit/...), см.
  locator-conventions.md.

## Диагностика при падении

К упавшему тесту (fail в `setup` или `call`) hook
`pytest_runtest_makereport` в `Tests/Mobile_tests/conftest.py`
автоматически прикладывает в Allure:

- `screenshot` (PNG) — что было на экране;
- `page_source` (XML) — дерево элементов с идентификаторами.

Метод — `DriverFunctions.attach_failure_diagnostics(driver)`: каждый
артефакт в своём try, сам метод исключений не бросает. Плюс лог мобильных
действий (`Logger.log_mobile_action`) — читай его первым: мобильный цикл
обратной связи самый медленный, собирай максимум диагностики за итерацию.

## appium-mcp — опция живого режима

Для интерактивной работы с живым эмулятором можно подключить официальный
Appium MCP-сервер (инспекция: page source, поиск элементов, скриншоты).
Сильная сторона — проход сценария без ручного снятия дампов (рецепт Б
выше: «ты за рулём» — человек тапает, агент снимает; «агент за рулём» —
агент сам выполняет заранее описанный кейс жестами и вводом), плюс
мгновенная проверка локатора (`appium_find_element`) и подготовка iOS
(`prepare_ios_simulator`). Берём ТОЛЬКО инспекцию: кодоген MCP не
используем (конвенции слоя — свои), vision-фичу `appium_ai` не используем
(требует сторонний VLM-ключ). Обзор, инструкция подключения и грабли —
статья [articles/appium-mcp.md](articles/appium-mcp.md) (версию сервера
пиновать; полная оценка — в истории git, APPIUM_MCP_ASSESSMENT.md). Скрипт
`dump_ui_tree.py` (`--walkthrough`) покрывает тот же сценарий без MCP.

## Как показать агенту экраны приложения — инструкция для человека

**Зачем это.** Чтобы написать автотест, агент должен «увидеть» экран:
из каких элементов он состоит и какие у них идентификаторы. Глаза агента —
**XML-дамп экрана** (текстовое дерево элементов) и скриншот. Сам агент
устройство в руки взять не может — дампы снимаешь ты, это одна-две
команды. Ничего страшного в них нет: ниже каждый способ расписан по шагам.

Агент в начале работы сам предложит выбор. Шпаргалка, что выбирать:

| Твоя ситуация | Способ |
|---|---|
| Хочу покрыть тестом сценарий (несколько экранов/действий), эмулятор или телефон под рукой | **А — проход сценария скриптом** (основной) |
| То же самое, и в Claude Code подключён appium-mcp | **Б — проход с агентом** (он снимает сам) |
| То же, appium-mcp нет, но хочу, чтобы агент прошёл сценарий сам | **Е — агент проходит по сценарию-файлу** |
| Нужен один конкретный экран | **В — один снимок** |
| Снимаю для коллеги, у меня нет этого репозитория | **Г** (Android) / **Д** (iOS) |
| Дамп уже есть файлом | просто отдай файл — агент разберёт его `--from-file` |

Общие предусловия для А, Б, В (один раз): эмулятор/устройство запущено,
на нём установлен тестовый билд, Appium-сервер поднят, `.env` заполнен
(секция мобильных тестов). Итог любого рецепта — файл(ы), которые ты
отдаёшь агенту, плюс словами: что за фича и что за сценарий.

**Рецепт А — проход сценария скриптом (основной для тест-кейсов).**

```bash
dump_ui_tree.py --walkthrough dumps/<имя_сценария>
```

Как это выглядит: скрипт запустит приложение и будет ждать тебя. Ты
проходишь свой сценарий руками, шаг за шагом, и **после каждого шага**
возвращаешься в терминал, пишешь короткое имя шага (например
`otkryl_formu_sozdaniya`) и жмёшь Enter — скрипт снимает XML-дамп и
скриншот текущего состояния. Пустой Enter тоже работает (имя даст сам).
Закончил сценарий — введи `q`. Сессия одна на весь проход: приложение
между шагами НЕ перезапускается, состояние не теряется.
Отдать: папку `dumps/<имя_сценария>` целиком (внутри `step_NN_*.xml`,
скриншоты и `steps.json` с последовательностью шагов — агенту этого
хватит, чтобы восстановить и шаги, и локаторы).

**Рецепт Б — проход сценария с appium-mcp (если подключён).**
Если в Claude Code подключён MCP-сервер appium-mcp (проверь: `claude mcp
list`; подключение и версия — см. секцию appium-mcp ниже), дампы и
скриншоты агент снимает САМ через живую сессию. Два режима на выбор:

- *ты за рулём*: ты тапаешь в приложении, после каждого шага пишешь
  агенту в чат «шаг: открыл форму создания» — он снимает дамп и скриншот;
- *агент за рулём*: заранее опиши ему тест-кейс по шагам — он сам пройдёт
  его (тапы, ввод текста), снимая дамп на каждом шаге; шаги при этом
  получаются проверенными исполнением.

Отдавать ничего не нужно — всё уже у агента.

**Рецепт Е — агент проходит сценарий сам, без appium-mcp.**
Тебе нужно только поднять устройство, Appium и заполнить `.env` (для
сброса ещё `IOS_APP_PATH` на iOS или `ANDROID_APP_PACKAGE` на Android).
Скажи агенту «сними сам» и опиши кейс словами. Агент запишет шаги в
JSON-файл (тап / ввод / назад по идентификаторам) и запустит:

```bash
dump_ui_tree.py --walkthrough dumps/<имя_сценария> --script dumps/<имя_сценария>.json --reset-app
```

`--reset-app` перед проходом возвращает приложение к чистой установке —
каждый повтор стартует с первого экрана, а не с того, где закончился
прошлый. Упавший шаг скрипт снимает как `step_NN_<имя>_FAILED.xml` и
останавливается. Учти: проход создаёт на стенде те же данные, что
создал бы ты руками (регистрация, заявка), — агент перечислит их в отчёте.

**Рецепт В — один снимок (нужен один конкретный экран).**

```bash
dump_ui_tree.py --wait-manual 30 --raw-out screen.xml
```

После запуска у тебя 30 секунд, чтобы РУКАМИ открыть в приложении нужный
экран — скрипт снимет дамп по истечении паузы. Отдать: `screen.xml`
(скрипт заодно напечатает JSON со списком найденных идентификаторов).
Для сценария из нескольких экранов НЕ гоняй этот рецепт по кругу —
каждый запуск пересоздаёт сессию и перезапускает приложение; бери
рецепт А.

**Рецепт Г — Android без Appium и без репозитория (для коллеги).**
Нужен только `adb` и запущенный эмулятор/устройство. Открой нужный
экран руками, затем:

```bash
adb exec-out uiautomator dump /dev/tty > screen.xml
```

Пометки: последняя строка файла — служебный мусор вида
`UI hierchary dumped to: /dev/tty` (парсеру не мешает, но знай о нём);
команда НЕ работает, пока к устройству подключена живая
UiAutomator2-сессия (accessibility-канал занят) — останови тест/Appium
или используй рецепт А. Отдать: `screen.xml`.

**Рецепт Д — iOS без репозитория, при поднятом WebDriverAgent.**
Открой нужный экран руками, затем:

```bash
curl http://127.0.0.1:8100/source?format=xml > screen.xml
```

Отдать: `screen.xml`. Идентификаторы в нём — в атрибуте `name`.

Разбор полученного файла (уже в этом репозитории):
`dump_ui_tree.py --from-file screen.xml`.

## Что спросить у человека

1. Платформа прогона (Android/iOS), где брать APK/бандл.
2. Есть ли стабильные идентификаторы у нужных экранов; если нет — кто
   добавит (отдать разработчикам промпт из locator-conventions.md).
3. Флоу входа в приложение (логин/пин/биометрия) — нужен для фикстуры
   логина (UI-вход, не HTTP).
4. Тексты/локализация: какой файл актуален.

## Env-переменные

Из коробки их в `.env.example` нет — у каждого проекта свои, дописываются под
проект: `PLATFORM`, `ANDROID_*`,
`APK_PATH`, `ANDROID_HOME_FOR_SIM_LAUNCH`, `REMOTE_PATH_IN_EMULATOR`,
`IOS_*`, `xcode*`, `MOBILE_ELEMENT_TIMEOUT`, `LOCALIZATION_FILE_PATH`.

## Верификация (без эмулятора)

```bash
python3 -m compileall -q Appium Tests/Mobile_tests
.venv/bin/python -m pytest --collect-only -q -m mobile
```

Реальный прогон требует эмулятор/девайс + APK — только в форке.
Стабильность связки launcher → эмулятор → APK проверяется в форке с
железом, не в шаблоне.

## Миграция legacy-форков (appium-flutter-driver)

Старый Flutter-контур (`ButtonActions`, `get_element_by_value_key`,
render tree, контексты FLUTTER/NATIVE_APP, `Appium-Flutter-Finder`)
удалён из шаблона: он построен на deprecated `flutter_driver`. Форкам на
старом слое — git-история до коммита редизайна (2026-07-14). Путь
миграции: разработчики приложения проставляют `Semantics.identifier`
(промпт — locator-conventions.md), app_keys переводятся с
`get_element_by_value_key("ключ")` на `get_element("идентификатор")`,
проверки отсутствия — с `is_widget_not_presented(render_tree, ...)` на
`is_element_not_presented("идентификатор")`.

## Копилка ловушек проекта

Сюда скиллы дописывают ловушки, найденные в работе на этом проекте
(формат: «сигнатура → как избегать», одна строка на ловушку; дедуп
против уже записанных).

Пример формата (запись из реального форка, в шаблоне — образец):

- Flutter `showDatePicker`/`CalendarDatePicker` (встроенный виджет фреймворка,
  не код продукта) не несёт наших `Semantics(identifier:)` и не может их
  получить без форка Flutter → тап по конкретному дню календаря или по
  кнопкам «Отмена»/«ОК» напрямую невозможен без локатора по тексту. Обход:
  тап по иконке «Переключиться на ручной ввод» (сама она тоже без
  identifier, ищется по локализованному accessibility-имени) → в открывшемся
  текстовом поле ввести значение `send_keys` → тап «ОК» (тоже по имени).
  Локатор по тексту тут допустим ровно потому, что виджет не принадлежит
  коду продукта, и держится он изолированным приватным методом СВОЕГО
  модуля, а не в `ScreenActions`.
- Найденный элемент по `ACCESSIBILITY_ID` иногда становится
  `StaleElementReferenceException` при немедленном действии сразу после
  находки другого элемента того же экрана (переключение раскладки клавиатуры,
  автокоррекция и т.п. пересобирают часть дерева семантики) → перезапрашивать
  элемент непосредственно перед действием, не переиспользовать ссылку,
  полученную даже за секунды до этого.
