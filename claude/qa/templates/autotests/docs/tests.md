# Как писать smoke- и regression-тесты

Эталоны: `Tests/Smoke_tests/ExampleFeature/test_example_smoke.py`,
`Tests/Regression_tests/example_resource/test_example_resource.py`,
`Tests/Regression_tests/example_flow/test_example_flow.py` (многошаговый).

---

## Железные правила независимости

Каждый тест обязан проходить **в одиночку, в любом порядке и параллельно**
(pytest-xdist). Отсюда:

1. **Никаких данных из другого теста.** Нужен ресурс — фикстура
   (`create_project`) или создание в самом тесте + регистрация в cleaner.
2. **Фикстуры возвращают значения**, тест принимает их параметром:
   ```python
   def test_get(self, create_project):
       project = Projects.get(create_project)   # create_project == id
   ```
   Общие словари для передачи данных между тестами запрещены.
3. **Только уникальные данные** — генераторы из `src/data_generators.py`
   (`generate_name`, `generate_email`, ...). Никаких фиксированных имён:
   параллельный воркер создаст дубль и один из тестов упадёт.
4. **Ожидание асинхронности** — `wait_until()` из `src/wait_utils.py`,
   никогда `time.sleep`.
5. Данные, созданные inline в тесте, — через `*_cleaner`:
   ```python
   def test_create(self, project_cleaner):
       project_id = Projects.create(name=generate_name("p"))
       project_cleaner.append(project_id)
   ```
   Если тест сам удалил ресурс — сними его с учёта:
   `project_cleaner.remove(project_id)` (образец — test_example_flow.py).

## Структура и разметка

```python
import allure
import pytest

from src.projects.projects import Projects

pytestmark = pytest.mark.regression      # или pytest.mark.smoke / mobile

@allure.epic("Regression")               # Smoke | Regression | Mobile
@allure.feature("Projects")              # имя фичи/домена
class TestProjectsCreate:                # один класс на операцию (регрессия)

    @allure.description("Создание проекта — happy path")
    def test_create_project(self, project_cleaner):
        ...
```

- Регрессия: классы по операциям — `TestProjectsCreate / Read / Update / Delete`,
  один файл на домен, одна директория на домен.
- Smoke: один класс на фичу, только критичный happy-path, минимум подготовки.
- Методы — обычные (`self`), имена `test_<действие>_<ожидание>`.
- Маркеры объявлены в pytest.ini: `smoke`, `regression`, `slow` и по маркеру на
  каждый слой UI. Модульный `pytestmark` обязателен.

## Тестовая матрица регрессии (минимум на CRUD-ресурс)

| Блок | Тесты |
|---|---|
| Create | happy path (id возвращён); поля сохранились (create → get → сверка); 400 на невалидное тело (обязательное поле пустое/пропущено) |
| Read | get по id — данные корректны; get несуществующего — 404; список содержит созданный ресурс |
| Update | PUT — изменение сохранилось; PATCH — меняется только указанное поле; update несуществующего — 404 |
| Delete | delete → get возвращает 404; delete несуществующего — 404 (или 204 — сверить с API!) |
| Доступ | 401 без токена / 403 чужой ролью — если у проекта несколько ролей |
| БД | персистентность через `DbInfo.get_value_where` — где уместно (см. пример в докстринге test_example_flow.py) |

Негативные вызовы — через `status_code=`:
```python
Projects.get(999999999, status_code=404)
Projects.create(name="", status_code=400)
```
Помни: при ожидаемой ошибке клиент возвращает `None` — не разыменовывать.

## Многошаговые сценарии

Эталон — `example_flow/test_example_flow.py`: несколько шагов API + проверки
в одном тесте, все данные — локальные переменные. Многошаговость живёт
ВНУТРИ одного теста, а не растягивается на цепочку зависимых тестов.

## Анти-паттерны (мгновенный реджект на ревью)

- Тест читает id, созданный другим тестом (в т.ч. через session-словарь).
- `time.sleep()` в любом виде.
- Хардкод URL, кредов, фиксированных имён ресурсов.
- Создание тестовых данных в `scope='session'` фикстуре.
- try/except вокруг ассертов «чтобы не падало».
- Тест без teardown-гарантии для созданных данных.

## Верификация (без живого стенда)

```bash
make verify                                           # всё одной командой
.venv/bin/python -m pytest --collect-only -q -m smoke # маркеры фильтруют
```

## Команды прогонов и логи (в форке с живым стендом)

Быстрая обратная связь — гонять минимум, а не весь прогон:

```bash
pytest -x -q Tests/Regression_tests/projects/test_projects.py::TestProjectsCreate::test_create_project
pytest -x -q Tests/Regression_tests/projects/        # один домен, стоп на первом падении
pytest -q -m smoke                                    # только smoke-срез
make regression                                       # полный прогон с allure-результатами
```

Разбор падений: главный источник — `logs/log_<время>_<pid>.log` (пишется
`logger.py` автоматически: каждый HTTP-запрос и ответ с телами). Смотри лог
свежего прогона (свой pid на воркер), а не вывод pytest: в логе видно, что
реально ушло на сервер и что он ответил. Классифицируй причину падения:
*баг теста* (чинить) / *расхождение со спекой* (зафиксировать и спросить) /
*баг стенда* (отчитаться, пометить `xfail` со ссылкой на тикет).

## Маршрутизация по классификации

Классификация падения — не финал отчёта, а маршрутизатор следующего шага.
Три типа → три действия (лимиты железные: упёрся — честный отчёт человеку,
не бесконечный цикл; счётчик каждой петли фиксируется в отчёте, 0 — тоже
значение):

| Тип падения | Действие | Лимит |
|---|---|---|
| Баг теста | чинит fixer на месте | 5 попыток verify / 10 итераций живого прогона |
| Расхождение со спекой | НЕ подгонять ассерт под фактическое поведение: возврат на стадию спеки — спека домена обновляется, тесты правятся по ней, точечный verify | 2 возврата на домен |
| Баг стенда | стоп по домену: `xfail` со ссылкой на тикет + секция в отчёте, решает человек | — (петли нет) |

Тот же маршрутизатор на ревью: находка high «нарушение конвенций» →
возврат к автору домена, лимит 1 круг доработки на домен.

## Ночной прогон (рецепт для форка)

В шаблоне настраивать нечего (стенда нет) — в форке это один GitLab
Pipeline schedule. Settings → CI/CD → Pipeline schedules → ночной cron
(например `0 3 * * *`); джоб по расписанию гоняет smoke-срез по маркеру:
`pytest -v -m smoke --alluredir=testresults/` (заготовка джоба по образцу
`regression` в `.gitlab-ci.yml`, отбор — `-m smoke`), артефакты —
`testresults/` и `logs/`.

**NB про критерий отбора.** MR-смоук (`./run_big_smoke_tests.sh`) берёт
тесты по ДИРЕКТОРИИ `Tests/Smoke_tests`, ночной — по МАРКЕРУ `-m smoke`.
В шаблоне это одно множество (все smoke лежат в `Smoke_tests`), но
smoke-тесты вне этой директории (например будущие в папках слоёв UI)
разведут два контура. Единый критерий выбирает форк: либо держать все
smoke в одной директории, либо перевести и скрипт на маркер.

**Авто-триаж падений.** Утренний разбор — промпт агенту в форке: «Прочитай
Allure-отчёт ночного прогона и `logs/log_<время>_<pid>.log` (там каждый
HTTP-запрос и ответ с телами — видно, что реально ушло на сервер), разложи
каждое падение по классификации: баг теста / баг стенда / расхождение со
спекой, с доказательством из лога». Дальше падения идут по маршрутизатору
из секции «Маршрутизация по классификации» выше — с теми же лимитами петель.
